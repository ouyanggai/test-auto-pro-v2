## 1. 到底发现了什么

目标源码说明：**有的地方可能“还没做完就往下走”，有的地方可能“已经做完了还在等”。** 优化要把这两种情况分清楚。

以下机制在目标源码里可以确认；当前执行器具体碰到多少、耗时多少，还需要第一步实测。不能把源码风险直接当成当前项目已经发生的故障，也不能现在承诺快几倍。

### 1.1 表单填进去了，不等于已经准备好

填入值以后，下拉选项、人员选择、显示文字和联动脚本可能还在后台处理。目标代码里的 `setData` 只等下一次页面更新，不等后面的所有联动；`fmDone` 事件和弹窗出现也不能证明这些工作都结束。部分组件还会过 200 ms 或 1000 ms 才开始初始化。（C17～C21）

**会出什么问题：** 太早提交可能丢字段、带旧值或显示值不对应；统一等很久，又会让已经准备好的普通表单白等。

**准备怎么改：** 后续按具体表单种类确认哪些工作必须结束，结束后就继续。保留原有校验、联动和完整取值；没有查清的动态脚本不提前省掉。第一步只记录这些时间，不改等待。

### 1.2 接口返回成功，不等于整件事做完了

普通发起可能要先保存业务数据，再发起流程，最后绑定业务记录。转发成功后还要给新实例保存当前附言；`fuyan` 勾选只控制是否复制原附言，不决定这次附言是否保存。即使当前附言为空，源码里的第二笔保存仍会执行。（C12、C13）

另外，有些请求包装会先返回成功，异步回调还没结束；有些错误和 401 分支会让外层等待一直不结束。（C22）

**会出什么问题：** 只看 HTTP 成功，会漏业务绑定或附言；看到没结束就重跑，又可能重复发起或重复审批。

**准备怎么改：** 分开判断“主请求成功”“必要后续保存完成”和“结果已核对”。后续保存失败时，保留已经成功的部分，不能把整个动作再发一遍。

### 1.3 看起来是查询，实际上也可能改数据

例如 `submit(first)` 看起来在检查是否能发起，但缺少流程代理时，会先复制模板或表单代理，再返回权限结果。表单数据源和动态脚本也可能调用业务写接口。（C11、C24）

**会出什么问题：** 把这类请求当普通查询缓存或自动重试，可能省掉必要准备，也可能多写一次。

**准备怎么改：** 沿着真实调用链确认有没有改数据，再决定能否复用或重试。不能只看接口名字，也不能用 GET、POST 来判断。

### 1.4 同一个账号的任务，可能互相影响

登录票据 SID 对应的不只是账号，还涉及登录类型、平台、项目和客户。重新登录可能使旧 SID 失效；网关处理请求时，也可能修改这张票据关联的平台和客户信息。（C02、C03）

同一个流程实例的审批还会争同一把数据库行锁。页面里有全局事件总线，晚到的事件也可能影响另一个组件。（C09、C23）

**会出什么问题：** 一口气增加并发，可能错账号、错项目、错实例，或者只是让多个动作排队抢锁，速度没变。

**准备怎么改：** 同实例的完整动作由一个执行者推进。不同实例能否并发，还要检查它们是否共用登录信息、页面事件或同一个业务对象。稳定登录环境里互不依赖的普通读取，才考虑有限数量的并发。

### 1.5 有些读取和整表复制确实可以研究减少

目标已有按任务关联 ID 缩小列表范围、按实例 ID 批量读取的能力。表单 `getValues` 会复制整张表，连 `getValue` 取一个字段也会先复制整表；反复逐字段轮询未必便宜。（C05～C08、C20）

**会出什么问题：** 重复请求和大表单复制浪费时间；但换成另一个“更精确”的接口，可能绕过原来的权限过滤，或者拿到不完整字段。

**准备怎么改：** 先统计真正重复的工作，再减少同一轮、同一身份和参数下的重复读取。保留权限、分页、缺失项判断，以及提交前必要的校验和完整数据。

### 1.6 为了展示而读的数据，也有不能省的部分

流程图用到了最新批次、实际处理人、会签人数和后继节点结果；这些不能拿配置人名、旧批次或单个状态字段代替。不同接口分别读取，也不能假装它们来自同一时刻。

**准备怎么改：** 不常看的详情可以以后按需加载。但展示用的旧记录不能成为“现在允许提交”的依据，打开动作时仍要核对当前任务、节点和权限。来源见附录的“页面展示依据”。

## 2. 可靠和快，怎么同时兼顾

这里的取舍不靠统一多等几秒，也不靠把所有操作都并发。判断顺序固定如下：

| 遇到的情况 | 后续准备采用的做法 | 不能越过的线 |
|---|---|---|
| 同一轮里完全相同、已证明只读的请求 | 研究只发一次，给需要它的地方共用结果 | 身份、权限、完整参数都相同；失败不能当空结果；写后重新读 |
| 同一登录环境里互不依赖的普通读取 | 研究同时发出，并限制同时请求数量 | 不夹带登录切换、代理准备或动态业务写；保留错误和分页 |
| 表单正在初始化或联动 | 必要工作做完就继续，减少多余等待 | 最后一次填值后的联动、显示值和原有校验必须完成 |
| 同一实例要推进流程 | 一个执行者负责完整步骤，其他动作排队 | 不能只锁主请求，把前后保存放到保护范围外 |
| 请求超时，不知道目标是否已经写入 | 记录“结果不确定”，先核对事实 | 不能自动重发整个动作，更不能把不确定记成成功 |
| 只为展示读取详情 | 研究展开时再读 | 当前操作所需的最新任务、权限、批次不能省 |
| 想复用页面或浏览器资源 | 最后再做，先测创建成本，再证明清理完整 | 登录、存储、监听器、全局事件和迟到回调不能串到下一任务 |

目标源码没有要求“每个动作必须新建一个浏览器环境”，也没有证明复用环境一定安全。后续选哪种隔离方式，要以能证明不串任务为前提，不能先建资源池再补证明。

## 3. 先后顺序：一次只改一小项

下面是后续路线，**不是一次性开工清单**。用户明确批准第一项后，也只实施 F-045；后面的每项要根据实际记录再确定范围。

| 顺序 | 这一阶段要交什么 | 明确不顺手做什么 | 怎样才可以继续 |
|---|---|---|---|
| 第一步 P0：记清现状 | 源码与部署版本对照；现有调用步骤；每段耗时；记录自身开销 | 不减少请求、不缩等待、不加并发、不改重试和结果判断 | 记录没有改变功能，相关自动验证通过，用户人工核对并验收 |
| 第二步 P1：省重复读取 | 从一个动作里选一项：同轮去重、原列表精确过滤、批量读或独立读并发 | 不绕权限；不把写前旧数据带到写后；不跨登录环境共用 | 身份、权限、分页、缺项和失效场景通过，并且实测有收益 |
| 第三步 P2：少白等、别早走 | 从一种表单或动作里确认完成条件，减少无用轮询和等待 | 不跳校验、联动、人员选择或后续保存 | 延迟、乱序、错误、卡住和各类选择都正确，用户核对该种表单 |
| 第四步 P3：提高执行效率 | 同实例完整动作排队；已证明互不影响的任务有限并发；取消尚未发出的等待任务 | 不取消或重发已经送到目标的写；不把共享账号或业务对象当独立资源 | 双击放行、晚回调、跨实例和途中失败都不重复写、不串任务 |
| 第五步 P4：减展示和资源开销 | 非必要详情按需读取；明确页面生命周期；符合条件才复用 | 不拿展示缓存放行；不先做大资源池；不隐藏实际工作量 | 展示完整，长时间运行无泄漏，身份和事件隔离得到验证 |

P1 不需要把表里的四个候选一起做；P2 也不需要一口气覆盖所有表单。任何阶段都先缩到一个能单独验收的变化。前一步通过后，按真实数据决定下一步做什么，不按猜测收益排序。

## 4. 第一项实施到底做什么

F-045 的目标只有一个：**在原来的调用旁边记时间和步骤，把“慢在哪、有没有漏步骤”查清楚。它本身不负责提速或修复执行行为。**

按以下顺序执行：

1. 核对本机参考源码、目标部署、前端组件和实际 FormMaking 构建是否对应。对应不上的地方写“未确认”，不把本机 Git 版本冒充部署版本。
2. 先列普通 FormMaking 发起/同意这一组，以及转发这一组的完整步骤。写明校验、身份、实例/任务/批次/节点、前后保存、四类人员选择和失败位置。其他动作即使顺带记到了，也不算验收过。
3. 只在已经发生的调用上记身份、参数、开始、完整响应、错误以及已有回调中可见的开始和结束。现有调用点看不到的内部异步结束时间记“未知”；不改目标组件，不全局拦截 Promise、定时器或事件，不为了看状态额外请求目标、登录、调用表单方法或挂载组件。
4. 把“响应正文读完”“原有页面或脚本处理结束”“后续业务保存结束”分开记录。没结束就记“仍未完成/未知”，不由记录逻辑取消动作、改结果或补一次提交。
5. 本地用目标源码提取的方法或按源码编写的模拟接口验证：加记录前后调用次数、参数、顺序、返回、错误都一样；新增目标请求和表单调用都为零。
6. 对比开启和关闭记录的耗时、内存分配和慢请求情况。记录本身不能造成明显退化或影响现有截止时间；有问题先减轻记录。
7. 提供真实采集和核对步骤。自动验证后停在 `ready_for_manual`；用户自行核对或明确授权代理验收，都要实际满足完成标准才记为 `accepted`。本次已授权代理核对，但没有全部通过，具体结果见 F-045 第 13 节。

已有执行行为如果与目标源码不一致，先记成独立问题。本切片不能一边采集，一边顺手修等待、错误处理或业务步骤。

## 5. 后面照着做，怎样防止越做越大

每次代码实施前，先在当次功能文档中写全以下六项；缺一项就先补计划，不能边做边扩大：

| 必须写清 | 具体要求 |
|---|---|
| 只改哪里 | 哪一种动作、哪一种表单、哪一个入口、哪些现有文件需要改 |
| 要解决什么 | 本轮记录证明的具体重复工作、等待或可靠性问题；目标源码依据 |
| 绝不能变什么 | 权限、表单字段和显示值、校验、选择、前后保存、错误和已发生写入 |
| 怎么证明 | 当前范围的本地测试、耗时比较、用户页面核对步骤 |
| 交付什么 | 一个可运行改动、验证记录、中文提交、当前已知未验证项 |
| 在哪里停 | 自动验证完成后停人工验收；不自动开始下一项 |

共同约束：

- 业务依据继续只看目标源码。实施时可以查看本项目当前代码确定接线位置，但不能从以前文档恢复业务规则。
- 不确定的动态脚本、未知组件或端点不能靠猜测省掉。先查当前源码和实际配置；查不清就保留依赖并记录未知。
- 不顺手加数据库字段、迁移、对外接口、资源池或大架构改造。确有必要时，先写清原因、范围和验证方式，重新取得该项批准。
- 程序里只保留本次确定的一条执行路径。替换时删除被替代代码和测试，不加入新旧两套兼容、自动回退或双写。
- 测试放在根目录 `test/` 对应分类里，只运行当次相关测试；修改的 Go 函数和关键逻辑按项目要求补中文说明。
- 不自动启动浏览器、不自动向真实目标发业务写、不代替用户验收。验证通过的原子成果使用中文提交。
- 完整请求/响应按项目要求在本地运行日志中记录；凭证、真实运行日志、缓存、构建产物和参考源码不提交。

## 6. 怎样证明没有把功能改坏

不能只比“最终状态相同”或“都返回 200”。每项优化前，先用当前目标源码写出这类动作本来要发生什么，再核对下面这些内容：

| 要核对什么 | 至少要看什么 |
|---|---|
| 身份和权限 | SID、登录类型、平台、项目、客户、查看谁的待办；普通权限账号也要覆盖 |
| 流程归属 | 实例、任务关联 ID、任务 ID、批次、节点、代理是否指向同一次操作 |
| 表单 | 实际值、显示值和虚拟伴生字段；校验和动态脚本的合法变化是否保留 |
| 完整步骤 | 必要请求、因果顺序、前置保存、主写、选择、绑定和附言是否齐全 |
| 失败后已经做了什么 | 前置已保存、主写可能成功、后置失败时，不能假装什么都没写 |
| 页面展示 | 最新批次、实际处理人、会签人数、并行节点和跳过后的证据是否完整 |
| 并发和资源 | 同实例双放行、跨项目、共享业务对象、迟到事件、初始化失败和长时间运行 |

各项的必要特殊情况：

- 同一登录类型/用户/平台重登、跨平台或项目、401，不能用旧票据覆盖新登录。
- 列表的 `data.id` 是任务关联行 ID，不是 `jobTaskId`。会签的 pending/done、分页和缺项不能自行简化；查不到或读失败不能放行。
- 四类选择都要保留：`custom_choose`、`parallel_choose`、`run_node_choose`、`extended_attribute_users`。不能凭空限制为三类或统一只允许一次继续。
- 覆盖延迟初始化、多级联动、选项乱序、一直不结束的回调、正文中断、主写响应丢失和后续保存失败。
- 普通发起、同意、不同意、暂存的校验和脚本不同。暂存会保存数据，但不等于推进流程，不能用同一套成功条件概括。
- 时间、新 UUID 等正常差异只按提前写明的对应关系比较；不能忽略任意字段，也不能拿历史表单全字段相等否定合法脚本变化。
- 动态脚本没查清的种类不裁剪依赖；特殊全权限账号通过不能代替普通用户权限通过。

测速度也要用同一段用户操作比较：进入页面到信息可用、点击详情到详情齐全、准备动作到必要后续业务完成。把请求移到后台，或者把预加载改为点击后加载，不能直接记成“省掉了时间”。

记录典型耗时、慢端耗时（100 次里 95 次不超过的耗时，即 P95）、最大耗时、真实请求数、排队、页面/资源数、内存分配和峰值。首次/重复加载、无人看页面/持续观察、同/跨登录环境、正常/延迟/中断分别比较。并发工作重叠的时间不能重复相加或相减。

## 7. 每次切换的具体步骤

这些步骤适用于后续已经获批并验证的优化；F-045 不包括上线部署。

1. **固定这次范围。** 写明改哪个动作/表单、减少什么、保留什么、依据哪段源码，还有什么未知。用户批准这一项后再动代码。
2. **完成一个实现。** 先做当前范围的功能验证，再测性能。需要一起变化的前端、执行器或服务形成一个完整可运行版本；数据库或接口变化另行规划。
3. **准备人工核对。** 写明真实页面上的操作和应看到的结果，保留前一个完整程序版本。测试记录要区分实际通过、失败、未做和未知。
4. **切换前停止接新动作和新放行。** 已送出的业务写、必要后续保存、目标 HTTP 转发、WebSocket 待返回请求、工作队列和落账要查清。页面和浏览器资源也要按实际生命周期核对。会话表为空、点了暂停或关了窗口，都不能单独证明没有任务还在执行。
5. **确认旧动作不会再写，再换完整版本。** 存在未确认的请求，先记录并核对；不能因为等过了超时时间就直接判定结束。只运行一个版本，必要时刷新旧页面。
6. **先检查版本、身份和只读状态。** 然后由用户按受控场景手工操作，核对字段、处理人、节点、附言和业务绑定，同时留完整时间记录。
7. **停在人工验收。** 用户确认功能和收益后，才考虑下一小项。任何重复写、错身份、丢字段、错批次/节点、漏附言/绑定、错误放行、资源未结束或明显慢端退化，都停止扩展，返回本项修正。

### 出问题时怎么停、怎么恢复

先停止接新动作，确认已送出的写和后续保存处于什么状态，再决定恢复前一个完整程序版本。恢复程序版本不是撤销目标业务数据，也不能顺便改历史记录或重新发送结果不确定的请求。

主写成功、附言或绑定失败时，要保留“主写已成功、后面失败”的事实。能否只补后面一笔，必须单独检查端点、当前业务记录和重复写风险，并取得这次补写的明确授权。本计划不授权默认补写。

如果仍有请求不知道是否执行完，先做只读核对或交给人工确认；不能拿“超时已过”“会话数为零”作为已经排空的证据。

## 8. 已经验证了什么，还有什么没验证

本轮做过一个内存模拟：从目标 FormMaking 源码原样提取 `setData`，模拟下一次页面更新和异步联动。等待 `setData` 返回时，主字段已变，但联动字段还是旧值；后面的异步结束，联动字段才更新。

| 时点 | 主字段 person | 联动字段 derived | 联动是否结束 |
|---|---|---|---|
| 等到原 setData 返回 | new | old | 否 |
| 模拟异步联动结束 | new | linked | 是 |

模拟里的 50 ms 是人为设置的时间，不是目标平台真实耗时。这个实验只证明“方法返回不等于联动结束”，没有证明真实业务通过或优化提速。没有启动 Vue 页面、浏览器或目标服务。

当前未确认：参考源码与部署是否一致、SID 有效期和限流配置、所有具体表单和动态脚本、跨服务失败后哪些保存能撤回、哪些写请求可安全重发、实际并发容量、回调何时可见、当前执行器各段真实耗时。

“不能破坏当前功能”在这里落实为可检查的条件：**没有证明可以省的步骤先保留；完整功能先验证；不确定的写不重发；切换前查清在途动作；每项停下来给用户验收。** 不能把尚未确认的情况写成已经安全。
