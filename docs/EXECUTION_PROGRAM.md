## 1. 愿景与可判定标准

愿景是“可配置执行、可观测、好用、易用、简单易懂”。愿景必须可判定，否则无法验收。本文把它固化为五条验收标准，后续每个切片都要说明自己把哪一条推进了多少。

| 愿景 | 可判定标准 |
| --- | --- |
| 可配置执行 | 任何一条数据状态为 `ready`、节点状态为 `configured` 的路径，用户不写代码、不改配置文件、不手工调接口，就能选定运行模式启动，并一直跑到成功断言给出判定。 |
| 可观测 | 任意一次失败，用户在运行详情里三次点击内到达解释它的那一行日志。任意一次工具程序异常，都有独立的程序错误日志记录，且界面文案与日志文案同源。运行结束后不依赖记忆就能复现整条请求序列。 |
| 好用 | 启动运行、看当前进展、看失败原因、处理写结果不确定，这四件事都在当前页完成，不需要跨页拼信息，不需要人工比对内部标识。 |
| 易用 | 运行模式、断点、暂停、放行、停止全部用中文业务语言表达；界面不出现目标内部 ID、字段英文名、状态枚举值和技术栈名词。 |
| 简单易懂 | 执行器没有单文件超过 800 行；一步执行的生命周期固定为七个阶段，这七个阶段在日志里能被肉眼逐行读出来；任何人读一份运行日志目录就能还原这次运行。 |

## 2. 现状基线：执行器可以直接消费什么

F-012 交付后，执行器不需要重新发明任何配置语义。可直接消费的输入如下。

- 真实流程结构与已选路径：`internal/analyzer` 的流程树与路径拓扑，路径与分支选择已持久化（F-004、F-005）。
- 路径要求：条件、人员规则、节点类型的只读分析结果（F-006）。
- 历史业务数据：目标原始表单数据快照与路径级来源覆盖，分支驱动字段的最小补丁（F-012）。
- 人员策略：节点级不透明候选键，运行时才解析为真实处理人（F-012）。
- 动作目录与门禁：`internal/engine/actioncatalog`，每个动作已带 `TargetOperation`、`Preconditions`、`Enabled`、中文 `DisabledReason`、`ReloadRequirements`。这就是执行器的写请求派发表。
- 编译场景：`internal/engine/scenario` 输出 `[]model.CompiledActionStep`，已区分 `user` / `recovery` / `navigation` 三种来源，并带 `Precondition`、`ExpectedEffect`、`StopOnFailure`、`RecoveryPolicy`、`ReloadRequired`。模型注释已写明“是未来执行器消费的只读步骤”。
- 目标读取通道：`internal/adapter/target` 是唯一允许接触目标平台的区域，会话与 SID 只在内存。
- 可借鉴的进程内 Worker 形态：`internal/formruntimemaintenance` 已有“数据库状态 + 租约 + fencing token + 有界日志 + Runner 循环 + 启动恢复”的完整实现，执行器沿用同一形状，不另造调度框架。

目前空缺的是：真实写通道、运行记录、运行控制、分层日志、日志查看入口、目标语义的系统化对照。`web/src/views/RunsView.vue` 仍是六行占位页。

## 3. 概念与术语补充

以下术语补充进 `CONTEXT.md` 的术语表（本文生效后由第一个切片同步）。

| 术语 | 含义 |
| --- | --- |
| 运行 | 一次启动动作产生的整体事实，覆盖该计划本次参与的全部路径。 |
| 路径运行 | 一次运行中一条执行路径的独立事实，独占一个真实目标主实例。 |
| 步骤 | 编译场景中的一条 `CompiledActionStep`。用户步骤、系统恢复步骤和系统导航步骤都各算一步。 |
| 尝试 | 一个步骤的一次执行。一个步骤可以有多次尝试，但每次尝试最多发出一次目标写请求。 |
| 事实重读 | 写请求之后回到目标平台重新读取实例、任务、节点和演员，用读到的结果判定这一步的成败。 |
| 写结果不确定 | 写请求已发出但无法确定目标是否生效（超时、连接中断、响应不可解析、进程崩溃）。 |
| 对账 | 通过事实重读判断不确定写是否已生效，并得出唯一合法的后续动作。 |
| 断点 | 挂在尚未执行的步骤、节点或动作类型上的暂停条件，只对当前运行生效。 |
| 运行日志 | `logs/runs/` 下按运行组织的诊断材料，可按保留期清理，不是运行事实。 |
| 运行事实 | 存在数据库运行记录表中的不可覆盖数据，永不自动删除。 |

节点运行状态沿用已定义的九个中文状态，不新增、不改名：未开始、等待运行、运行中、核验中、暂停、已完成、失败、已停止、已取消。

## 4. 执行器

### 4.1 代码边界与拆分

执行器落在 `internal/engine` 下，按职责拆包。这一条是硬约束：V1 曾把编排写成 10523 行的单文件，不能重演。

| 包 | 职责 | 禁止 |
| --- | --- | --- |
| `internal/engine/run` | 运行与路径运行的状态机、租约、启动恢复 | 不直接发目标请求 |
| `internal/engine/step` | 一步的七阶段生命周期 | 不做多路径调度 |
| `internal/engine/gate` | 执行前门禁复验，复用 `actioncatalog` | 不改写门禁结论 |
| `internal/engine/reconcile` | 不确定写的对账与唯一合法恢复动作 | 不自动重发写请求 |
| `internal/engine/control` | 运行模式、断点、暂停、放行、停止 | 不修改已发生事实 |
| `internal/engine/schedule` | 串行、并行、最大并发、单次定时启动 | 不做周期调度 |
| `internal/engine/assert` | 成功断言判定 | 不用工具推断代替目标事实 |
| `internal/logging` | 分层日志、日志作用域、脱敏、轮转与清理 | 不承载业务判断 |

目标写请求仍然只能由 `internal/adapter/target` 发出。执行器给出语义意图，适配层负责协议。

### 4.2 运行状态机

运行：`等待运行 -> 运行中 -> 已完成 | 失败 | 已停止 | 已取消`。暂停不是运行的独立状态，而是运行中且存在被暂停的路径运行。

路径运行：`未开始 -> 等待运行 -> 运行中 -> 核验中 -> (已完成 | 失败 | 暂停 | 待对账 | 已停止 | 已取消)`。

不可破坏的约束：

- 状态只前进，不回退。需要“重新运行此路径”时新建一次运行，不复用旧路径运行。
- 一条路径失败不终止其他路径。运行的整体结论由所有路径运行汇总得出。
- 进程崩溃后重启，处于`运行中`或`核验中`的路径运行一律进入`待对账`，绝不自动继续。因为崩溃前可能已经发出过一次写请求。
- 租约与 fencing token 保证同一路径运行同时只有一个 Worker 推进，形状与 `formruntimemaintenance` 一致。

### 4.3 一步的七阶段生命周期

这是执行器的核心，也是“简单易懂”和“可观测”的落点。每一步固定走七个阶段，每个阶段都写一行 `step.log`，阶段名就是日志里的 `phase=`。

1. `plan` 取步。从编译场景取下一个未执行步骤，分配 `step_id`，记录步骤来源、动作、语义节点、演员策略。
2. `gate` 门禁复验。重读目标实时上下文投影为 `model.ActionContext`，用 `actioncatalog` 重新计算门禁。配置时通过、此刻不通过，就停止并给出中文原因。**门禁不通过绝不跳过**，产品已明确不做“跳过失败写动作”。
3. `control` 控制判定。按运行模式与断点决定是继续、还是暂停等待放行。暂停在这里发生，不在写请求中间发生。
4. `prepare` 演员与会话。把人员策略解析为真实处理人，取得该处理人的目标会话。SID 只在内存，不进日志、不进数据库、不进快照。解析不出唯一真实处理人就停止，不模拟、不替换处理人。
5. `submit` 发写请求。按动作目录的 `TargetOperation` 发出**唯一一次**写请求，生成 `trace_id` 与 `curl_trace_id`，写 `network.log` / `network-error.log` / `curl.log`。这一阶段内部禁止任何重试。
6. `verify` 事实重读。路径运行进入`核验中`，重读实例状态、当前节点、当前待办、演员与已办，给出三值判定：确定成功、确定失败、不确定。写请求超时或响应不可解析，不等于写没有发生。
7. `settle` 落账。把尝试结果以 INSERT 写入运行记录，推进节点状态与步骤游标。判定为不确定时路径运行进入`待对账`并停止。

一条不可协商的规则：**一次尝试最多一次写请求；任何重发都必须先经过 `reconcile`，并作为新的一次尝试记录。**

### 4.4 写结果不确定与安全重试

- 先对账后动作。对账只允许读，通过实例状态、当前节点、当前待办、已办记录和动作痕迹判断上一次写是否生效。
- 对账得出三种结论，每种只对应一个合法后续动作：已生效则前进到下一步；未生效则允许重放同一步；仍无法判定则保持`待对账`并要求人工确认，不给第二个按钮。
- 界面上只出现这一个合法恢复动作，避免用户在“重试”和“继续”之间猜。
- 对账过程、结论、依据和最终决定全部写 `recovery.log`，并落 `run_step_attempts`。这一段沿用 V1 已验证的 `recovery.log` 字段语义。

### 4.5 暂停、停止、并发与定时

- 暂停只在阶段 3 生效，不打断已发出的写请求。已进入 `submit` 的步骤必须走完 `verify` 和 `settle` 才能停。
- 停止是终态，产生`已停止`；已发生的事实全部保留。
- 串行按路径顺序推进；并行按计划保存的最大并发数推进，同一路径内部永远串行。
- 定时启动只支持单次定时，并强制自动模式。周期调度是产品明确不做的事情。
- 放行按钮只出现在当前打开的那条路径运行详情里，不提供批量放行。

## 5. 调试器

调试器不是独立页面，也不是“仅观测模式”（产品明确不做）。它是真实运行过程中的控制能力，寄生在路径运行详情页。

### 5.1 运行模式

每次启动时选择，不写进计划配置：

- 自动运行：连续执行，只在断点、门禁不通过、需要人工或写结果不确定时停。
- 单步运行：每一步执行前都停，等用户放行。
- 人工控制：不自动前进，用户逐步放行，并可随时改断点。

定时启动强制自动运行。

### 5.2 断点

断点全部挂在“尚未执行的对象”上，只对当前运行生效，可随时增删，每次增删都写 `control.log` 与 `run_controls`。

| 断点类型 | 命中时机 | 默认 |
| --- | --- | --- |
| 首次写断点 | 本次运行的第一个写请求之前 | 开启，作为安全阀 |
| 步骤断点 | 指定编译步骤执行之前 | 关闭 |
| 节点断点 | 进入指定语义节点之前 | 关闭 |
| 动作断点 | 指定动作类型（如不同意、回退、撤回）执行之前 | 关闭 |
| 路径偏离断点 | 分支条件求值后实际命中分支与已配置路径不一致 | 开启且不可关闭 |

路径偏离本来就该停，所以它不是可选项。

### 5.3 单步语义

- 执行一步：走完下一个编译步骤的七个阶段。
- 执行到下一节点：连续执行直到语义节点变化，然后暂停。
- 继续运行：自动执行直到命中断点、需要人工或本路径结束。

调试器允许：暂停、放行、停止、增删断点、对不确定写执行唯一合法恢复动作。

调试器禁止：跳过一步、修改已发生事实、任意跳节点、重置目标实例、在运行中修改计划配置。前四条是产品明确不做的事情；第五条来自“产生运行记录后固化”的产品原则。

### 5.4 暂停时可检视的内容

这是“足够的数据来分析运行情况”的界面侧对应，也是调试器的全部价值所在。

- 当前目标事实：实例状态、当前节点、当前待办、当前演员、已办情况，全部用业务名称展示。
- 下一步预览：动作、演员、预期效果、门禁结论，以及即将发出的请求的可复现形式（脱敏后）。
- 当前路径的条件字段实际值与命中分支。
- 本步已产生的日志行，直接给出跳转入口。

不提供修改表单值、跳过步骤和重置实例的入口。

## 6. 日志系统

参照 `/Volumes/oygsky/bigsys/test-auto-pro`（V1）已被用户认可的形态设计，并补上它缺的那一块。

### 6.1 V1 的形态与缺口

V1 的可用之处，全部保留：按运行分目录、单行 `key=value`、`trace_id` 与 `curl_trace_id` 双向关联、成功与失败分文件、独立的 `curl.log` 提供完整可复现命令、独立的 `recovery.log` 记录恢复决策、运行记录里存 `networkLogRef` 指向具体日志、用 code-server 直接看日志目录。

V1 的缺口，本文补齐：

1. **没有按运行组织的程序日志。** V1 只有一个全局 `logs/app.log`，所有运行、所有请求、所有后台任务混在一起。要分析某次运行时打开运行目录，看不到工具自身当时在做什么。
2. **没有独立的程序错误日志。** 工具自身的异常、panic、SQL 失败、JSON 解析失败、状态机不变量被破坏，全都淹在 `app.log` 里，而且控制台还刻意屏蔽了 ERROR。用户说“少了程序的错误日志”，指的就是这里。
3. **没有执行器决策流水。** 只能看到发出了什么请求，看不到为什么发这个请求、门禁怎么判的、为什么在这里停。
4. **没有控制事实。** 暂停、放行、停止、断点无处可查（V1 本身也没有单步能力）。
5. **日志行没有级别列，也没有行号回指**，只能靠 `trace_id` 搜索，无法直接跳到某一行。

### 6.2 文件布局

```
logs/
  app.log                      全局程序日志（INFO 及以上）
  app-error.log                全局程序错误日志（仅 ERROR 与 panic）        [新增]
  archive/app-YYYY-MM-DD.log
  archive/app-error-YYYY-MM-DD.log                                        [新增]
  runs/<计划名>/<路径名>/<运行号>/
    meta.json                  运行身份、运行模式、配置指纹
    step.log                   执行器七阶段决策流水                        [新增]
    program.log                本次运行内的程序日志                        [新增]
    program-error.log          本次运行内的程序错误与 panic 栈              [新增，核心缺口]
    network.log                目标请求成功与运行提示
    network-error.log          目标请求失败与最终错误
    curl.log                   可直接重放的完整请求块
    recovery.log               对账、恢复与重试决策
    control.log                运行模式、断点、暂停、放行、停止              [新增]
```

目录名沿用 V1 的可读分段（计划显示名 / 路径目录名 / 运行号），因为用户就是靠这个在 code-server 的文件树里找运行的。分段全部经过路径清洗，不接受目标返回的原始名称直接落盘。

同一条程序日志同时写全局文件和当前运行文件：全局用于跨运行排查，运行内用于“打开一个目录就够”。这是双写，不是替代。

### 6.3 统一行格式

所有 `.log` 文件统一为单行 `key=value`，空格分隔，值内空格替换为下划线，空值写 `-`。前两列固定：

```
time=2026-06-25 17:17:56 level=info ...
```

V1 的 `network.log` 没有级别列，V2 统一补上，这样 `grep level=error logs/runs/**/*.log` 就是一次完整的失败清单。

必须贯穿全部日志的关联键：`run_id`、`path_run_id`、`step_id`、`attempt`、`phase`、`trace_id`、`curl_trace_id`。它们通过 `context.Context` 携带的日志作用域自动注入，不靠调用方逐处传参，形状沿用 V1 的 `LogScope`。

多行内容只允许出现在 `curl.log` 和 `program-error.log`，并且必须用块包裹，便于折叠和 grep：

```
--- begin curl trace_id=40b79dd79e7be71b ---
...
--- end curl trace_id=40b79dd79e7be71b ---
```

### 6.4 程序错误日志的字段要求

这是本次新增的核心文件，字段按“能不能定位问题”倒推，不是随手打印错误字符串。

| 字段 | 作用 |
| --- | --- |
| `error_class` | 分类为工具缺陷、工具配置、工具存储、工具依赖、目标契约不符、目标运行时拒绝、网络、未知。产品原则要求工具问题与目标平台问题分开说明，无法判断时按工具问题处理，这个字段就是那条原则的落点。 |
| `error_chain` | 展开后的 Go 错误链，保留每层的包装信息。 |
| `source` | 触发位置的包、文件与行号。 |
| `stack` | 仅 panic 时写，有界截断（建议 4 KiB），放在块结构里。 |
| `run_terminated` | 这次异常是否终止了运行。 |
| `user_message` | 界面上给用户看到的中文文案。日志与界面必须同源，否则事后无法对齐用户描述与日志。 |
| `step_id` / `phase` / `trace_id` | 关联到具体一步和具体一次请求。 |

同时要求：任何被吞掉的错误都算缺陷。执行器不允许出现忽略错误的分支；实在只能记录的情况必须显式写 `level=warn` 加原因。

### 6.5 日志原样记录（内网）

用户已明确：本项目是内网请求与测试，日志的唯一目标是方便找问题和排查问题，不做与此无关的安全处理。因此日志按 V1 已验证的方式原样记录，不引入脱敏层、不引入诊断级别开关、不做正文摘要化。

- 目标请求与响应正文原样写入 `curl.log`，`curl=` 必须是可直接复制重放的完整命令，包含真实会话值。会话短期有效，事后不可重放不是问题，能在出问题的当时立刻重放才是价值所在。
- 目标实例 ID、任务 ID、节点 ID、代理 ID、处理人标识原样写入日志。没有它们就无法拿着日志回到目标平台核对那条真实数据，这是 V1 日志好用的直接原因。
- 工具自身的 SQL、参数、状态机快照和错误链原样写入 `program.log` 与 `program-error.log`。
- 不做的事：脱敏过滤器、日志级别开关矩阵、正文结构指纹替代正文、按角色裁剪日志。

仍然保留的两条，都不是安全考虑而是别的原因：

- 日志文件不进 Git。它们是运行产物，仓库只存代码与文档，这是既有的仓库卫生规则。
- 公开 DTO、API 响应和界面继续只给业务名称与不透明键。这来自产品规则“不面向用户的内部标识体系”和“界面使用中文业务语言”，与日志无关。日志给排查者看，界面给测试人员看，两者要求不同。

### 6.6 容量、轮转与清理

- 运行内单个日志文件有界（建议 8 MiB），超出后轮转为 `.1`，最多保留 3 个。沿用 form-runtime 维护已验证的有界日志思路，避免一次异常刷爆磁盘。
- `logs/runs/` 按保留期清理，默认 14 天并可在系统设置里调整（V1 默认 7 天）。
- 清理只删过期运行的诊断材料，永不触碰数据库里的运行事实。运行事实不自动删除，与产品“明确不做自动删除、归档体系”一致。

### 6.7 查看方式：code-server

保留用户已经满意的方式，不另造日志页面（产品明确不做独立技术状态页）。用户已确认 code-server 与其余服务一起进 Docker，正式发布用 Docker Compose。

- 镜像沿用 V1 已验证的 `codercom/code-server` 固定版本，挂载 `logs/` 目录，内网直接访问，不设登录，带健康检查。
- 分两步交付：F-013 先给一个可立即使用的启动方式（`make` 目标或单条 `docker run`，挂载本机 `logs/`），让日志底座当场可验证；完整编排放到 F-023 与后端、前端、`form-runtime` 和 MySQL 一起打包。
- 挂载可读写而不是只读。用户要在编辑器里搜索、标注、临时删旧目录，只读会挡路，而这里没有需要防的对象。
- V2 增加从运行记录跳到日志的能力。V1 只存了`相对路径 + trace_id`，仍需进编辑器搜索。V2 在落账时把该记录所在的**行号**一并存进运行记录，界面按钮直接跳到那一行。
- 深链形式需实测确认后才能在界面上承诺：code-server 支持以查询参数打开目录，打开指定文件与行号的参数形式必须在实施时实际验证。未验证通过前按钮退化为“复制日志位置”，不展示没验证过的跳转。
- 按钮只显示“查看日志”。路径与 `trace_id` 放在复制内容里，不作为页面主要信息。

## 7. 运行记录

### 7.1 不可覆盖

- 事实表只 INSERT，永不 UPDATE、永不 DELETE：步骤、尝试、事件、控制、断言判定。
- 聚合表（运行、路径运行）允许状态列单向前进式更新，但每次更新必须在同一事务内追加一条事件行，做到“状态怎么变的”可回放。
- 计划在首次产生运行记录后固化，后续运行不覆盖历史事实。“再次运行”和“重新运行此路径”都是新建运行，不改旧记录。

### 7.2 数据模型

| 表 | 内容 | 关键约束 |
| --- | --- | --- |
| `runs` | 一次启动：计划、运行号、运行模式、触发方式、并发上限、起止时间、公开状态 | 运行号在计划内单调递增 |
| `path_runs` | 一条路径的运行：执行路径、目标主实例引用、公开状态、结果、失败分类、断言结论 | 一条路径运行独占一个真实主实例 |
| `run_steps` | 每个编译步骤的执行事实：序号、来源、动作、语义节点、演员、门禁快照摘要、起止时间 | append-only |
| `run_step_attempts` | 每次尝试：写结果三值判定、对账结论、恢复动作、是否重放、trace 与日志引用（含行号） | append-only；一次尝试最多一次写请求 |
| `run_events` | 运行事件流，带中文标签，供实时界面与事后回放 | append-only |
| `run_controls` | 人工控制事实：谁在何时暂停、放行、停止、增删断点 | append-only，可审计 |
| `run_assertions` | 成功断言判定：结束节点、期望状态、实际到达次数、判定依据 | append-only |

字段一律只存不透明键与业务摘要，不把目标临时标识暴露到公开 DTO。这一条与 `internal/engine/scenario` 已有的 `forbiddenParameterKey` 约束一致。

### 7.3 记录与日志的引用关系

每条尝试记录都带日志引用：相对日志路径、`trace_id`、`curl_trace_id`、行号。这四项让运行详情页的每一行都能一键落到具体日志行，这就是“可观测”标准里“三次点击”的实现方式。

反向也要成立：日志里的每一行都带 `run_id` 与 `step_id`，从日志能查回运行记录。双向可达是本节的验收点。

### 7.4 成功断言与路径结果

- 一条路径配置一个成功断言：一个结束节点加期望状态；节点在路径上重复出现时必须指定“第几次到达”。
- 判定只依据目标事实重读结果，不使用工具侧推断。
- 路径结果与断言结果分开呈现：步骤全部执行成功但断言不成立，是失败，且失败原因必须说明是断言不成立而不是执行出错。
- 失败分类至少区分：门禁不通过、演员不可解析、目标拒绝、写结果不确定、断言不成立、工具缺陷。分类直接对应第 6.4 节的 `error_class`，同一件事在界面和日志里叫同一个名字。

## 8. 目标平台规则与语义

### 8.1 为什么单独立项

目标平台的规则与语义分散在后端 Java 与前端 Vue 两侧，是本项目工作量最大、最容易返工的部分。产品原则已经写明“目标平台代码和真实运行结果决定流程、分支、人员与动作语义”，所以这部分不能作为各切片的附带产物，必须作为贯穿全程的独立工作流，有自己的清单、证据和测试。

产出物：新增 `docs/TARGET_SEMANTICS.md`，逐条记录语义、证据位置和对照测试。每个切片只允许推进与自己相关的条目，禁止为补语义扩张到无关文件。

### 8.2 语义清单

### 8.3 证据与对照测试

每条语义必须同时具备三样东西才算完成：

1. 证据：具体文件与方法或组件的位置，写进 `docs/TARGET_SEMANTICS.md`。
2. 对照测试：保存在根目录 `test/` 下按类别归档，用真实目标环境验证工具复刻的语义与目标一致。
3. 中文说明：解释规则本身和不能破坏的约束，而不是翻译代码。

参考仓库只通过 `make refs-sync` 同步；`rsh-cloud-invest-power-system` 侧只看 `GroupApproveManage` 及其直接引用的公共组件。

### 8.4 语义漂移检测

参考仓库同步后跑一个证据点存在性检查：断言清单中引用的类、方法与组件仍存在，且关键分支数量未变。发生变化时报到维护日志并要求人工复核对应语义条目。这样目标平台改动不会静默让工具的复刻语义失效。

## 10. 工程纪律

V1 的失败不是能力问题，是节奏问题：一个 10523 行的编排文件、一个 7277 行的工作台文件、12 天 2390 次提交、三次重写前端、没有人工检查点、两份互相竞争的权威文档。本项目已有的门禁必须继续硬执行。

- 单文件上限 800 行，执行器不允许出现单一编排文件。第 4.1 节的分包就是为此。
- 一次只实施一个已获批准的切片，到达 `ready_for_manual` 后停下，不自动开始下一项。
- 权威文档链唯一：`docs/PRODUCT.md`、`docs/ARCHITECTURE.md`、本纲领、`docs/features/`、`docs/TARGET_SEMANTICS.md`。不产生第二份行为定义。
- 不为旧接口、旧数据或旧流程保留兼容层、兜底、别名或迁移回退；需求变更直接删除旧代码与旧测试。
- 每个原子成果验证通过后提交一次，提交说明用中文。
- **F-012 的零写入断言不删除，改造为白名单断言。** 每个切片明确声明本切片允许调用的目标写端点清单，测试断言实际发出的写请求集合是该清单的子集。这样“写能力”的扩张过程本身是被测试守住的，而不是一次性放开。
- 测试按类别保存在根目录 `test/`，只跑当前功能相关测试。真实写测试必须在用户指定的可污染目标账号与流程上进行。

## 11. 已裁决事项
