## 二、Java 对照与证据

### 1. 目标自动跳过不产生可取回已办

目标 `FlowOperateServiceImpl.java:530-565` 的 `isSkip=true` 分支会递归查找后继节点。路径 1、6 的准备同意步骤读到实例待办已在后继节点，日志明确记录“模板声明允许跳过”，因此目标没有在该节点产生通过审核记录。

工具原先只对准备同意本身做了跳过落账，下一条取回仍按普通取回门禁查找该节点的审核记录，最终停在“审核记录里没有该节点的通过记录”。这是工具把“目标节点没有生成已办”误当成“取回动作可以继续尝试”的编排缺陷。

本轮修复在取回预览阶段读取前一步落账事实：仅当直接前置步骤是同一节点的 `RetrievePrepareConsent`、来源为恢复链、尝试结论为 `target_skipped` 且原因包含“目标自动跳过”时，取回才记录为零写入目标跳过。已有真实已办而跳过准备同意的路径仍走正常取回门禁，不会被误判。

### 2. 恢复触发动作被跳过时，动态加签步骤也不适用

路径 4 的驳回步骤被目标跳过后，工具已正确把恢复链步骤记录为 `recovery_not_applicable`。但控制层在加签写后动态插入的合成同意步骤仍使用 `system_default` 来源，没有携带原恢复锚点的 `SourceActionKey`，所以恢复跳过判定无法覆盖该步骤，最终在加签节点因没有处理人而阻塞。

目标 Java 的恢复入口 `FlowReSubmitServiceImpl.java:54-55` 只接受已驳回、撤回或草稿等合法状态；被目标自动跳过的驳回没有这些前置副作用，工具不应继续构造恢复写请求。修复后，动态插入步骤在锚点属于恢复链且带触发键时继承 `Source=system_recovery` 和相同 `SourceActionKey`，与普通恢复步骤使用同一 `recoveryTriggerWasSkipped` 判定；普通锚点仍保持 `system_default`。

### 3. 路径 9、10 的取回后事实与 Java 预期不一致

目标 `FlowInstanceServiceImpl.java` 的 `saveRetrieveProcess` 在 `723`、`881`、`884`、`889`、`905-910`、`964-979` 明确包含：创建新批次、调用 `createPendingJob`、写入取回审核记录，并在非并行场景把实例当前节点设置为取回节点；`createPendingJob`（`1769-1783`）将新任务写为 `pending` 并关联取回节点。

运行 172 的路径 9 `curl.log:87-90` 与路径 10 `curl.log.1:212-215` 均返回取回 `isSuccess=true`，后续日志也出现 `auditStatus:"retrieve"`。但重复读取的待办列表为空，当前节点响应没有稳定返回可执行的当前处理人。该结果与 Java 的 `createPendingJob` 和当前节点写入语义不一致，归属目标平台异步可见性/任务生成链路，工具侧不再添加计划账号、旧节点 ID 或空处理人兜底。由于本轮在有限轮询次数后停止，人工复验时需让一次完整重读窗口结束，以排除目标响应延迟。
