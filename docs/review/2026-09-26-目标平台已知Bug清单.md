## BUG-001：会签节点 approve 后不生成新待办（isCountersign && isEqExNode 分支提前返回）

**状态**：已确认，Java 团队已知悉，计划下周修复

**影响运行**：计划 59「欧阳改测试 09」运行 #4（run=173），路径 9（pr=475）、路径 10（pr=476）

**问题描述**

在流程会签节点，当 `isCountersign=true` 且 `isEqExNode=true` 时，`FlowInstanceServiceImpl.java` 里某个分支执行了 `return true`，没有生成新的待办任务，导致工具在下一步 approve 时轮询 20 次找不到处理人（`currentAuditUserInfo` 为空），最终按 `assignment_missing` 停止。

**触发条件**

- 节点类型为会签（`isCountersign=true`）
- 同时满足 `isEqExNode=true`（分支相等执行条件）
- approve 请求成功返回，但没有触发新待办生成

**证据**

1. 日志证据（`logs/runs/欧阳改测试 09__运行4/paths/路径 9__2026-09-26 15-16-59/step.log`）：
   ```
   step=20 action=approve 目标节点已到达但尚未生成处理人，正在第 1/20 次复查 ... 第 20/20 次
   ```

2. 数据库证据（目标平台 `t_flow_jobtask_link`，192 库）：
   - 路径 9 实例 `42f54dc4d4b440eda27b2e1911d4119b` 在节点 `6f91b42e47ac49a1bdf99a07d12af2e6` 上没有 `pending` 状态的待办记录
   - 同一流程在非会签场景下，approve 后立即生成新待办

3. Java 源码（`FlowInstanceServiceImpl.java` 约第 28-965 行）：
   ```java
   if (isCountersign && isEqExNode) {
       return true;  // ← 提前返回，未执行待办生成逻辑
   }
   ```

**复现步骤**

1. 创建一个包含会签节点的流程
2. 会签节点配置为 `isEqExNode=true`（分支相等执行）
3. 运行到会签节点，执行 approve
4. 检查 `t_flow_jobtask_link` 表，会发现没有新的 `pending` 记录

**期望行为**

## BUG-002：flowInstanceApi/list 在 extendedAttribute 类型审批节点不填充 currentAuditUserInfo

**状态**：待确认（有数据库证据，需目标平台开发确认是 Bug 还是设计）

**影响运行**：计划 60「欧阳海测试 10」运行 #1（run=175），路径 1（pr=491）、路径 2（pr=492）

**问题描述**

节点 `11c2ab83`（"发起人部门分管领导"）的审批人配置类型为 `extendedAttribute`（扩展属性），`type=scramble`（乱序）。当流程流转到该节点时：

- `t_flow_jobtask_link` 里确实有 `status=pending` 的待办记录（`task=9ea722ad`，`job_task_id=20c14138649f4a5aa66c8b17354c302f`）
- `t_flow_instance.current_node_proxy_id` 确实指向该节点
- 但 `flowInstanceApi/list` 返回的实例数据里，`currentAuditUserInfo` 为空，或不包含该节点的处理人信息
- `flowJobTaskLink/list` 返回的待办里 `currentPendingUserId=null`、`currentPendingUserName=null`

工具依赖 `currentAuditUserInfo` 里的 `bizIds`/`userIds` 来确定当前处理人，字段为空则无法切换到处理人会话执行 approve，轮询 20 次后按 `assignment_missing` 停止。

**触发条件**

- 节点审批人类型为 `extendedAttribute`（扩展属性型）
- `type=scramble`（乱序审批）
- `form_person_fields` 字段为空（未配置从表单字段取处理人）
- 流程流转到该节点后，`currentAuditUserInfo` 没有该节点的 `bizIds`/`userIds`

**数据库证据**

1. 目标平台 192 库 `t_flow_node_audit_config_proxy`（按 `node_template_id=11c2ab832dcd448896a0fc59e28545ed` 查询）：
   ```
   audit_type = extendedAttribute
   type       = scramble
   form_person_fields = （空）
   ```

2. 目标平台 192 库 `t_flow_jobtask_link`：
   ```
   flow_instance_id = 65bea52f974747c888fbf8bcc72bc5b0
   flow_node_proxy_id = 11c2ab832dcd448896a0fc59e28545ed
   task_status = pending
   job_task_id = 20c14138649f4a5aa66c8b17354c302f  ← MongoDB ObjectId，处理人在 MongoDB 里
   ```

3. 工具日志（`logs/runs/欧阳海测试 10__运行1/paths/路径 1__2026-09-26 18-34-44/step.log`）：
   ```
   目标节点已到达但尚未生成处理人，正在第 1/20 次复查 ... 第 20/20 次复查
   ```

4. `t_flow_job_task` 表在 192 MySQL 库里不存在 — 处理人信息存在 MongoDB 里（`job_task_id` 是 32 位十六进制 MongoDB ObjectId），而 `flowInstanceApi/list` 接口没有把 MongoDB 里的处理人回填到 `currentAuditUserInfo`。

**复现步骤**

1. 在流程模板里配置一个 `extendedAttribute + scramble` 类型的审批节点
2. 不配置 `form_person_fields`（使用扩展属性决定处理人）
3. 提交流程，流转到该节点
4. 调用 `flowInstanceApi/list?ids=[instanceId]`，观察返回里该节点的 `currentAuditUserInfo` 是否包含处理人信息
5. 同时查 `t_flow_jobtask_link`，确认 `pending` 待办存在

**期望行为**

`flowInstanceApi/list` 的 `currentAuditUserInfo` 字段应包含所有当前活动审批节点的处理人信息，包括 `extendedAttribute` 类型节点。处理人 ID（`bizIds` 或 `userIds`）应能被工具用来查找登录账号。

**实际行为**

`extendedAttribute + scramble` 类型节点的待办存在于 MongoDB（通过 `job_task_id` 关联），但 `flowInstanceApi/list` 不把这部分处理人信息回填到 `currentAuditUserInfo`，导致外部系统无法通过标准接口发现当前处理人。

**需要目标平台确认的问题**

1. `extendedAttribute` 类型节点的处理人是否本来就不通过 `currentAuditUserInfo` 暴露？如果是设计决定，请提供正确的查询方式。
2. `t_flow_job_task` 只在 MongoDB 里，没有 MySQL 映射，是否有 REST API 可以按 `job_task_id` 查询处理人信息？
3. `form_person_fields` 为空时，`extendedAttribute` 节点的处理人通过什么机制确定？

## BUG-003：getCurrentFromData 接口在节点切换后不返回人员选择组件伴生字段

**状态**：已确认为目标平台正常行为（非 Bug），工具侧已修复误判逻辑

**影响运行**：计划 60「欧阳海测试 10」运行 #1（run=175），路径 3（pr=493）、路径 4（pr=494）、路径 5（pr=495）

**问题描述**

`myCompanyName__condition`、`myDepName__condition`、`myUserName__condition`（以及同类 `__formPersonId`、`__virtualName` 后缀字段）是目标平台人员选择组件的联动字段。

- 第 1 步（submit，发起节点）：工具覆盖写入了这些字段，`storageFormData` 接口返回成功，写后核对通过
- 第 2 步（storage_form_data/approve/reject，下一节点）：工具调用 `/flowInstanceApi/getCurrentFromData` 读取当前表单，这些字段不在响应里

**数据库确认**

目标平台 `t_form_fields_proxy` 里这些字段的配置：
```
english_name = myCompanyName__condition / myDepName__condition / myUserName__condition
field_type   = stringType
value_origin = fromUser
```

**原因**

`/getCurrentFromData` 按当前节点的字段权限范围返回表单数据。下一个审批节点（"行政综合部-考勤管理"）没有这些人员选择组件，所以这些字段不在它的字段权限范围内，接口也就不返回它们。字段没有真正消失，只是当前节点不可见。

**工具侧已修复（commit a859413）**

在 `internal/adapter/target/field_ownership.go` 增加 `IsPersonPickerCompanionField` 函数，识别 `__condition`、`__formPersonId`、`__virtualName` 后缀字段为人员选择组件伴生字段，`formdata.go` 和 `executor.go` 的跨节点核对均跳过这类字段，不再误判为"字段丢失"并阻断运行。

**给目标平台开发的说明**

这条记录在此保留，作为字段行为的文档说明。如果目标平台希望在节点切换后也能通过 `getCurrentFromData` 读取上一节点写入的人员组件字段，需要在接口里去掉字段权限过滤，或提供一个"完整表单数据"的独立接口。目前工具侧已适配这个行为，不阻断运行。
