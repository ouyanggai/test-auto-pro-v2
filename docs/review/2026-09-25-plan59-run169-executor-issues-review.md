## 三、各异常路径的详细技术诊断

### 1. 目标平台明确 Bug：路径 9 与 路径 10
* **现象**：
  * 路径 9 在第 19 步成功取回（`王宇庆` 取回），第 20 步审批门禁轮询 60 秒后停止；
  * 路径 10 在第 18 步成功取回（`郝兴有` 取回），第 19 步审批门禁轮询 60 秒后停止。
* **日志证据**：
  > `放行条件不满足，已自动停止：目标节点已到达，但等了 60 秒 仍未生成处理人和待办（assignment_missing）；本步没有发送任何写请求，请到目标平台确认该节点的处理人配置`
* **根因确认**：
  目标平台在带有手动分支选择/自选配置的节点执行取回接口（`/web/flowInstanceApi/withdraw`）后，底层未重新触发流程流转监听器，没有为该回退节点生成 `currentAuditUserInfo` 与 `flowJobTaskLink` 待办任务。执行器依据 F-035/T07 规则进行了 60 秒非阻塞有界轮询，在确认目标确实未生成任务后按 `assignment_missing` 安全阻断，**执行器行为完全符合设计预期**。

---

### 2. 取回准备同意遇到空节点跳过：路径 1 与 路径 6
* **现象**：
  * 路径 1 第 7 步（节点 `38404fe86e5c4e5348a1e3e591051550`，审核人2）拦截：
    > `固定人员发现：实例 4fc0edfaa12a4e289402f1afe4e1bbfe 的 currentAuditUserInfo 里没有本节点的处理人信息`
    > `放行条件不满足：当前待办已经处理，不能重复执行`
  * 路径 6 第 6 步在相同节点报相同拦截。
* **根因链条**：
  1. 用户在「审核人2」节点上配置了 `action: retrieve`（取回）。
  2. 场景编译器（`internal/engine/scenario/scenario.go:291`）为了满足取回前必须有已办的先决条件，预置插入了准备同意步骤：
     `prep.RetrievePrepareConsent = true`。
  3. 但是该「审核人2」节点在模板中未分配人员且设置了 `isSkip=true`（目标空节点自动跳过）。上一节点同意后，目标平台瞬间穿透跳过了审核人2，实例已推进至审核人3。
  4. 遇到跳过的节点，执行器原本有 `targetSkippedStepReason` 可以判定为目标跳过；
  5. 然而 `internal/engine/step/executor.go` 中有如下逻辑：
     ```go
     // executor.go:800
     if isRecoveryEffectStep(step) {
         return nil, false // 恢复型动作不参与目标跳过判定
     }
     
     // executor.go:1361
     func isRecoveryEffectStep(step model.CompiledActionStep) bool {
         if step.RetrievePrepareConsent {
             return true // 准备同意被强制归为恢复型动作
         }
         ...
     }
     ```
  6. 因为被判定为恢复型动作，执行器**排除了目标跳过判定**，直接进入普通审批门禁。此时实例待办已在下游，本节点没有当前待办，门禁判定为「当前待办已经处理，不能重复执行」而阻断。

### 3. 驳回被目标跳过导致的级联恢复失效：路径 3 与 路径 4
* **现象**：
  * 路径 3 第 5 步（审核人2，`action: reject`）被目标自动跳过；第 6 步（`action: resubmit`）阻断：
    > `放行条件不满足：当前实例状态不允许重新提交`
  * 路径 4 第 17 步（审核人7，`action: reject`）被目标自动跳过；第 18 步（`action: resubmit`）报同样阻断。
* **根因链条**：
  1. 路径 3 与 4 配置了对某个节点的 `reject`（驳回）动作。
  2. 场景编译器在静态编译时，为每次 `reject` 预编排了后续的恢复链：`resubmit`（重新提交）。
  3. 运行时，由于配置了驳回的节点在模板中无人且允许跳过，目标平台直接跳过了该节点（执行器第 5/17 步如实判定 `TargetSkipped: true`）。
  4. **关键矛盾**：因为驳回动作被跳过，**实例从未真正被驳回**，主实例依然保持 `status="run"` 正常向前流转，并未变成 `withdraw`/`rejected`。
  5. 执行器接着执行下一步静态恢复动作 `resubmit` 时，重提门禁检查 `instanceCurrent.Status` 必须是草稿或已撤回/已驳回状态，面对运行中的实例坚决拒绝重新提交并停止。

### 4. 历史快照残留流程元数据键污染：路径 11
* **现象**：
  * 路径 11 第 2 步 `action: forward`（转发）调用成功后，写后核验报告：
    > `表单数据写后核对不一致：字段 flowInstanceId 发送后未出现在目标实例数据中`
  * 第 3 步被上一步核验失败门禁拦截停止。
* **根因链条**：
  1. 路径 11 的表单配置来自真实历史实例的深拷贝快照（F-012/F-043），该快照的原始表单 JSON 中携带有上游接口返回的流程元数据键 `"flowInstanceId": "e4652589afa948ab8e1469ea6c2b1944"`。
  2. 在新实例运行至第 2 步 `forward` 时，`BuildNodeFormData`（`internal/engine/step/formdata.go:169`）以新实例的真实表单为基线。目标真实表单字段并不包含 `flowInstanceId` 这个隐藏元数据键。
  3. `formdata.go` 发现配置中存在、但基线中没有该字段，且该字段未被其他节点独占，误将其作为业务字段加入 `OverlaidFields`（覆盖写入清单）。
  4. 随后在 `verifyFormDataAfterWrite`（`internal/engine/step/executor.go:1270`）中，写后核验逐字段检查所有 `OverlaidFields` 是否在目标持久化数据中存在。由于目标存储表单文档时根本不保存 `flowInstanceId`，核验比对缺失，判定为字段丢失而报错。

### 5. 多人/会签节点写后核验因快照异步滞后误判「未变」：路径 8
* **现象**：
  * 路径 8 第 39 步（审核人10，`approve`，第一处理人侯宏伟同意成功），在第二处理人高琛杰调用 `/flowInstanceApi/audit` 接口返回 200 成功后，核验报告：
    > `核验事实：实例可读=true 状态=run 当前处理人待办=true 当前处理人已办=已按执行人核对但无该已办 实例当前节点=[62bf..._be04...]`
    > `执行结果：目标接口已返回成功，但执行结果暂时无法确认`（判定为 `uncertain`，路径进入待对账停机）。
* **根因链条**：
  1. 高琛杰提交同意后，目标后端将高琛杰的已办记录中 `flowNodeProxyId` 改写为了后续节点 `be049ad45946473c91de119facdc86cb`（审核人11），导致按当前节点等值比对已办时未命中（`CompletedTaskBasisCheckedAbsent`）。
  2. 昨天提交 `fae2a4f` 曾针对末签改写修复了 `advancedByNodePosition`（用后续合法节点集合识别推进）；
  3. 但 `advancedByNodePosition` 包含一道前置检查：
     ```go
     // verify.go:975
     for _, node := range after.CurrentNodes {
         if strings.TrimSpace(node) == current {
             return false // 只要当前节点还在当前节点列表中，即判未推进
         }
     }
     ```
  4. 在会签或并行分支上，该节点可能仍有其他候选人待办未结，或者目标后端状态更新存在毫秒级时序窗口，导致重读到的 `CurrentNodes` 同时包含了当前节点和后续节点（`[62bf..._be04...]`）。
  5. 检查项因发现 `current` 仍存在而直接返回 `false`；同时待办列表尚未刷新（`CurrentTaskFound=true`）。
  6. 综合得出「重读明确未变（Unchanged）」，与「HTTP 成功响应」构成事实冲突，按安全对账矩阵判定为 `uncertain`，停机进入待对账。

## 四、排查总结与改进建议

| 问题分类 | 涉及路径 | 缺陷性质 | 建议改进方向 |
|---|---|---|---|
| **目标平台 Bug** | 路径 9、10 | 目标平台后端取回不重新发牌 | 保持现有 `assignment_missing` 阻断事实，由业务侧或目标流程修复。 |
| **取回前置步骤遇跳过** | 路径 1、6 | 执行器门禁跳过白名单盲区 | 在 `targetSkipPreview` 中解除对 `RetrievePrepareConsent` 的盲目排除，若目标节点已证明跳过，准备同意应随之一同跳过。 |
| **驳回跳过后的级联失效** | 路径 3、4 | 静态场景恢复链动态感知缺失 | 执行器在执行恢复型动作（如 `resubmit`）前，检测其关联的前置破坏性动作是否为 `TargetSkipped`；若前置未实际生效，则恢复步骤应自动静默跳过。 |
| **表单元数据污染核验** | 路径 11 | 历史数据清洗与核验黑名单缺失 | 在表单回放配置与写后核验中，将 `flowInstanceId` 等流程级系统字段加入系统元数据排除清单，不作为业务表单字段提交或比对。 |
| **会签并发多节点核验** | 路径 8 | 节点推进判定未考虑并行/多节点共存 | 优化 `advancedByNodePosition`：当新节点已在后续合法节点集合中出现时，结合已办记录中新节点的存在事实，准确识别会签推进，避免被并发节点阻塞。 |
