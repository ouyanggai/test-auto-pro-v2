因此，目标取回成功的可验证结果是：

```text
实例状态仍为 run
currentNodeProxyId 回到取回任务对应的运行时节点
currentAuditUserInfo 出现该节点的处理人
flowJobTaskLink/list 出现新的 pending jobTaskId
```

### 2. 无处理人且声明可跳过时，目标递归跳过节点

文件：`FlowOperateServiceImpl.java`

- `recursionGetNextNodeProxyData`（530-565 行）和 `recursionGetNextNodeProxy`（691-727 行）取得下一个节点后，调用 `validateNodeAndSettingsNodeAuditDetailConfig`。
- 结果没有处理人时：`nodeSkip=false` 返回该节点等待/报错；`nodeSkip=true` 递归继续取下一个节点。
- 这说明目标把 `isSkip=true` 的无人节点作为正常路径跳过，不会为该节点生成可审批处理人。

### 3. 重新提交不接受 `run` 状态

文件：`FlowReSubmitServiceImpl.java`，45-55 行：

```java

    return error("当前实例状态不正确,无法重新发起");
```

### 4. 同意后的下一节点和 pending 由目标运行时事实决定

文件：`FlowAuditServiceImpl.java`

- `passLogic` 390-406 行调用 `recursionGetNextNodeProxyData` 和 `getNextFlowNodeProxy` 计算真实后继。

## 四、逐路径证据与归因

### T-A：取回准备同意错误排除目标跳过判定（路径 1、6）

#### 运行证据

- 路径 1：第 5 步同意写成功，写后实例当前节点为 `7ef9a1511fb540f8b44d12a9bffd5b07`；第 7 步准备同意仍使用静态节点 `38404fe86e5c4e5348a1e3e591051550`，日志为 `currentAuditUserInfo 里没有本节点的处理人信息`，随后显示“当前待办已经处理”。
- 路径 6：第 4 步加签后的同意写成功，写后实例当前节点为 `89bc228c9eda40649e8d8f8fde682aa1`；第 6 步仍以静态节点 `38404fe86e5c4e5348a1e3e591051550` 做准备同意门禁，得到同样的阻断。
- 两条路径的静态节点都是模板中的无人 `isSkip=true` 节点；目标已经沿后继节点继续运行，没有待办是目标跳过的结果，不是目标数据丢失。

#### 工具代码根因

`internal/engine/step/executor.go:827-838` 的 `targetSkipPreview` 在调用 `targetSkippedStepReason` 前先执行 `isRecoveryEffectStep`。`isRecoveryEffectStep`（1396-1414 行）把 `RetrievePrepareConsent` 直接归为恢复型动作，因此准备同意永远不进入目标跳过判定。

随后工具按普通固定人员门禁调用 `currentHandlerForNode`，而静态节点不在 `currentAuditUserInfo` 中，错误地把“目标已跳过”解释为“当前待办已处理”。这与 Java 递归跳过规则不一致。

#### 修复计划 T-A

1. 将“取回动作本身的恢复语义”和“取回前置准备同意是否随无人节点跳过”拆开。`RetrievePrepareConsent` 不能再无条件复用 `isRecoveryEffectStep` 的跳过排除。
2. 准备同意在写前按以下顺序裁决：
   - 当前事实显示实例待办已经越过本节点，且目标节点 `isSkip=true`：记录 `target_skipped`，不发同意写请求，继续到取回步骤。
   - 当前节点仍在本节点且有真实 pending：按正常同意门禁执行一次写请求。
   - 节点已越过但未证明 `isSkip=true` 或属于 `run_node_choose`：阻断并说明目标配置冲突。
3. 保留“本节点已有已办时准备同意可跳过”的现有正面审核记录校验；该校验与“目标自动跳过”是两条不同证据，不能互相替代。
4. 在步骤事实中区分 `target_skipped` 和 `already_done`，避免详情页再次显示“当前待办已经处理”这一错误文案。
5. 回归场景：路径 1、6 的同意/加签后无人 `isSkip=true` 节点必须零写入跳过，随后取回步骤仍能按真实已办执行。

### T-B：驳回被跳过后仍执行无条件恢复重提（路径 3、4）

#### 运行证据

- 路径 3 第 5 步计划为节点 `38404fe86e5c4e5348a1e3e591051550` 的 `reject`。日志明确记录“目标自动跳过，实例待办在审核人 3，节点动作不执行”，没有 `/flowInstanceApi/audit` 驳回写请求；下一步第 6 步仍编译为 recovery `resubmit`，门禁以实例 `run` 状态拒绝。
- 路径 4 第 17 步节点 `ef32971e89f9a37a608e3c6999987d83` 的 `reject` 同样被目标按 `isSkip=true` 跳过；第 18 步 recovery `resubmit` 同样面对 `run` 状态停止。

#### 工具代码根因

- `internal/engine/scenario/scenario.go:308-317` 对 `reject`/`withdraw` 直接设置恢复状态并调用 `emitRecoveryFromStart`。
- `emitRecoveryFromStart`（335-358 行）无条件把 `resubmit` 和后续恢复同意步骤加入 `Steps`，只保存触发动作键，没有运行时“触发动作是否实际生效”的依赖。
- 控制层在跳过步骤成功落账后继续推进 `nextIndex`，于是把没有前置副作用的恢复链当成普通下一步执行。
- `evaluateResubmit` 和目标 Java 都正确拒绝 `run` 状态；这一步本身不应修改。

#### 修复计划 T-B

1. 为恢复步骤补充不可变的触发依赖标识，例如 `RecoveryTriggerStepNo/RecoveryTriggerActionKey`，并在运行时保存触发动作的结论：`executed`、`target_skipped`、`business_rejected`、`failed`。
2. 当 `reject`/`withdraw`/`rollback` 被目标跳过、确定失败或零写入时，将其依赖恢复步骤标为 `not_applicable`，不调用 `resubmit`，不发送任何恢复写请求。
3. 只有触发动作已发出且写后事实证明实例进入 `rejected`/`withdraw` 等恢复状态时，才放行对应 recovery group；重提仍使用实时实例状态门禁。
4. “跳过”不能伪造为 `rejected` 或 `withdraw`，也不能把实例状态强行改成编译器状态；详情应显示“触发动作被目标跳过，恢复链未适用”。
5. 回归场景：路径 3、4 在目标 `isSkip=true` 节点上不得出现 `/flowInstanceApi/reSubmit` 请求，路径应继续到后续独立动作或按配置停止，并保留触发动作的跳过事实。

### T-C：取回后没有把目标运行时节点重绑定到后续步骤（路径 9、10）

#### 运行证据

路径 9：

- 第 19 步取回写请求 `trace_id=29747fa8ed03e1ff` 返回成功。
- 写后 `/flowInstanceApi/list` 返回 `currentNodeProxyId=8a6c55a707034e8d9012e78b122b3364`、`currentAuditUserInfo` 含该节点的两名处理人；同一批事实的 `/flowJobTaskLink/list` 可见新的 pending 任务，节点也是 `8a6c55a7…`。
- 第 20 步系统同意仍打印计划节点 `f5e7e958d111335f0dd5c5289722dff3`，随后 1/20 至 16/20 只读复查，最终因静态节点没有对应处理人而停下。

路径 10：

- 第 18 步取回写请求 `trace_id=cdbdcf6fb04cec73` 返回成功。
- 写后目标返回 `currentNodeProxyId=c82e8cb224d943e58b4a108a0f4844f3`，`currentAuditUserInfo` 含该节点处理人，pending 任务的 `flowNodeProxyId` 也是 `c82e8cb2…`。
- 第 19 步系统同意仍打印计划节点 `1e7a26433b4d53c9e18cbb95edb7b47f`，随后只读复查并停下。

这两条路径已经有目标处理人和 pending；因此“目标取回后没有产生处理人”的旧结论不成立。

#### 工具代码根因

1. `internal/engine/step/executor.go:1215-1218` 的 `stepTargetNodeIDOf` 从 `runCtx.Nodes[step.NodeKey].TargetNodeID` 取静态 ID。
2. `readInstanceFacts` 和 `readActionTaskFacts` 以该静态 ID 作为 `StepNodeKey` 和 `currentHandlerForNode` 的匹配键；`currentHandlerForNode`（3817-3824 行）不会用目标返回的当前节点进行语义重绑定。
3. `RunApprovedStep` 目前只有加签分支明确回填 `outcome.CurrentNodeProxyID`（约 1931 行）；取回后的新当前节点没有进入控制层代理重绑定条件。控制层 `control.go:1305-1342` 因此没有为取回后的新批次刷新运行时代理映射。
4. 结果是目标 Java 已经按新 pending 的运行时 `flowNodeProxyId` 切回节点，工具下一步仍用旧代理/静态节点查询，错误地进入“等待处理人生成”循环。

#### 修复计划 T-C

1. 取回写后核验必须把 `after.FlowProxyID`、`after.CurrentNodes`、`after.CurrentTaskNodeID` 和新 pending 的 `flowNodeProxyId` 作为运行时事实输出；在唯一节点场景下回填 `outcome.CurrentNodeProxyID`，并在并行场景保存完整节点集合。
2. 取回成功后调用与加签同一套 `RemapProxyTreeForRun`/`ApplyProxyRemap` 代理树重绑定流程，使用新批次的实时代理树，不把编译期节点 ID 直接传给下一步。
3. 维护“语义 NodeKey → 当前运行时 NodeProxyID”的映射；后续 `currentHandlerForNode`、任务列表查询、审批写请求和写后核验均从该映射取 ID。映射不唯一时必须阻断并说明“无法唯一绑定”，不能退回旧 ID。
4. `classifyRetrieveReread` 同时对照旧 `jobTaskId` 与新 pending 的 `jobTaskId`；新 pending 节点可以与静态节点不同，但必须和写后目标当前节点及取回任务链一致。
5. 写入运行日志：取回前静态节点、目标返回节点、新 `jobTaskId`、重绑定结果和下一步实际使用的节点 ID，便于证明是目标已生成任务还是工具未映射。
6. 回归场景：路径 9、10 的取回后下一步必须查询 `8a6c55a7…`/`c82e8cb2…` 这类目标运行时节点，能够发现处理人并进入正常审批；禁止再出现 20 次无写轮询。
