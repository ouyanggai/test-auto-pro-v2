#### 组合 A / B（手动控制）怎么做

- 启动后运行会停在第一步等放行。**每一步都要在页面上真实点「执行这一步」或「继续执行后续步骤」。**
- 每步之间**看一眼画布**：当前节点高亮对不对、步骤时间线有没有多出来/漏掉的步骤、节点弹窗文案是不是大白话（不许出现"演员""核验""落账""门禁"这类词）。
- 遇到安全停机（路径偏离保护、写后核对拦截）：**截图 + 记 step.log 行号 + 判断是工具错还是门禁对**，然后：
  - 是工具错 → 修 → 重跑该路径
  - 是门禁对 → 记入报告，该路径标记「按设计安全停」，继续下一条路径，不要卡死在这一条
- 手动组合跑不完 12 条是正常的（时间不够）。**跑到 08:00 前必须停**，把已跑完的条数如实记录，剩余标记「未执行（时间不足）」。

#### 组合 C / D（自动运行）怎么做

- 启动后不干预，让它自己跑。
- **但要盯着**：每隔几分钟截图一次，记录运行号、已完成路径数、当前卡在哪条路径。
- 自动组合卡住超过 10 分钟无进展 → 判定卡死，截图 + 抓 `logs/runs/<本次运行>/paths/<路径>/` 下的 `step.log`、`control.log`、`network.log` 尾部 → 记问题 → 停掉该运行 → 修 → 重跑。
- 死循环、反复重试同一动作、租约不释放，都属于**必须修**的问题。

#### 每一轮运行都要记录的事实

- 运行号、路径清单、实际用了几条路径
- 每条路径的最终结果（成功 / 安全停 / 确定失败 / 结果待确认 / 未执行）
- 每条路径的步骤数、耗时

- 页面异常：控制台报错、请求失败、弹窗按钮不见了、白屏、状态不一致

## 六、遇到问题怎么办（这是本次任务的核心动作）

### 判断与处置流程

```
发现问题
  ├─ 能复现吗？不能 → 记录，标注「偶发，未能复现」，继续
  ├─ 是工具的问题吗？
  │    ├─ 否（目标平台行为 / 环境问题 / 设计上的安全门禁）
  │    │     → 记录事实 + 证据，不改代码，继续下一项
  │    └─ 是
  │         ├─ 能修 → 改代码 → go build ./... + 相关测试 → 页面重跑验证 → 中文原子提交 → 记录
  │         └─ 修不了 / 修了风险大
  │               → 记录：现象、根因判断、为什么没修、建议方案，继续下一项
  └─ 全程不要问用户
```

### 修代码时的纪律

- 改动**最小**：只修当前这个问题，不顺手重构、不顺手加功能。
- 修完必须**页面重跑验证**，不许只跑单测就说修好了。
- 新增/修改的 Go 具名函数必须写中文注释（职责、输入边界、关键约束）。
- 提交前跑：`go build ./...`、`go vet ./...`、`pnpm --dir web run typecheck`、`git diff --check`，以及当前改动相关的测试。
- 提交信息中文，格式类似：`修复加签后编译场景不含插入节点导致路径偏离安全停`。
- **不推送、不合并、不切分支、不删别人的提交。**

### 问题记录格式（每个问题都要按这个填）

| 字段 | 说明 |

## 九、什么情况下可以提前收工

只有这两种：

1. **危险级问题无法修复**：例如出现重复写、数据被破坏、门禁失效，且你判断继续跑会造成目标平台数据混乱。→ 立刻停止所有运行，把现象和证据写清楚，报告置顶，然后可以继续做**只读的代码排查和记录**，但不再发起真实写运行。
2. **环境彻底不可用**：后端/目标平台/执行服务任一挂掉且 30 分钟内无法恢复。→ 写清现象和排查过程，收工。

**除此之外，一律继续测到 08:00。**
