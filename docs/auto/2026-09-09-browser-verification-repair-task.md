## 3. 执行方式和证据规则

### 3.1 建立现场

开始时运行以下只读检查，记录当前提交、未提交文件和实际可用命令：

~~~bash
git status --short
git log -5 --oneline
git diff --stat
~~~

读取根目录及 web、form-runtime 的 package.json、README.md。当前开发入口如下，启动前先确认相应端口是否已有本项目服务，优先复用，不重复起服务，也不终止其他任务的进程：

~~~bash
pnpm dev:f
pnpm dev:form
pnpm dev:b
~~~

三条命令分别放在独立前台终端。主页面为 http://127.0.0.1:19000，表单运行时为 19001，后端为 19080。后端健康入口是 http://127.0.0.1:19080/api/health。

本机已有被忽略的环境配置时沿用；不要把配置值打印到任务报告。不能通过“重配基础设施”绕开业务缺陷。表单源码修改后，确认浏览器实际消费的服务或构建产物就是当前代码。

创建持续更新的执行报告：docs/auto/2026-09-09-browser-verification-repair-report.md。报告记结论和脱敏证据索引。测试用例、复现脚本按类别放在根目录 test/；浏览器用例可新增 test/e2e/，人工步骤可放 test/manual/。原始日志、网络记录、截图等敏感或运行产物放入被忽略的 .runtime/ 或 logs/，不得提交凭证、SID、完整业务数据。

### 3.2 浏览器必须怎样用

通过可用的浏览器控制能力打开真实应用，按页面上的按钮、输入框、候选和导航完成操作。可以使用 DevTools/浏览器工具读取 DOM、网络和控制台帮助诊断。

创建计划、选择路径、配置动作和人员、选择历史数据、保存、启动、切换模式、暂停与停止，必须至少有一次从网页正常入口完成。不得通过直接改数据库、注入前端状态或手工调用内部 API 代替这些用户流程。

接口读取和日志核对用于补足证据；单元/集成模拟只用于稳定覆盖错误、超时和竞态，不得冒充真实目标验证。目标写操作由本工具真实执行器发出；不要用手工 API 写入绕过执行器之后宣称它可用。

### 3.3 每个问题使用同一修复循环

1. 在网页复现，记录入口、点击顺序、期望与实际结果。
2. 保存当前计划/路径/运行定位信息和相关时间；截图、控制台、网络、日志至少选择能证明问题的证据。
3. 沿“页面输入 → 保存请求 → 服务端重读 → 编译 → 执行 → 目标结果 → 页面”查出断点。没有证据时写“待验证假设”。
4. 写出这个问题的完成标准，再做最小修改。
5. 给状态、数据、人员或重复写类缺陷补有意义的回归测试。单纯样式修改按实际浏览器检查，不机械补字符串测试。
6. 运行相关检查，重新在网页走原来失败的流程，再检查同范围相似场景。
7. 确认效果后做一次中文原子提交，更新报告，继续下一个明确问题。

第二次失败必须换验证方法，例如从 UI 转到消息时序或目标源码核对，不只是加长等待。第三次失败先列出 3 个不同根因假设并分别验证。结束为阻塞前必须查完整错误原文、读直接相关源码/文档、尝试一种根本不同的方法；错误中有敏感内容时只在本地搜索，不上传外网。

| H09 | 人工控制、执行到下一节点、断点命中与继续 |

## 5. 工作包 A：先恢复表单可以打开

依赖：现场建立、用户失败路径已找到。关联 F-024 和已有表单加载修复。

### 5.1 浏览器复现顺序

1. 从测试计划打开问题路径，点击“表单数据”。
2. 记录遮罩出现时间、显示文案、工具栏能否点击、iframe 是否已请求并挂载、控制台错误和未结束请求。
3. 等到当前实现声明的总超时，观察遮罩是否关闭、错误是否可见、按钮能否恢复；不要无上限等待。
4. 在加载中返回节点配置，再打开；切换到另一条路径再返回。
5. 切换历史数据、节点视图，执行保存和恢复已保存数据；核对是否重现卡住或被旧数据覆盖。

### 5.2 查完整状态链，不只查某个 loading 变量

逐段确认谁开始、谁结束、谁取消：

~~~text
打开表单工作区
  → 读取路径数据和运行时会话
  → 挂载 iframe
  → iframe 文档 load / runtime boot
  → 父页面发送 load 命令
  → 模板与历史数据装载
  → 目标组件初始化、远程选项、宿主二次 editData / refresh
  → 关键字段最终协调
  → 运行时 result / ready 或 error
  → 父页面关闭遮罩，允许保存
~~~

优先检查这些具体风险，结论必须用时序或代码证明：

- loading 为 true 时通过 v-if/v-else-if 把 iframe 排除，导致等不到 ready 的相互等待。
- 数据接口结束就清掉父页面计时器，但 iframe boot/load 后续阶段没有完整退出路径。
- iframe 文档 load、runtime boot、重复加载的先后顺序改变，旧重置把新会话清理掉。
- 取消只拒绝宿主 Promise，运行时的请求和联动仍继续，迟到事件重新打开遮罩或覆盖新值。
- 会话标识与操作代次判断过严而丢弃当前合法 load，或过松而接收旧 state/result。
- pending Promise、定时器、事件监听、XHR/fetch 计数没有在成功、错误、超时、abort、同步异常、销毁时恰好清理一次。
- 为等远程选项不断 refresh，刷新本身又发新请求，导致“等所有请求结束”永远达不到。
- 读取实时模型失败后吞异常、退回旧快照，被误报为“数据一致”；必须区分仍在初始化与真实错误。

不能只把遮罩隐藏就算修好。必须让表单可见、值正确、能够保存；失败时不能显示 ready，也不能允许提交未经准备的数据。

### 5.3 通过条件

- 页面进入可用或明确失败的时间有整体上限；重试共享总预算，不能每层重试重新获得一整段预算。
- 成功、HTTP/业务错误、网络断开、请求超时、取消、离开页面、iframe 重载都关闭本轮等待。
- 旧请求既不能改新路径的数据，也不能结束或重新开启新路径的加载状态。
- 遮罩仅覆盖表单内容，顶部返回/切换操作仍可用；浅深主题正常。
- 错误说清阶段和下一步，例如“合同分类选项读取超时，尚未完成分类修正”，提供对应重试入口；具体请求路径放可展开的诊断信息，不要求普通用户理解 iframe/SID。
- 原失败路径和另两类表单均重新打开、保存、刷新成功。

## 6. 工作包 B：彻底解决关键字段显示与真实值不一致

依赖：A 可用。不能只针对“合同分类”名称写特殊代码。

### 6.1 对每个问题字段核对六处事实

| 位置 | 要核对的内容 |
| --- | --- |
| 历史快照 | 原始绑定值、原始显示名称、相关父级选项 |
| 路径补丁与右侧说明 | 为什么需要改，目标值是什么，应在哪个节点填写 |

### 6.2 修复边界

1. 先确认字段对应的真实 JSON 路径、绑定值类型和目标组件协议，不按中文标签、名称相似度或页面位置猜字段。
2. 用目标真实选项关系同步绑定值与显示值；目标只给出名称且无法唯一匹配时明确阻塞，不能随便选第一个。
3. 选项异步到达、父子级联、宿主二次初始化、onChange 派生字段都结束并稳定后，再确认最终补丁结果。
4. 必要联动执行目标组件原有逻辑；不能只改 label 或虚拟名称，让底层 ID 仍是旧值。
5. 只改当前路径需要的关键字段和其真实关联字段，保留其他历史数据、嵌套对象、子表、附件引用及数字精度。
6. 缺失选项、同名多值、历史选项失效、类型不同或数据源失败，要准确指向字段和原因，不能用旧值假装匹配成功。
7. 用户主动修改关键字段时，重新计算实际路径；确实换路则保留现有确认和受影响配置提示，不能把用户值强制改回旧补丁。
8. 节点视图切换遵守 F-024：后续节点才能填写的字段在发起视图不回显样本值，不等于把服务端基线保存为空。执行时按当前实例数据叠加本节点允许修改的配置值。
9. 最终修正不能造成持续自触发；同一输入反复打开/刷新应稳定，不重复改值、重新随机或无限请求。

### 6.3 必查场景

- 合同 10 条路径：逐条打开表单核对关键信息、保存、关闭重开、浏览器刷新，再核对。
- 普通下拉、远程下拉、级联、嵌套/子表选项、多选：实际表单存在的类型均检查；不存在的类型用可重复测试覆盖并注明非真实样本。
- 远程选项先到/后到、父级先变、迟到响应、切换来源、切换路径、切换视图、恢复历史快照。
- 空值、选项不存在、同名不同 ID、数字与字符串绑定、大整数：以目标真实类型约定处理，不能统一转数字或字符串。
- oyg 与请假单的相关字段采用同一修复路径；没有同类字段时如实注明，并选本轮指定流程中另一条真实表单覆盖。
- 至少一条带分支补丁的路径完成目标写入，证明“看起来一致”也能正确命中分支。

## 7. 工作包 C：动作配置必须形成可执行的流转

依赖：A、B 达到可保存状态。先核对目标语义，再修一键配置、手动校验、编译与执行的衔接。

### 7.1 基本业务规则

| 动作/阶段 | 成功后代表什么 | 后面仍要走节点时必须怎样处理 |
| --- | --- | --- |
| 新发起保存草稿 | 形成或保存待发数据，没有自动进入审批 | 对同一主实例执行目标允许的提交，再读取真实待办 |
| 提交 | 发起流程并由目标决定真实分支和待办 | 使用实际下一节点处理人执行后续动作 |
| 撤回/用户所说“撤销” | 按目标规则回到待发等可重提状态 | 切回有权发起的人，对同一实例重新提交；名称与端点按目标核实 |
| 审批暂存 | 只保存当前处理人的表单检查点，当前任务未完成 | 仍需同意等目标允许的离开动作 |
| 同意 | 完成当前待办的一次审批 | 会签未达到条件时仍可能留在本节点，不能直接跳到下一节点 |
| 退回上一节点 | 回到目标允许的真实上游人工节点 | 重读代理/待办和处理人；上游是发起人时提交/重提，上游是审批时同意，再继续 |
| 不同意/驳回 | 按目标定义形成拒绝或驳回结果 | 是否能重提必须按目标事实，不与“退回上一节点”混同 |
| 移交、加签、取回 | 改变处理人、代理树或任务可操作状态 | 重读任务、批次、节点和人员，不能沿用旧 task 或旧执行账号 |
| 催办、转发、关注等 | 不代表主实例到达下一节点 | 仍按主实例实际待办继续；转发辅助实例单独记录 |
| 条件、并行、空节点、结束等自动节点 | 目标引擎处理或可验证的目标事实 | 工具只读核验，不用“导航成功”虚构跳过人工节点 |

“提交”和“重新提交”具体采用哪个目标端点，必须依据实例当前状态与目标前后端源码；用户说“再提交”不意味着所有情况都发同一个接口。

### 7.2 一键配置要求

- 对所选完整路径生成可完成的动作序列。发起节点需要离开时有提交；审批节点需要离开时有同意或目标认可的流转动作。
- 保留已有原子动作覆盖能力，但“随机选择了一个可用动作”不能作为节点配置完成的充分条件。
- 保存草稿、暂存、撤回、回退等动作保留时，补出必要的前置/恢复/继续步骤；在场景预览中明确展示新增步骤、人员和原因。
- 不能为了更容易跑通而把所有动作都删成“提交 + 同意”，也不能无依据添加会产生通知或辅助实例的动作。
- 已人工确认的动作顺序和人员不被一键配置悄悄覆盖；重复一键配置幂等，不增加重复提交或恢复步骤。
- 只处理用户勾选的路径，逐条显示完成和未完成原因。不能最终都标“已配置”却在首个人工节点必然停住。

### 7.3 手动配置和预检要求

用户可保存待完善的草稿配置，但不能把无法推进的配置显示成可执行。现有保存流程要求完整时，可阻止保存并定位；无论哪种，状态与运行前检查必须一致。

最少支持以下提示及定位，文案中的节点名替换成实际名称：

| 问题 | 可用提示 | 点击后 |
| --- | --- | --- |
| 发起人只有保存草稿 | “发起人只配置了保存草稿，流程会留在待发。要执行后续节点，还需要提交。” | 打开发起人动作区，定位缺少的流转步骤；可提供明确补全操作 |
| 审批只有暂存 | “合同管理部暂存后仍未完成审批，需要补充同意才能进入后续节点。” | 定位该节点动作区 |
| 撤回后直接执行下游审批 | “撤回后流程已回到待发，需要先由发起人重新提交。” | 定位撤回后的动作位置与补全预览 |
| 回退后仍用当前节点人员 | “退回后应由上一节点的处理人继续，当前步骤人员与实际待办不一致。” | 定位恢复步骤及相应人员区 |

动作删除、排序、重复记录、当前节点保存、批量保存均需回读验证。尤其核对保存一个节点时是否丢弃实例动作，删除后是否又被旧草稿恢复。

### 7.4 编译和执行必须一起检查

重点读取 scenario.go 的 Compile、recoveryStep、finalNavigationStep，与 executor.go 的导航分支。

- 当前静态代码中草稿/撤回后补重提依赖“还有下一个用户动作”。检查最后一个用户动作但线路仍未走完时是否遗漏必要提交。
- 恢复步骤不能机械复制原动作的节点和人员。退回到上一节点后，必须使用上游真实待办；退到发起人不能用审批同意代替提交。
- 系统导航不能仅以“能读到实例”就判已到结束。必须核对预期节点/状态，人工待办必须有真实流转动作。
- 会签、并行活动节点、重复访问同一节点时，每个任务/批次按实时事实执行；不能仅靠数组下标或“上一个节点名”推进。
- 每条路径从发起到恢复结束始终使用同一主实例。新发起路径之间各自独立，历史快照 ID 不得当作运行实例 ID。
- 配置、预检、执行均使用同一语义依据，避免前端提醒可执行而后端编译或执行采用另一套规则。

通过条件：第 4.3 节中草稿、撤回、暂存、回退和手动遗漏均实际跑过，目标待发/待办/已办证明状态正确；完整路径不依赖人工到目标平台补点遗漏的提交或同意。

## 8. 工作包 D：人员配置真正驱动执行，会话正确复用

依赖：C 的动作预期明确。人员模块已有 F-025，不另建一套。

### 8.1 先分清四个身份

| 身份 | 用途 | 来源 |
| --- | --- | --- |
| 计划发起人 | 发起、保存草稿、依法重新提交等发起行为 | 本次固定骆蒙恩 |
| 当前任务处理人 | 同意、暂存、回退、移交等当前待办行为 | 节点人员配置、目标规则与实时待办 |
| 下一节点选人参数 | 让目标在当前提交/同意时生成正确下一节点待办 | 当前路径的下一节点策略及目标接口规则 |
| 动作接收人/表单人员 | 加签、移交、转发接收人，或表单人员字段 | 对应独立配置域，不覆盖节点主处理人 |

不能把 NextNodeAuditors 已传入当作处理人切换已经完成。必须证明当前请求的会话属于当前动作有权执行的人。

### 8.2 逐段追踪

~~~text
节点人员候选与策略
  → 保存 person_strategies
  → 运行前按当前目标范围复验
  → 当前动作需要的实际处理人 / 下一节点选人
  → 解析真实账号
  → 按该账号获取或复用会话
  → 用该会话读取实时任务与权限
  → 发出当前动作请求
  → 目标已办/操作记录中的实际人员
  → 运行界面与日志中的人员
~~~

检查 buildRunContext、ResolveNodeAuditors、ResolveActionPersonIDs、nextAuditorsForTransition、BuildPreview、写前准备、失效重登、事实重读和结果记录。不能只替换一个 PlanAccount 引用就算完；计划归属/发起语义仍保留，当前动作会话必须按职责区分。

### 8.3 人员验证矩阵

- 一键配置的可选节点为合法范围内稳定随机，刷新和重复配置不漂移。
- 手动改为另一个合法人员并保存，执行中目标待办/已办、实际登录账号、页面处理人均对应此人。
- 固定人员、主管/职级/扩展属性/表单人员由目标规则解析，不强制使用计划账号，不伪造可编辑候选。
- 会签指定人数、会签全部、竞签一人、可跳过零人等实际适用规则，分别核对选择人数和完成条件。
- 缺候选、候选失效、无法解析账号、无权限或登录失败，指出节点、人员、原因与可处理位置，不回退到骆蒙恩继续写。
- 移交/加签/回退/取回后重读真实任务，处理人改变时切换会话；同一节点多次进入不能复用过期 task/batch。
- 手动分支、线性下一节点、并行多个下一节点的选人参数均按目标要求核对，不只支持单个 nextNodeKey 的简单线路。

至少一个完整样本必须包含与骆蒙恩不同的实际审批人。若所有样本都由骆蒙恩审批，不能证明人员配置被执行器消费。

### 8.4 会话验证矩阵

- 同账号连续步骤复用有效会话；页面轮询不会每次登录，写前不会无理由强制重登。
- 不同账号使用独立缓存与登录锁；不能把 A 的 SID 交给 B 的动作。
- 同账号并发首次登录/失效恢复正确合并；旧请求报告失效不能删掉后来新建的有效会话。
- 只读请求确认会话失效后按既有有界规则恢复；不会无上限登录重试。
- 写前登录失败时没有业务写；明确被鉴权层拒绝且能证明未进入业务的写，才允许按已勘定规则有界恢复。不能把任意业务失败、超时或响应丢失解释成可重发。
- 写是否发生无法确定时，结束为“结果待确认”，不自动继续或重放。
- iframe 发放的会话有效；表单选项读取、页面轮询与执行器写请求同时发生时不互相踢登录。
- 服务重启后按现有恢复规则处理运行状态；会话可重新取得，但不能借重登重新发送已有不确定写。

失效、响应丢失等难以安全重现的分支用隔离测试覆盖；真实环境验证缓存复用、多处理人切换和并行稳定性。不要为了测失效高频登录共享账号。

## 9. 工作包 E：浏览器验证执行、控制和调度

依赖：至少一条路径已证明表单正确、动作完整、实际处理人正确。先跑简单完整链，再扩大到 10 条合同路径。

### 9.1 单步、自动和人工控制

| 编号 | 浏览器操作 | 必须观察到 |
| --- | --- | --- |
| E01 | 选择单步启动，等待后点击执行一步 | 点击前不发送该步写；一次有效点击仅推进一步，写后核验落账再展示下一步 |
| E02 | 快速重复点击执行一步 | 按钮和后端共同防重复，同一动作不会多发一次 |
| E03 | 自动模式，保留首次写断点启动 | 在第一次真实写前停下，原因明确；放行后按自动模式继续 |
| E04 | 自动模式，关闭首次写断点启动 | 开关真实生效，按配置连续执行；必要安全断点仍有效 |
| E05 | 单步切自动 | 从当前未执行步骤继续，不重做已完成步骤，不新建另一条运行 |
| E06 | 自动执行中切单步 | 当前已发步骤完成核验和落账，在下个安全边界停；显示切换请求和实际生效状态 |
| E07 | 人工控制分别点击执行一步、执行到下一节点、继续运行 | 每个按钮的实际停止条件与说明一致；不是三个按钮都只执行一步 |
| E08 | 当前人工控制与其他模式互切 | 产品提供的切换入口均验证；若有真实限制，按钮禁用且说明原因，不提供死按钮 |
| E09 | 设置并命中步骤/节点/动作断点，继续 | 命中对象正确，继续后不在同一步无限重复命中 |
| E10 | 暂停 → 继续；写请求进行中请求暂停 | 暂停在安全边界生效；待处理请求有真实状态，不伪装已暂停 |
| E11 | 停止当前路径 | 已发请求按规则收尾，之后不再发送新动作；停止为终态，不能继续 |
| E12 | 刷新页面、离开运行页再返回 | 同一运行事实持续可见，不重复启动，不丢控制状态 |

单步中的“执行一步”是一个编译步骤，不一定等于离开一个节点；保存草稿和审批暂存后留在原位置必须说清楚。只读系统步骤也要明确区分。

路径偏离必须强制停止，不能“跳过失败继续”。可用隔离测试验证偏离判定；需要真实目标外部操作制造偏离时，限本轮测试实例且先明确操作范围，不碰历史业务实例。

## 10. 工作包 F：运行页面的信息层次与可处理提示

依赖：已有真实运行数据、暂停和失败状态。可以随对应问题修复，但最终必须用真实复杂运行再验证。

### 10.1 卡片排布目标

沿用现有画布和组件系统，调整信息层次，不更换布局引擎或引入整套界面框架。

节点卡片建议按以下顺序组织；具体尺寸由真实最长名称和状态检验：

~~~text
节点名称                         状态
当前动作：审核同意
处理人：实际姓名        第 3 / 8 步
耗时或简短暂停/失败原因
~~~

只在有相应事实时显示对应行。未开始节点不塞满“暂无/--/未知”。多个处理人给出可读摘要和详情入口，不能把几十个姓名挤成一行。

详细配置、全部动作、日志和原始诊断放到点节点后的现有面板；画布上的一句错误必须仍能让用户判断要点哪里。

### 10.2 提示验收规则

每条可处理的问题都回答：

1. 哪个计划、路径、节点、动作或字段出了什么问题。
2. 为什么影响当前操作，哪些内容尚未保存或尚未执行。
3. 用户下一步能做什么，按钮能否直接带到对应位置。

禁止只显示“配置有误”“需要重新确认”“执行失败，请重试”“请联系管理员”等泛化提示。

示例应按真实原因生成：

| 场景 | 提示方向 | 实际动作 |
| --- | --- | --- |
| 人员数量不足 | “合同管理部需要 2 位处理人，目前只选择了 1 位。” | 打开该路径该节点的处理人员区 |
| 分类选项失败 | “合同分类选项读取失败，分类调整尚未完成，当前不能保存。” | 重试该阶段，或定位合同分类字段 |
| 动作缺失 | “暂存不会完成审批，请补充同意后再运行。” | 定位缺项动作区并展示补全 |
| 当前人员登录失败 | “无法登录本节点处理人〈姓名〉，本步尚未发送。” | 查看具体原因；可修改配置时定位人员区 |
| 目标业务拒绝 | 显示真实业务原因与受影响节点 | 可处理时定位字段/人员，不能通用换号或重试 |
| 写结果不确定 | “请求已发出，但暂时无法确认处理结果。本次运行已结束，请先查看目标实例状态。” | 提供既有只读结果/定位入口，不提供盲目重发 |

已运行计划配置只读时，定位应显示配置及原因，给出从计划重新准备的正确入口；不能出现点了却无法修改且没有解释的按钮。

定位不只是打开页面：应选中正确路径/节点，展开对应人员、动作或表单区域并滚动到问题。跨页面定位后刷新仍应合理，不能只靠一次易丢失的内存事件。

### 10.3 真实视觉检查

在常见桌面宽度至少检查 1366 和 1920、浅色和深色、侧栏展开与收起、画布全屏与退出。

逐项检查：长节点名、多人、长错误、多个并行节点、连续轮询、当前节点切换、暂停、失败、完成。文字不重叠，按钮不挤出卡片，关键内容不被遮罩挡住；缩放后节点和连线关系仍清楚。

状态变化不让整张卡片跳动或脉冲闪烁。当前节点定位不反复抢夺用户正在拖动的视口。加载、空数据、请求失败采用不同且有用的说明。
