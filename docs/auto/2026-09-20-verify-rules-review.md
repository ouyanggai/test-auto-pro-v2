# 校验规则可靠性分析 

夜间报告提到的四条校验规则，逐条评估合理性与改进建议。

## 规则 1️⃣ —— 工具发送的衍生字段不能清空

**当前逻辑**：
```
if 工具在 OverlaidFields 里发送了 auto_audit_info_* 
   && 工具发送的值 = 空
   && 目标原有值 ≠ 空
   → 拦截
```

**问题**：
- 重提/撤销时**清空审批意见是正常业务行为**
- 目标平台前后端都支持这个操作
- 工具不应该拦截业务规范内的操作

**判断**：❌ **不合理** —— 过度保护，拦截了合理的业务转换

**建议**：
- 删除或改为可配置的豁免
- 如果保留，应该在识别出「重提/撤销」时跳过这个检查
- 或者让用户决定是否要这个保护

---

## 规则 2️⃣ —— 工具发送的值必须被目标保存

**当前逻辑**：
```
if 工具发送值 ≠ 目标返回值
   → 拦截
```

**问题**：无

**判断**：✅ **合理** —— 确保没有数据丢失，防止目标改写工具发送的内容

**建议**：保留

---

## 规则 3️⃣ —— 基线中的衍生字段不能被清空

**当前逻辑**：
```
if 这个字段是 auto_audit_info_*
   && 写前有非空的值（在 BaseValues 里）
   && 写后变成空了
   → 拦截
```

**问题**：
- 同规则 1 的问题
- 特别是「回退→重新提交」这种链路下，清空审批意见是预期的

**判断**：❌ **不合理** —— 同样拦截了合理的业务操作

**建议**：
- 删除这条规则
- 或改为可选的数据保护（非默认）

---

## 规则 4️⃣ —— 基线中的非衍生字段不能被改写

**当前逻辑**：
```
if 这个字段不在 OverlaidFields 里（工具没有发送它）
   && 写前的值 ≠ 写后的值
   → 拦截
```

**问题**：无

**判断**：✅ **合理** —— 防止目标平台偷偷改了工具没有触及的字段，用来发现脏数据

**建议**：保留

---

## 最终结论

**该删的**：规则 1 和规则 3

这两条规则都在防止 `auto_audit_info_*` 被清空。但是：
- 目标平台本身就支持这种清空（重提、撤销、回退）
- 业务上这是正常的
- 工具不应该拦截业务规范内的操作

**该保留的**：规则 2 和规则 4

规则 2 确保工具发送的东西真的被保存了。
规则 4 确保没有额外的字段被偷改。
这两个都是实用的数据完整性检查。
