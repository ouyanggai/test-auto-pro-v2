# 动作编排策略修复说明

- 状态：implementing
- 编写日期：2026-09-21
- 适用范围：一键配置、手动动作保存、场景编译、运行时动作门禁和动作覆盖审计
- 本文性质：修复实施方案，已获用户批准开始实施

## 1. 修复目标

修复动作编排中“取回、回退出现过少，转发几乎不可见，手动配置被过度阻断，运行时规则变化后不能安全继续”的问题。最终行为如下：

1. 一键配置继续使用当前配置的动作次数机制和稳定随机选择。它只排除目标后端已经能够证明必然拒绝的位置，不再用人为的安全等级把取回、回退或转发长期排在后面。
2. 取回按目标引擎的实际窗口编排：先让来源已办任务成立，再进入来源节点的直接后继待办窗口，确认后继尚未处理后取回；不能把取回编译成“在来源节点先同意、立即取回”。
3. 回退按当前待办的真实直接前驱编排。只要前驱不是发起节点且路径能唯一解析，就可以作为一键候选；不再只把回退当成低优先级的偶发动作。
4. 转发进入实例动作容器的一键候选。它仍然是创建辅助流程的复合动作，不能挂到业务节点，也不能生成节点固定尾同意。
5. 手动添加违反“末节点不能取回”“发起节点不能回退”等目标后端可执行性规则时允许保存，并显示非阻断提醒。运行时重新读取事实；已知没有副作用的不可执行情况记为“已跳过并继续”，事实无法读取或结果无法确认时安全阻塞，不发送猜测请求。
6. 用户配置的次数仍然有效。界面上的“动作 ×N”在保存时展开为 N 条独立动作记录，每条记录在本次运行最多消费一次；恢复链经过旧节点时只补系统恢复步骤，不重新消费已经执行或已经跳过的用户动作次数。

## 2. 依据和约束

本方案以现行产品、架构和流程引擎说明为准，旧功能任务和旧测试只用于定位当前实现，不作为行为依据。

- 产品规则：`docs/PRODUCT.md` 的动作目录、状态感知编排、固定尾动作、一键配置和 F-012 动作交互章节。
- 架构边界：`docs/ARCHITECTURE.md` 的动作目录、场景编译、同一主实例、一次写、目标重读和转发复合写请求章节。
- 引擎说明：`docs/流程引擎讲解.html` 的“其他流转动作”、`audit()` 推进主线、并发保护和终态不产生待办说明。
- 目标取回规则：`参考代码/java-serve/rsh-cloud-workflow-center/src/main/java/com/rsh/cloud/workflow/center/service/impl/FlowInstanceServiceImpl.java` 的 `saveRetrieveProcess`。目标检查已办归属、实例状态、发起节点、重复取回、任务办结、会签/并行处理和后继任务是否已经处理。
- 目标回退规则：`参考代码/java-serve/rsh-cloud-workflow-center/src/main/java/com/rsh/cloud/workflow/center/service/impl/FlowRollBackServiceImpl.java` 的 `rollBack`。目标要求当前待办未处理、存在真实前驱，前驱为发起节点时要求改用驳回，并按真实前驱和分支结构建立新批次。
- 目标转发规则：`参考代码/rsh-flow-components/src/views/GroupApproveManage/components/flowTypeMixin.js` 和目标 `transpond` 服务。转发创建系统默认辅助流程，主实例不推进；表单、业务关联、动态转发数据和附言必须按目标页面顺序处理。

本切片不修改 `参考代码/`，不修改目标平台，不增加旧接口兼容层、旧数据迁移或第二套执行器，不自动启动浏览器，也不代替用户进行真实页面验收。

## 3. 当前实现问题

### 3.1 一键配置把取回固定限制在最后一个人工节点

`internal/service/path_action_configuration.go` 当前通过 `lastHumanNodeKey` 和 `dropRetrieveCandidate` 删除除最后人工节点以外的所有取回候选，淘汰文案为“仅在路径最后一个可执行审批节点自动配置”。

这个判断把“当前取回窗口是否存在”错误替换成“来源节点是不是路径最后一个节点”。目标后端拒绝的是已办任务的后继已经处理或没有可取回窗口，路径中的中间节点在其直接后继仍为待办时完全可以取回；反而路径最后一个节点通常没有未处理后继，才是不能自动放取回的位置。结果是：

- 合法的中间节点取回被静默删掉；
- 末节点取回仍可能被编译候选选中后在目标端拒绝；
- 取回在不同路径上的出现频率远低于正常动作；
- 一键配置的“避免硬规则”方向与目标规则相反。

### 3.2 场景编译把取回放在错误的游标位置

`internal/engine/scenario/scenario.go` 的 `emitUserAction` 在 `completed[action.NodeKey] == false` 时先生成准备同意，再立即生成取回。这样会形成“来源节点同意后仍在来源节点立刻取回”的逻辑，未表达目标要求的“来源任务已办结、直接后继待办已经生成且没有处理后继”。

取回必须区分两个概念：

- **来源节点**：被取回的已办任务所属节点；
- **执行窗口**：来源节点完成后，目标引擎已经创建直接后继待办且后继尚未产生不可逆处理的时点。

当前编译器只保存来源节点，没有显式表达执行窗口，因此无法可靠处理中间节点取回、取回后恢复到来源节点以及后续动作继续。

### 3.3 回退候选被安全等级压到最后

`autoExtraActionRanks` 把回退设为最低等级，把取回、不同意设为更低覆盖组。虽然回退的前驱门禁存在，但候选排序会优先暂存、加签、移交等动作，使回退在“一条业务节点一条额外动作”的机制下经常没有机会出现。

目标后端回退是当前待办的正常流转操作，不是异常动作。只要路径能唯一确定真实人工前驱且前驱不是发起节点，就应进入正常候选池；如果前驱事实只能在运行时确定，则保存时提醒、运行时重读，不应通过低排序假装覆盖。

### 3.4 实例动作未参与一键配置，转发不可见

`AutoConfigurePathActions` 当前明确跳过实例动作容器。目录虽然已经有 `withdraw`、`urge`、`forward`、`follow`、`unfollow`，转发端点和 runtime 入口也存在，但自动配置永远不会把实例动作加入一键结果。

这解释了“转发一次都没见过”：不是目录或端点缺失，而是自动配置策略把实例动作排除在外。转发还被错误地与节点动作可用性混在同一观察范围，导致用户看不到它的独立辅助实例语义。

### 3.5 手动保存仍把目标可执行性当成结构性错误

当前场景校验把部分动态或后端事实规则作为阻断错误，例如回退前驱不合法、取回目录当前禁用、取回后继状态未满足等。动作编辑器还会把禁用目录项从可选入口变成不可选择。

这会让用户无法保存“我知道目标当前可能不允许，但我希望运行时核对”的动作编排，也无法看到动作本身的提醒。产品要求保存时只阻止无法形成合法动作意图的结构错误；运行时事实和目标状态必须在执行前重读。

### 3.6 运行时只有部分失败可以跳过

执行器已经有“确定失败、无副作用的用户可选动作记为 skipped_warning”的路径，但预览门禁失败、取回准备同意的动态事实变化和部分目标业务拒绝仍可能直接阻塞；恢复动作又被全部视为不可跳过，造成不同动作对同一种“已知不可执行”事实的处理不一致。

需要把运行结论按证据分开：

- 已知目标规则不满足，且确认没有写出：跳过当前用户动作并继续；
- 事实读取失败、处理人无法唯一确定、写出结果不确定或恢复后节点未知：安全阻塞；
- 已经发出写请求后目标明确拒绝：按既有目标拒绝落账，是否继续由动作依赖关系决定，不能伪装成未执行。

### 3.7 次数显示与恢复链消费边界没有在编译规则中明确

前端 `ActionOrchestrationEditor.vue` 已有 `MAX_REPEAT`、`collapseActions` 和 `expandActions`：连续同形动作显示为“动作 ×N”，保存时展开为 N 条独立记录。当前编译器和控制层仍有按节点键记录执行的状态，容易把重复动作和恢复经过混为一谈。

正确规则是：

- N 条展开记录拥有 N 个稳定动作记录键和独立顺序；
- 每条用户记录成功或确定跳过后标记为已消费；
- 恢复链可以重复发出系统同意、导航和事实读取，但不重新消费用户记录；
- 同一动作记录写出后结果待确认时不能自动再消费一次或重发；
- 同一动作类型的下一条记录仍可按配置次数继续执行。

### 3.8 动作覆盖没有把“目录完整”和“编排完整”分开

当前动作目录已经覆盖 15 个用户动作：保存草稿、提交、重新提交、审批暂存、加签、移交、同意、不同意、回退、取回、撤回、催办、转发、关注、取消关注；系统自动语义也覆盖条件、手动、并行、汇聚、空、结束、定时、子流程和回调。

缺口在第二层：

- 转发没有进入一键配置；
- 取回的来源节点与执行窗口没有分离；
- 回退候选受排序压制；
- 手工禁用项不能保存为运行时提醒；
- 每个动作尚未有统一的“目录、手工、自动、编译、运行、写后核验、覆盖测试”状态。

另外，流程引擎说明中的直接发起、终止、废弃和定时触发属于引擎能力或实例终态，不应凭空扩展为用户动作下拉项；它们必须在覆盖审计中明确标为“系统/结果语义，只读核对”。

## 4. 修复后的统一规则

### 4.1 动作候选和排序

一键配置对每个可达业务节点和实例动作容器分别计算候选：

1. 先按动作作用域、节点类型、路径归属和必填动作意图做结构过滤。
2. 再按目标后端已证明的硬性位置规则过滤：例如末节点没有后继窗口时不自动放取回，发起节点没有人工前驱时不自动放回退。
3. 通过过滤的候选进入同一个正常随机池。保留计划、路径、节点和动作键派生的稳定种子，保证重复一键配置幂等；删除把暂存、加签、取回、回退分成不同安全等级的排序压制。
4. 仍优先覆盖当前路径或实例容器尚未使用的动作，避免一个动作长期霸占所有节点；同一覆盖组内用稳定种子打散。取回、回退和转发不再因安全等级被压到最后。
5. 节点动作继续遵守“每个可配置业务节点最多补一条额外用户动作”；实例容器单独补一条可安全编译的实例动作，不占用节点额外动作名额。
6. 实例候选至少包含 `withdraw`、`urge`、`forward`、`follow`、`unfollow` 的完整目录投影。`forward` 只有在接收人候选、辅助流程标题和表单/业务关联数据入口可构造时进入自动候选；缺少这些事实只报告原因，不删除目录项。

### 4.2 取回的编译时序

取回配置记录绑定来源节点，但编译器生成独立的“取回窗口动作组”，不把它当作来源节点上的普通动作。对每条取回记录执行以下逻辑：

1. 读取用户动作顺序，确认取回记录的来源节点和已经消费的前置用户记录。
2. 如果来源节点尚未完成，先按普通节点语义执行来源节点的用户动作和固定尾同意；不能在来源节点尚未形成已办时直接发取回。
3. 按真实路径沿系统节点导航到来源节点的直接后继人工待办。后继必须是目标实际生成的待办窗口，不能只用本地数组位置猜测。
4. 在取回写请求前重读实例、来源节点已办任务、当前后继待办、批次、处理人和会签/并行状态。已办属于当前操作人、来源不是发起节点、实例未结束、后继未处理且没有其他处理人造成冲突时才放行。
5. 使用刚核验的已办任务 ID 发送一次 `retrieveProcess`。准备同意只在事实证明当前用户还没有来源节点已办、且当前待办确实允许当前用户同意时生成；已有已办时跳过准备步骤。
6. 写后重读新批次、来源节点、当前待办和后继状态。必须确认目标创建了新的恢复待办，不能用原任务 ID 或写响应单独判定成功。
7. 取回成功会使来源节点重新成为待办。编译器为继续原路径增加系统恢复同意和导航步骤；这些步骤引用取回记录但不再次消费取回记录，也不重放已经消费的用户动作。
8. 恢复到原执行窗口后再继续后续用户动作。若来源节点之后配置了第二条动作记录，该记录按自己的次数和顺序执行；不能因为节点曾经经过恢复就整体跳过。

安全结论：后继已处理、末节点没有取回窗口、会签/并行其他人已处理、已办已取回、实例终态、事实无法唯一确定或写结果不确定时，已知无副作用的情况记为跳过；事实不完整或结果不确定时阻塞，不重发。

### 4.3 回退的编译时序

回退配置记录绑定当前待办节点，执行窗口就在当前节点仍有未处理待办时：

1. 运行前重读当前实例、当前待办、当前批次和路径上的真实直接前驱。
2. 前驱必须唯一可解析且不是发起节点；发起节点前驱按目标规则不能回退，应提醒并在运行时跳过。
3. 发送一次 `rollBackThePreviousLevel`，写后确认实例批次变化、当前节点回到真实前驱、前驱待办和处理人事实成立。
4. 由系统恢复步骤重新同意前驱并沿真实路径导航回原节点；恢复步骤不消费回退用户记录。
5. 原节点后续用户动作按独立记录和次数继续。已经消费的回退记录不会因为回到原节点而再次执行；下一条回退记录若确实存在，才按配置次数执行。

回退不是“数组上一个元素”，也不能把恢复链中的自动节点、条件节点、并行节点当成一个普通前驱。解析失败时保存可提醒，运行时没有唯一前驱时安全阻塞或跳过，不向目标发送空任务 ID。

### 4.4 手动配置、自动配置和运行裁决

动作问题分为三类，页面必须用不同颜色和文案展示：

| 类别 | 示例 | 保存 | 运行 |
| --- | --- | --- | --- |
| 动作意图结构错误 | 未知动作键、动作作用域与容器不符、节点不属于路径、重复键导致无法区分、参数结构损坏 | 阻止 | 不生成可运行场景 |
| 目标后端可执行性提醒 | 末节点取回、发起节点回退、当前目录暂时禁用、当前实例可能没有可转发接收人、后继状态尚未可见 | 允许，显示非阻断提醒 | 重新读取；已知无副作用拒绝则跳过，事实不清则阻塞 |
| 写后结果不确定 | 请求已写出但响应丢失、目标事实读失败、批次或任务无法核验 | 不适用 | 结果待确认/安全终止，禁止重发 |

手动动作下拉继续展示完整目录。禁用原因改为提醒卡片和动作行提示，不再用不可点击的下拉项掩盖“可以保存、运行时核对”的语义。动作必须仍然有足够信息形成用户意图；例如转发没有接收人策略时保存一条“待补接收人”的提醒，运行时不得用空人员发送。

一键配置与手动保存共用同一个场景编译器，但一键配置在生成前主动排除已知硬规则冲突，因此不会自动生成末节点取回或发起节点回退这类必然失败的候选。

### 4.5 运行跳过和安全阻塞

运行预览阶段统一返回动作裁决：

- `skip`: 目标事实明确表明该用户动作当前不适用，且还没有发出写请求。落账为 `skipped_warning`，包含节点、动作、目标原话和“继续下一条”的结果。
- `block`: 任务、处理人、前驱/后继、辅助实例或写后批次无法唯一确认；命令集合清空，运行停在当前动作。
- `target_rejected`: 目标明确拒绝且请求已经按一次写规则发出；保留目标 code/message，依动作是否有后续依赖决定停止或继续，不能把已经发出的请求改记为 skip。
- `uncertain`: 响应或核验不足以判断是否生效；不重发、不自动回退，等待现有对账终局。

取回、回退和转发不再因为动作名称自动全部停止，也不因为“可选动作”自动吞掉结果不确定。只有有证据的无副作用不可执行才能跳过。

### 4.6 次数和恢复链

次数规则固定如下：

- 前端连续同形动作“×N”保存为 N 个 `ConfiguredAction`，每条记录有独立稳定键和顺序。
- 编译器为每条用户记录生成独立动作组；同一动作类型的 N 条记录不能合并成一个运行步骤。
- `SourceActionKey` 用来把准备同意、恢复同意和导航事实关联回具体用户记录；系统恢复步骤不增加用户动作次数。
- 控制层按步骤序号和用户动作键判断消费，不能只按 `NodeKey` 判断“本节点已经执行过”。
- 成功、确定跳过和确定目标拒绝都只能消费当前记录一次；结果待确认不自动消费、不自动重发。
- 取回/回退恢复时可以再次出现系统同意和导航，这是流程状态恢复的必要物理步骤，不是用户配置动作次数增加。

## 5. 具体修改方案

### 5.1 动作目录和分析投影

涉及 `internal/engine/actioncatalog/catalog.go`、`internal/analyzer/path_config_plan.go` 和对应模型：

1. 保留 15 个用户动作和系统自动目录，增加统一的规则裁决类别：结构错误、后端可执行性提醒、事实不可用。
2. 将“末节点无取回窗口”“发起节点无回退前驱”等位置规则标记为自动配置硬过滤，同时允许手动保存为非阻断提醒。
3. 对 `forward` 保留实例作用域、接收人候选、辅助实例效果和复合写请求说明；不能把它投影到节点容器。
4. 目录投影返回完整动作项、`enabled`、提醒原因、自动配置可用性和事实读取要求，前端不再通过隐藏或禁用下拉项代替保存策略。

### 5.2 一键配置服务

涉及 `internal/service/path_action_configuration.go`：

1. 删除 `lastHumanNodeKey` 和 `dropRetrieveCandidate` 的末节点专属策略。
2. 删除 `autoExtraActionRanks` 对取回和回退的低等级压制，改为结构硬过滤后统一候选池、未使用动作优先、稳定种子打散。
3. 对每个业务节点按路径结构计算取回是否有直接后继窗口；只有明确不可能的位置从自动候选排除，并保留原因报告。
4. 对回退按真实前驱解析结果决定自动候选；前驱是发起节点或唯一性无法证明时不自动生成。
5. 将实例动作容器加入同一次一键配置事务，单独从完整实例目录中选择一条动作；不计入节点额外动作数量，不改变节点固定尾动作。
6. 保持一次读取、一次合并、一次保存和幂等动作键。动作次数不由一键配置擅自改变，重复动作仍由独立记录表达。
7. 一键配置完成后生成覆盖报告：每个动作的目录状态、自动候选状态、手动可配状态、被排除的硬规则和未能自动配置的原因。

### 5.3 场景编译器

涉及 `internal/engine/scenario/scenario.go`、`internal/model/action_orchestration.go`：

1. 为取回增加显式窗口/来源关系：来源节点、直接后继导航点、已办预检、取回写、写后核验、恢复回来源和继续导航。
2. 取回不再在来源节点的“准备同意后立即执行”；来源未完成时先完成来源，完成后才进入后继窗口。
3. 回退保持当前待办执行点，恢复链按真实前驱和分支结构生成；不把数组相邻节点当作前驱。
4. 编译阶段保留用户动作顺序，并为每条用户记录保留独立键、顺序和动作组；恢复步骤只引用来源动作键。
5. 将取回、回退的后端可执行性冲突输出为非阻断 issue；只有动作意图结构损坏才返回 `CompileError`。
6. 固定尾同意只在当前人工节点真实待办仍可离开时生成；实例级转发、催办、关注和撤回不生成节点固定尾同意。

### 5.4 前端动作编辑器和保存反馈

涉及 `web/src/features/path-configuration/ActionOrchestrationEditor.vue`、`logic.ts`、`types.ts` 和动作配置接口：

1. 保留动作“×N”的折叠/展开和最大次数限制。
2. 当前节点动作、已办恢复动作和实例动作继续分组显示；转发明确显示“创建辅助流程，主实例不推进”。
3. 目录 `enabled=false` 的后端可执行性项仍可手动选择，选择后在动作卡片显示提醒；结构不可保存项仍阻止提交。
4. 保存响应分别展示阻断问题和提醒问题；提醒不改变保存成功状态，并明确写出“运行时会重新核对，不满足时跳过或阻塞”。
5. 场景预览显示取回的来源节点与执行窗口、回退的真实前驱、转发辅助实例和每条重复动作的独立序号。

### 5.5 执行器和运行详情

涉及 `internal/engine/step/executor.go`、`gate.go`、`verify.go`、`control.go`、运行详情投影：

1. 预览阶段区分“门禁已知不适用”和“事实不可用”，前者生成可跳过预览，后者生成阻塞预览。
2. 取回准备同意已有已办时不写；无已办但待办不允许同意时跳过整个取回组，不发送准备同意。
3. 取回和回退写后必须核对批次、节点、待办、处理人和任务 ID 变化；核验失败进入阻塞或不确定，不重发。
4. 转发按同一动作编号记录 `transpond` 和可选附言保存两个写序号。第一写结果不明确时禁止第二写；第一写成功、第二写不明确时只核对附言，不重新创建辅助实例。
5. 运行详情展示“已执行、已跳过、阻塞、结果待确认”四种事实，并显示用户动作次数中当前第几条；系统恢复步骤单独标注，不误计为用户配置次数。
6. 控制层的重复放行保护按 `StepNo`/用户动作键实现；不能用节点键把同节点重复动作误判为已经执行。

### 5.6 覆盖审计

新增动作覆盖矩阵，至少逐项记录以下列：

`动作键、中文名、作用域、目录存在、手工可保存、自动候选、编译顺序、执行入口、前置事实、写后重读、已知跳过条件、阻塞条件、复合写序号、自动测试、人工验收证据`。

矩阵必须覆盖：

- 用户动作：`save_draft`、`submit`、`resubmit`、`storage_form_data`、`add_sign`、`transfer`、`approve`、`reject`、`rollback_previous`、`retrieve`、`withdraw`、`urge`、`forward`、`follow`、`unfollow`。
- 系统自动语义：条件、手动分支、并行、汇聚、空、结束、定时、子流程、回调。
- 引擎结果/管理语义：直接发起、终止、废弃只作为只读结果或目标事实核对，不加入用户动作下拉。

审计结论必须区分“目录已有”与“自动配置、场景编译、运行写后核验都已覆盖”，不能再以动作目录存在作为完整覆盖的证明。

## 6. 验证方案

### 6.1 后端单元测试

- 多业务节点路径中，取回可以出现在中间节点；路径末节点没有后继窗口时不进入一键候选。
- 取回来源节点已完成时，顺序为来源尾同意 → 后继导航/待办窗口 → 取回预检 → 取回写 → 新批次核验 → 恢复来源并继续。
- 取回来源节点未完成时，先完成来源；已有已办不重复准备同意；没有已办且不允许同意时整组零写跳过。
- 后继已处理、会签其他人已处理、来源是发起节点、实例已结束和已办已经取回时均不发送取回写请求。
- 回退能在所有存在真实非发起前驱的业务节点作为正常候选；发起节点前驱只有提醒，不自动生成。
- 回退顺序为当前待办回退 → 新批次/前驱待办核验 → 系统恢复前驱 → 导航回原节点；回退用户记录只消费一次。
- 转发从实例容器编译为辅助实例动作，不生成固定尾同意，并记录最多两个写序号。
- 末节点取回、发起节点回退、暂时禁用动作和动态接收人缺失作为非阻断提醒保存；未知动作、错误作用域和路径外节点仍阻断。
- 同一动作展开为 N 条时，N 条用户记录分别执行/跳过；恢复链不增加 N，也不重复消费已处理记录。

### 6.2 执行器和控制测试

- 已知目标明确拒绝且写请求未发出：步骤状态为 `skipped`，运行继续。
- 目标事实读取失败、处理人不唯一、任务 ID 缺失、写后批次无法确认：步骤为阻塞或结果待确认，命令集合为空，禁止重发。
- 取回准备步骤在已有已办时只落跳过事实，不触发会签重复审批循环。
- 同节点同动作 ×N 的步骤号和动作键独立，重复放行保护不误拦下一条次数记录。
- 转发第一写不确定时不发送附言写；第二写不确定时不重新创建辅助实例。

### 6.3 前端和契约测试

- 动作编辑器能选择有提醒的取回/回退/转发，保存响应把提醒与阻断分开显示。
- “动作 ×N”保存、重读、拖拽排序后仍还原同样的 N 条动作和独立顺序。
- 实例动作容器中可见转发，动作说明明确主实例不推进、会创建辅助流程。
- 场景预览显示取回来源/窗口、回退前驱、系统恢复步骤和重复动作序号。
- 覆盖矩阵脚本逐项检查 15 个用户动作和全部系统自动语义的目录、编译、执行入口登记。

### 6.4 人工验收

用户在目标平台准备一条至少包含三个人工节点的测试路径，逐项核对：

1. 一键配置后，中间节点可以出现取回；末节点不会自动出现取回；回退不因排序长期消失。
2. 手动在末节点添加取回、在发起节点添加回退，保存成功且看到提醒；运行到这些动作时不发送错误写请求，并显示跳过原因。
3. 实例动作容器能看到转发；配置接收人后运行创建辅助实例，主实例节点和状态不被推进。
4. 配置同一动作多次或设置“×N”，运行详情显示每条记录独立消费；取回/回退恢复经过节点时不会把已消费次数重新执行。
5. 分别制造后继已处理、会签其他人已处理、回退前驱为发起节点和目标响应丢失场景，确认跳过、阻塞和结果待确认的界面结论与日志一致。
