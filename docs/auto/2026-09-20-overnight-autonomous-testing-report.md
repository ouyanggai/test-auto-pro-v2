判据的四个必要条件（缺一不可，全部只用已读事实）：

1. 本步节点标识非空；

第 4 条的两个子条件是分开判的：只满足「本步节点不在了」不够——那可能是越到了配置之外的分支，
属于路径偏离，必须按原样判「未变」，交给独立的偏离判定处理，**绝不能把走错分支洗成成功**。

**这个分类是诚实的**（「失败 / 工具缺陷」，依据行明确"写请求没有发出"），
没有把工具自身的问题伪装成目标平台的问题，符合语义清单。

**根因（已用落盘事实定位）**

失败点是 `executor-service/src/server.ts:767` 的 `waitForExecutorNative`：它在发起/详情装载前等待
注入脚本捕获原生宿主 `window.__executorNative`，上限 `CAPTURE_TIMEOUT_MS` = 60 秒。
而原生宿主能否出现，取决于页面能否拿到模板数据 —— 即经 Go 转发的
`POST /api/web/flowTemplateApi/list`。

查 `logs/application/2026-09-21/network-error.log`，该端点自 06:41 起**每分钟恰好 1 次**失败
（正好对应 60 秒超时节奏），单条事实为：

```
method=POST endpoint=/api/web/flowTemplateApi/list request_class=read
status_code=- duration_s=0.000 result=failure outcome_kind=-
error_type=timeout message=- code=- retry=false retry_attempt=1
transport_phase=unclassified request_written=false
```

四个字段合起来把结论钉死了：

- `error_type=timeout`：这是一次超时；
- `duration_s=0.000` 且 `request_written=false`：**请求一个字节都没发出去**，
  不是"发出去没等到响应"，而是连连接都没建立成；
- `transport_phase=unclassified`：连"连接被拒"或"连接中断"都归不了类，

也就是说：**页面发起的模板列表转发请求没能建立到目标网关的连接，页面因此拿不到模板数据，
原生宿主永远不就绪，60 秒后判装载失败。**

**进一步证据：一条 06:40:51 建立的到目标网关的长连接**

`Get-NetTCPConnection -RemoteAddress 192.168.1.220` 显示 Go 后端（pid 67336）持有**一条**
到 `192.168.1.220:38081` 的 Established 连接，`CreationTime = 2026/9/21 6:40:51`
—— **正好是 F-P04 开始出现的时刻**（该运行 54 是 06:33 启动的，前面的路径 5/6/7 在 06:40 前跑通）。

而 `internal/adapter/target/client.go:94-104` 的 HTTP 客户端配置是：

```
Timeout:               cfg.Timeout          // TARGET_HTTP_TIMEOUT，默认 120s
Transport: &http.Transport{
    Proxy:                 bypassProxy,
    DialContext:           (&net.Dialer{Timeout: 10s, KeepAlive: 30s}).DialContext,
    TLSHandshakeTimeout:   10s,
    ResponseHeaderTimeout: cfg.Timeout,     // 同样 120s
    IdleConnTimeout:       90s,
}
```

把配置和事实对上：

- `DialContext` 超时是 **10 秒**，而日志里 `error_type=timeout`、`duration_s=0.000`、
  `request_written=false`、`transport_phase=unclassified`；
- `duration_s=0.000` 说明这次 `Do` 调用**几乎没有耗时**就返回了错误——真正的建连等待
  （若走满 10 秒）不会记成 0.000 秒。也就是说**不是在等建连**，而是取到了一条已经坏掉的
  复用连接后立刻失败；
- 这正对应 `transport_phase=unclassified`：`probe.classify(err)` 见到的是
  "复用了已失效的连接" 这类错误，它既不是连接被拒（`connect_refused`）也不是中断
  （`interrupted`），只能落到 `unclassified`；
- 单条连接建立于 06:40:51 且此后一直未被替换，与该时间点之后**每分钟稳定 1 次**失败
  （正好是 60 秒 `CAPTURE_TIMEOUT_MS` 的节奏）完全吻合：每次装载都复用同一条坏连接、
  立刻失败、页面拿不到模板数据、60 秒后判装载超时。

**排除项（都用事实排除了，不是推测）**

- 目标平台本身可达：`http://192.168.1.220:38080` 返回 200、`http://192.168.1.220:38081/api`
  返回 200 且耗时 33ms；同一时刻另外一条到 9187 端口的连接处于 `SynSent`（与本缺陷无关）；
- 不是会话失效：同期 `network-error.log` 里**没有** RESP401；
- 不是执行服务挂了：`http://127.0.0.1:19011/health` 返回 `{"ok":true,...}`；
- 不是部署问题：同一份二进制在 06:33—06:40 之间连续跑通路径 5、6、7 三条（共 87 步）；
- 不是目标平台负载：目标前端与网关在同一时刻都秒回 200。

**通用修复方向（本轮未实施，如实记录）**

根因是"HTTP 客户端复用了一条已被对端单方面关闭的连接，且没有识别出这类错误并淘汰连接"。
正确的通用修法有两条互补路径，都必须建立在**先能识别**这个错误类型的前提上：

1. 在 `ForwardRuntimeRequest` / `call` 的建连失败分支里，把 `err` 的具体类型落进
   `transport_phase` 的诊断（`net.OpError` 的 `Op`/`Net`/`Err`，是否 `ECONNRESET` / `EPIPE` /
   `ErrUnexpectedEOF`），让 `unclassified` 不再吞掉根因；
2. 对"请求尚未写出（`request_written=false`）的连接类错误"按幂等安全处理：只读转发请求
   在未写出时重试一次（会自然换一条新连接），写请求仍严格保持"一次发送一次"不变
   ——这与既有 `readOnlyWithSessionRetry` 只包只读回调的设计一致。

**为什么本轮不硬修**：任务书要求「拒绝表面硬修」。把 `CAPTURE_TIMEOUT_MS` 调大、
或在装载外层整体重试，都会掩盖"连接坏了"这个事实且不解决下次复用；而按上面第 2 条修
必须先把错误类型识别清楚（否则会退化成"所有错误都重试一次"），当前证据还不足以安全落地。
**该项如实记录，留给后续最小验证。**

### F-P05 中止运行会泄漏 runtime 会话，导致同账号后续全部无法启动（已定位根因）

为了验证 F-P04 的"坏连接"假设而重启后端后，运行 56 的路径**在 1 秒内**全部失败
（06:59:57 → 06:59:58），失败形态与 F-P04 完全不同：

```
执行失败：创建 runtime 会话失败：执行服务返回 HTTP 409：
{"error":"账号 骆蒙恩 已有未关闭会话 2c62db14-e37c-415d-b7f1-f4d837101e3e，同一账号必须由 Go 串行排队执行"}
依据：写请求没有发出，不存在目标侧执行结果
```

**这是一条独立缺陷，而且它把 F-P04 的因果链补齐了。**

根因在 `executor-service/src/session-manager.ts:35-39`：

```ts
for (const existing of this.sessions.values()) {
  if (existing.accountKey === key && (existing.status === 'creating' || existing.status === 'ready')) {
    throw new Error(`账号 ${key} 已有未关闭会话 ${existing.sessionId}，同一账号必须由 Go 串行排队执行`)
  }
}
```

这道闸门本身是**正确的**（执行服务按账号唯一开放会话，防止同账号并发操作目标平台，
与 Go 侧的账号锁是同一约束的两层防护，绝不能拆）。缺陷在于**会话的释放依赖 Go 侧主动关闭**：
当 Go 进程在运行中途被重启（或运行被强杀）时，Go 侧已经不知道这些会话的存在，
再也不会去关它们，而执行服务会一直把它们记作 `ready`，于是该账号此后**任何**新建会话
都被 409 拒绝——**永久性卡死，直到执行服务自己重启**。

**这解释了本轮遇到的整条因果链**，也修正了我在 F-P04 里"坏连接"的推断：

1. 06:32:46 我为加载 F-P01/F-P02 修复重启了 Go 后端，**丢弃了它持有的运行 53 上下文**；
2. 运行 53 在执行服务侧留下的 runtime 会话**没有被关闭**，成为孤儿；
3. 此后每次装载，Go 侧新建会话的请求与该孤儿会话冲突；
4. 页面侧拿不到可用的 runtime 会话 → 原生宿主永不就绪 → 60 秒 `waitForFunction` 超时
   → 表现为 F-P04 的"runtime 装载失败"。

F-P04 日志里那个"每分钟恰好 1 次"的节奏（正好 60 秒），以及"同一时刻目标前端与网关都秒回
200"，在这一解释下完全自洽：**问题不在网络、不在目标平台、也不在连接池，而在会话生命周期**。
我在 F-P04 记录的"坏连接"推断**证据不足，此处按新证据更正**；`transport_phase=unclassified`
`request_written=false` 那一行日志对应的是被中止的那次转发（运行时已无有效会话），
而不是"复用了失效连接"。

**为什么本轮不硬修**

- 加"会话被占用就强杀旧会话"是**拆安全门禁**，任务书明令禁止；
- 加"自动重试"也治不了根：孤儿会一直在，重试永远撞同一堵墙；
- 真正的修法是让会话有**可回收的生命周期**，例如执行服务在创建新会话前按
  "孤儿判定"回收同一账号下已无对应 Go 运行上下文的会话（需要 Go 侧心跳或会话租约），
  这是一个涉及两侧契约的改动，**不适合在夜间剩余时间内仓促落地**。

**因此本项的处置是：如实记录 + 明确不修**，并把"夜间自测期间不要重启 Go 后端"作为
本轮的操作约束（本轮已因重启付出代价：运行 54/55/56 的失败都源于此）。

**该缺陷对生产的真实影响**：任何一次 Go 后端重启或强制终止，都会让当时正在执行的账号
在**执行服务重启之前**无法再启动任何运行，且界面只会显示"runtime 装载失败/会话已存在"，
从现象看不出根因。这是值得优先修的一条。

**根因（已定位到具体分支与代码行，证据闭环）**

第 25 步的 `step.log` 完整相位序列（路径 2）：

```
[plan]    取第 25 步：动作 approve，节点 3d4526129ea53e51c1ab2e9c191922c6
[gate]    放行条件已满足：同意
[prepare] 当前处理人 周宏宇（登录账号 周宏宇）会话就绪，即将发出 /flowInstanceApi/audit
[submit]  目标接口返回成功
[verify]  核验事实：实例可读=true 状态=run 当前处理人待办=true（发现能力=true）
          当前处理人已办=已按执行人核对但无该已办 实例当前节点=[62c02a8f5875457a8447e631bcfa41dd]
[verify]  执行结果：目标接口已返回成功，但执行结果暂时无法确认
[settle]  目标接口已返回成功，但执行结果暂时无法确认，路径运行已停止
```

注意两个决定性事实：

1. **实例已经前进**：本步的 `targetNodeId` 是 `a43dd40f…`（第 24 步暂存后实例就停在这里），
   而重读到的 `实例当前节点=[62c02a8f…]` —— 正是本步的**下一跳**。同意**确实生效了**。
2. **`当前处理人待办=true` 且 `已办=已按执行人核对但无该已办`**：周宏宇在本节点的**
   待办还在**，而按执行人过滤的已办里**没有**他这一条。

于是 `ClassifyReread`（`internal/engine/step/verify.go`）走到：

- 第 585 行的分支条件是
  `(approve|reject|storage) && after.CurrentTaskRead`；`CurrentTaskRead=true`，**进入该分支**；
- 第 594 行 `if after.CurrentTaskFound` → 值为 `true`，进入；
- 第 595 行 `actorDone` 要求
  `after.CompletedTaskBasis == CompletedTaskBasisCheckedFound`，
  而实际值是 **`已按执行人核对但无该已办`**（`CheckedNotFound`），所以 `actorDone=false`；
- 于是第 598 行 `return verdict.RereadUnchanged`（**明确未变**）。

回到 `combine`（`verdict/classify.go` 第 110-125 行）：`InitialSuccessClaim` + `RereadUnchanged`
→ 既不满足 `RereadAdvanced`，也不满足「非推进型动作 + Unchanged + ActionFactVerified」
（`approve` 是推进型动作，不在 `isNonAdvancingAction` 名单里）→ 落到 `uncertain(...)`，
原因文案正是 **`successClaimReason(RereadUnchanged)` = 「目标接口已返回成功，但执行结果暂时无法确认」**。

**结论：这是一个真实的判定缺陷，而且判定所依据的「事实」本身自相矛盾。**

同一份重读事实同时告诉工具两件互相冲突的事：

- 「实例当前节点已经变成 `62c02a8f…`」= 流程**已推进**（指向 `RereadAdvanced`）；
- 「周宏宇在本节点的待办还在、且查不到他的已办」= **未推进**（指向 `RereadUnchanged`）。

`ClassifyReread` 只看了后者，完全没有用前者（实例当前节点已经越过本步节点）做交叉验证，
于是把一个**已经成功的写**判成了「无法确认」，并让整条路径终局停止。

**这是「会签/多处理人节点 + 处理人即非计划账号」场景下的通用缺陷，不是某个节点的特例：**

- 该流程节点上存在多人（含加签插入的人），周宏宇只是其中之一；
- 周宏宇同意后**实例直接推进**（因为其他人的待办已在早前被处理完），
  但目标返回的**任务列表里他这条 pending 记录尚未及时消失**（目标侧读到的仍然是写前快照，
  典型的读写时序窗口）；
- 工具于是拿到「节点已前进 + 本人待办未消失」这一对矛盾事实，选择了保守的一侧判「未变」。

**为什么必须修（且不能靠放松门禁来修）**

- 门禁原则「拿不到正面证据不许判成功」**是对的**，绝不能改成「看到成功声明就判成功」；
- 要修的是**`ClassifyReread` 漏用了「实例当前节点已经越过本步节点」这条已经读到的事实**：
  当重读同时观察到「实例当前节点 = 本步配置的下一跳」时，这本身就是**动作已生效的直接事实**，
  应当按 `RereadAdvanced` 处理，而不是只看本人待办快照；
- 同一次运行里路径 1（第 33/37/38 步）、路径 4（第 30/34/35 步）判定完全正确，
  它们的事实是 `待办=false`（本人的待办已经读到消失），走的是正常路径 —— 说明修复面很窄、
  只影响「节点已前进但本人待办快照滞后」这一种时序窗口，不会波及其他场景。

**通用化修复方向（已实施并验证，见「阶段 4」）**

在 `ClassifyReread` 的审批分支里补一条**基于已读事实的推进判据**：
当 `after.CurrentNodes` 已经**不再包含本步节点**、并且**命中了配置的下一跳节点**时，
判 `RereadAdvanced`（写已生效）。这条判据：

- 只用**已经读到的目标事实**，不新增任何猜测；
- 不写死任何节点 ID / 人名 / 流程 ID（下一跳由运行期分支选择或路径配置给出）；
- 不放松「读不到事实」时的保守判定；
- 与既有 `verify.go`「待办已消失：…写都已生效 → RereadAdvanced」的语义一致，
  只是把「已推进」的判据从**仅有本人待办**扩展到**本人待办或实例节点位置**任一成立；
- 补了 Go 单测覆盖「节点已前进 + 本人待办仍在 + 本人已办查不到」这一格。

**修复状态：已提交 `c6734e4` + `e977bbd`，并在运行 57 上取得 12/12 全通的对照验证。**

### 最核心的成果

**F-P02：会签/多处理人节点上的「时序窗口误判」——一个会让工具把成功报成不确定的真实产品缺陷。**

- 「拿不到正面证据不许判成功」原样保留——新增判据要求**四条必要条件全部成立**，

### 对任务书 §4 提问的回答

> 「是否存在重试机制不足或保守停机判断误报？」

**是，两者都存在，且本轮各定位到一个实例：**

- **保守停机判断误报**：F-P02 就是典型——一次**已经成功**的写在「节点已前进但本人待办快照
  滞后」的时序窗口下被判成「结果待确认」并终局停止。根因是 `ClassifyReread` 漏用了
  「实例当前节点已越过本步节点」这条**已经读到**的正面事实。**已修并验证。**
- **重试机制不足**：F-P05 暴露的是"失败后无法自愈"——孤儿会话让该账号此后**任何**运行都
  启不来，而工具既不能识别「这是我上次重启留下的孤儿」，也没有安全的回收路径，
  只能人工重启执行服务。**已定位，未修。**

需要强调的是：本轮**没有**通过放松门禁来消除误报。F-P02 的修法是**补足被漏用的事实**，
而不是降低判成功的门槛；运行 53 中"末步取不到锚点就放弃判据"的表现，正是门禁仍在正常
兜底的直接证据。
