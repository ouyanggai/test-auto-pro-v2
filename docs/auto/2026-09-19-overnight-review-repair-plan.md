# 2026-09-19 夜间工作审查与修复方案

## 文档目的

本方案审查夜间真实浏览器报告中的三个问题，并把可实施的修复收敛为后续功能切片。本文只做事实核对和方案设计，不修改业务代码，不修改目标平台参考仓库，也不把任何功能推进到 `implementing`。

完成标准：

1. 对“登录协议有改动”给出有源码和真实请求证据的结论，并标出仍需白天复核的部署差异。
2. 恢复加签、取回在动作目录和一键配置中的真实覆盖；取回使用“先形成已办、再取回”的特殊编排，不把它当普通尾动作。
3. 明确固定尾同意的适用边界，给出覆盖全部动作类别的统一编译、门禁、写后核验和动态重绑定模型。
4. 解释目标平台加签导致的代理树变化、节点 ID 变化和画布投影失败原因，明确本项目后端、前端和测试的修复位置。
5. 给出自动测试、真实浏览器验证和人工验收门禁；验证完成后停在 `ready_for_manual`，不代替用户验收。

## 一、夜间结果审查

### 1. 登录协议是否是瞎说

结论：不是瞎说，但“服务端不校验验证码文字”的表述不能直接推广到所有部署环境。

证据链如下：

- 夜间报告 `docs/auto/2026-09-19-zcode-overnight-real-browser-flow-test-report.md` 的问题 #1 记录了浏览器 XHR、curl trace `94b2792d423d0601`、目标源码和三个账号重跑结果。旧登录请求被目标以“用户名错误或密码错误”拒绝，先调用 `getVerifiCode` 后再登录恢复成功。
- 本项目提交 `56b42e3` 在 `internal/adapter/target/client.go` 增加登录前的 `/web/user/api/login/user/getVerifiCode`，读取 `data.flag`，把新鲜 flag 放入登录请求顶层 `sign`。验证码接口失败时在凭证校验前终止，不能带空 sign 继续撞登录端点。
- 目标参考后端 `参考代码/java-serve/rsh-cloud-user-center-api/src/main/java/com/rsh/cloud/user/center/api/service/impl/AccountLoginApiServiceImpl.java` 使用 `requestProtocol.getSign()` 查询 Redis 的 `VERIFICATION`。在 `pro` profile 下还比较 `data.code` 与 Redis 内容；夜间部署的实际行为只证明了 flag/sign 门禁，不能证明所有环境都跳过文字校验。

因此方案结论是：保留 `56b42e3` 的新鲜 sign 适配，白天用目标环境实际 profile 分别验证“只需 flag”和“flag+验证码文字”两种响应。登录协议应作为目标事实登记，不能把一次夜间环境观察写成永久的“服务端不验 code”规则。

白天复核项：

- 同一账号连续两次登录，确认旧 flag 是否必然失效。
- `code` 正确、错误、为空三种组合，确认当前部署的响应和错误分类。
- 登录后首个请求是否仍有 SID 首请求失效或同账号互踢；该行为属于会话事实，不与 sign 协议混为一谈。

### 2. 一键配置排除加签和取回的问题

两个提交分别把夜间失败固化为永久排除：

- `e2553f2` 在 `internal/service/path_action_configuration.go` 直接跳过 `add_sign`。
- `65e2bb5` 直接跳过 `retrieve`。

这与产品约束冲突。`docs/PRODUCT.md` 要求动作目录覆盖加签和取回，F-034 要求按完整候选编译；只有在当前事实、参数、人员、恢复链或动态结构无法安全证明时，才淘汰具体候选并说明原因。动作目录已经有加签的代理可编辑和人员候选门禁，也有取回的已办任务、重复取回、会签和他人处理门禁，因此不能用“夜间一次失败”代替动作能力模型。

夜间失败的真实原因也不是“动作永远不支持”：

- 加签写入成功后，目标实例出现了新的审批节点；原编译场景没有为这个节点生成后续审批步骤，所以在插入节点处路径偏离安全停。
- 取回要求当前用户在该节点已有已办任务。把取回简单排在固定同意前没有已办，把它排在固定同意后实例又已经离开节点，两个位置都可能不可执行。

短期排除可以作为现场止损，但不能作为产品终态。修复后应删除这两个永久 `continue`，改为候选级条件判断和完整编译验证；无法证明时保留“未自动配置 + 节点级原因”，允许人工配置。

## 二、固定尾同意的评估

当前 `internal/engine/scenario/scenario.go` 的固定尾逻辑对普通人工节点是正确的：发起节点尾部生成提交，审批/协同节点在该节点用户动作之后生成同意，驳回、撤回或草稿状态再由编译器生成重新提交。这样能保证用户动作和系统默认流转分离，也符合 `docs/PRODUCT.md` 第 43、47、125 条。

但“所有动作最后固定同意”不成立，原因是动作会改变任务或流程结构：

| 动作类别 | 固定尾同意是否直接适用 | 必须追加的语义 |
| --- | --- | --- |
| 保存草稿、审批暂存 | 适用，但写后必须重读当前待办 | 仍停留在原节点时才能继续尾部同意 |
| 移交、关注/取消关注、催办、转发 | 不能只看尾部顺序 | 按目标作用域读取新的处理人或实例状态；移交后不能继续假设原演员可写 |
| 不同意、撤回、回退 | 不适用为普通尾部动作 | 进入同一主实例的恢复链，重新提交并沿真实路径逐节点同意 |
| 取回 | 不适用 | 必要时先同意形成当前用户已办，再按已办任务执行取回；取回后重新读取当前节点和游标 |
| 加签 | 不适用为原节点尾部动作 | 写入新审批节点，按真实新节点处理人完成独立审批，再回到新代理树继续编排 |

因此保留“普通节点固定尾动作”的概念，但把它改成有条件的系统步骤：只有运行时确认原节点仍有可处理的活动待办、没有待处理的动态插入节点，且前置用户动作的写后核验已完成，才生成或执行该尾动作。固定尾同意不能作为所有动作的统一收尾模板。

## 三、完全适配动作的统一编排模型

### 1. 动作规格

为每个动作建立统一的 `ActionSpec` 语义（可落在现有动作目录/编译器模型中，不新增兼容层）：

- 作用域：发起人、当前待办、已办任务或实例。
- 前置事实：必须读取的实例、节点、待办、已办、代理树、人员和权限。
- 演员：计划账号、当前待办处理人、动作专属接收人或目标目录选定人员。
- 写端点和载荷：继续由 `internal/adapter/target` 作为唯一目标请求出口。
- 写后事实：任务状态、实例节点、代理树、分支、处理人和表单值。
- 结构效果：无变化、游标移动、代理树重建、插入节点、进入恢复链或实例状态变化。
- 重读屏障：写后必须读取哪些事实；读不到或不一致时进入失败/结果待确认，禁止重发。

候选状态分为 `可自动配置`、`仅人工配置`、`当前事实不可用`。一键配置只保存第一类；第二类和第三类都返回具体原因，不再用固定尾动作凑“已配置”。候选是否可用必须经过完整场景模拟和现有 `compilePathActions`，不能只看动作目录的 `enabled`。

### 2. 加签编排

加签按一个会改变代理树的动作组编译：

1. 写前读取当前活动人工待办、可编辑的实例代理树、锚点节点和加签人员策略。
2. 使用目标真实协议构造完整代理树。目标前端 `AddCounterSign.vue` 读取当前实例/模板树，`nodeWrap.vue` 用 `styleType` 和 `flowNodeAuditConfig.flowNodeDetailConfigList` 表示加签节点和人员明细；目标后端 `FlowProxyServiceImpl.saveFlowProxy` 会复制或重建实例私有代理、软删除旧节点、递归保存新树、迁移运行节点引用并在提交后清缓存。
3. 写后按实例当前事实重新读取最新 `flowProxyId` 和整棵代理树，核验全树恰好一个节点包含本次加签人员，不能只相信写响应或旧代理 ID。
4. 以写前当前节点为插入锚点，按稳定结构路径整体重绑定旧节点、边、分支选择、提交分支目标和下一节点处理人；任何无法唯一证明的映射都清空后续放行命令并停机。
5. 从新代理树读取插入节点的真实审批方式、会签人数和实际处理人，生成独立的系统审批步骤。该步骤不冒充原节点固定尾同意；会签按目标人数/全部规则生成必要的物理审批步骤。
6. 插入节点审批完成后再次读取实例和代理树，再继续原编译路径。新节点处理人必须来自目标最新待办事实，不能复用写前演员。

当前仓库已经包含 F-037 对独立插入节点、锚点重绑定和运行画布动态投影的实现，状态为 `ready_for_manual`；本方案要求把夜间报告中的旧失败场景作为人工验收回归，不重复实现一套旁路逻辑。

### 3. 取回编排

取回必须是可重读的特殊动作组，不能作为普通节点动作简单排序：

1. 写前读取当前用户在目标节点的已办任务，确认任务未被取回、未被他人处理，且当前实例仍满足目标取回门禁。
2. 如果没有已办但当前活动待办允许由当前用户同意，则先执行一次独立的“准备同意”物理步骤，写后确认该用户在该节点产生已办任务。已有已办时跳过准备步骤，不能重复同意。
3. 使用刚读取到的已办任务事实调用取回端点；取回前后都只允许一次写请求，响应不明确时终止为结果待确认。
4. 写后重新读取当前节点、待办、已办、流程代理和分支游标。确认实例回到预期节点后，才继续后续用户动作；如果回到的节点或处理人无法证明，停在查看/停止状态。
5. 取回后的固定尾同意只有在新的当前节点重新满足活动待办门禁时才可执行，不能沿用取回前的尾动作计划。

一键配置只有在目标事实允许上述准备同意、取回和回到原节点的完整编译模拟时才自动选择取回。否则仍展示取回动作和阻塞原因，交给人工配置，不把取回从动作目录删除。

### 4. 其它动作和统一安全边界

不同意、撤回、回退继续使用现有恢复链，但每个恢复步骤必须带实际节点、演员和写后重读事实；移交后必须切换到目标返回的实际处理人；转发使用独立实例级容器，不能伪造节点动作。所有动作遵守：单个物理步骤最多一次写请求、响应丢失不自动重试、写后事实不确定进入结果待确认、目标代理树重建时不能继续使用旧 ID。

## 四、加签差异与画布问题的修复边界

### 目标平台事实

- 前端加签从当前实例或模板读取完整代理树，把节点模板提交给 `updateFlowProxy`；节点展示依赖 `styleType`、节点类型和 `flowNodeAuditConfig.flowNodeDetailConfigList`。
- 后端保存不是原地修改旧节点 ID 的简单更新：实例代理可能首次复制为私有代理，后续重建会软删除旧节点、生成新节点 ID、迁移运行引用并清理缓存。
- 因此“加签成功但画布仍显示旧节点”不是目标代理树异常，而是调用方继续使用旧 ID、旧边或新旧 ID 集合并集展示的投影错误。

### 本项目修改位置

- `internal/adapter/target`：只负责目标协议、完整加签代理树载荷、取回载荷和事实读取，不把目标临时 ID暴露成稳定业务键。
- `internal/engine/step`：加签写后读取最新实例代理、验证唯一插入节点、整体应用 `ProxyRemap`；取回动作读取已办并验证游标回归。
- `internal/engine/scenario`：把动态插入节点审批和取回准备同意编译为独立动作组；普通固定尾动作保留条件门禁。
- `internal/service/run_orchestration.go` 及运行详情前端：画布只消费当前实例最新代理树；按稳定结构路径投影计划节点，新增节点使用目标真实 ID 和人员明细；映射不唯一时保留事实卡片、显示原因并禁止放行，不能把旧图和新图直接合并。
- `参考代码/`：只作为目标行为证据，禁止直接修改。若目标环境本身需要后端变更，应单独建立目标平台变更流程，不混入本项目修复提交。

## 五、实施分期与门禁

### 切片 A：动作候选恢复与编译器模型

- 删除一键配置对 `add_sign`、`retrieve` 的永久排除。
- 引入动作规格的前置事实、结构效果和写后重读要求。
- 加签和取回候选逐候选完整编译；不安全时返回节点级原因并保持未配置。
- 先补单元/契约测试，禁止进入真实写动作。

完成标准：现有普通动作行为不变；加签和取回不会因静态黑名单消失；测试能区分“缺候选/缺已办/动态结构不可证明”和“动作不支持”。

### 切片 B：加签动态节点与取回特殊动作组

- 接入加签写后唯一节点核验、锚点重绑定和独立插入节点审批。
- 接入取回的已办预检、必要准备同意、取回后游标复验。
- 所有动态步骤保留运行记录和请求/响应原文，写结果不明确时停在结果待确认。

完成标准：仿真目标树、重复人员、会签人数不足、已办缺失、取回后节点不一致等场景全部安全停；可证明场景能继续使用同一主实例。

### 切片 C：运行画布与真实页面回归

- 用真实加签实例核对目标“查看流程”、工具运行画布、侧栏人员和步骤时间线四方一致。
- 验证加签后的新节点可见、可点击，后续步骤指向新代理树；映射失败时只有查看/停止，没有放行。
- 重跑取回、加签、普通审批、恢复链和并发组合，保留失败实例与日志。

完成后停在 `ready_for_manual`，由用户检查目标平台和本项目页面；未得到明确验收前不标记 `accepted`，也不开始下一功能。

## 六、验证清单

自动验证只运行当前切片相关内容：

- 登录：sign 新鲜度、登录错误分类、不同 profile 的 `code` 校验契约。
- 动作配置：加签/取回候选恢复、完整编译、人员策略、幂等保存和具体阻塞原因。
- 场景编译：普通固定尾同意、加签独立审批、取回准备同意与取回后重绑定的顺序。
- 目标协议：加签完整代理树载荷、取回已办任务载荷、一次写请求和写后核验。
- 代理树：插入锚点、同类型节点、重复路径、旧 ID 未映射和会签节点的确定性重绑定。
- 画布：最新代理树投影、新增节点、人员明细、边和节点状态；映射失败降级且不放行。
- 基础检查：受影响 Go 测试、`go build ./...`、`go vet`、前端类型检查、契约检查和 `git diff --check`。

真实浏览器验收至少覆盖：

1. 登录前后 flag/sign 与目标响应；
2. 一键配置选择加签，目标流程图出现独立加签审批节点，按目标实际处理人完成该节点后继续；
3. 一键配置选择取回，记录“已有已办直接取回”和“先同意再取回”两条路径；
4. 普通同意、不同意恢复、回退恢复、移交和并发运行不受影响；
5. 运行详情刷新后不出现旧节点和新节点重复显示，结构无法证明时明确停机。

## 未决事项

- 目标生产 profile 是否强制校验验证码文字，需要白天实测确认；本方案不把夜间“只校验 flag”扩大为通用协议。
- 加签的竞签/会签完成条件必须以目标最新代理树和待办列表为准，不能固定假设“一人同意”或“全部同意”。
- 取回是否允许当前用户先同意后立即取回，需用目标真实页面和响应确认；若目标部署拒绝该组合，候选应显示明确的“当前部署不可自动编排”而不是静默删除。
- F-037 当前仍等待用户页面验收；本方案将其作为前置门禁，未验收前不扩大到新的实现范围。
