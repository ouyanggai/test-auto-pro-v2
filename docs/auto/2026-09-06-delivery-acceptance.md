# 全自动交付验收与修复任务

## 目标

从收到任务起持续执行到 **2026-09-07 08:55（Asia/Shanghai）**。不要等待人工审核；通过真实网页完成验收，发现问题立即修复、复验并用中文提交。

当前各 F 功能虽然已完成代码和自动测试，但仍不能直接视为可交付：F-019 的真实动作证据有限，F-023 冷启动曾受镜像仓库阻断，运行详情仍有无价值的对账交互和布局问题。本任务以真实用户能否顺利完成流程为最终标准，不以文档状态或测试通过代替验收。

## 已确认的产品调整

### 1. 移除用户侧对账功能

用户不理解也不需要运行详情顶部的“待对账”区域、说明、输入框和人工登记操作，全部移除。

- 服务重启造成运行现场丢失时，不再要求用户填写对账信息。
- 页面给出一句大白话提示后返回运行记录上级页面，让用户重新进入；禁止跳转循环。
- 重新进入后展示已经落库的只读运行记录；无法安全继续的运行明确结束，并引导用户从计划重新运行。
- 不得因移除对账界面而自动继续、重放或重复发送真实写请求。
- 后端可以保留保证安全所必需的内部判定与日志，但不能再把处理责任推给用户；清理不再使用的接口、DTO、前端状态和测试，并同步 PRODUCT、ARCHITECTURE、EXECUTION_PROGRAM、ROADMAP、PROGRESS 与相关功能文档。

### 2. 修复返回入口对齐

运行详情的返回按钮、标题和下方内容区左边界必须对齐。使用同一内容容器、间距变量或布局规则解决，不用针对某个分辨率硬写偏移。实际检查常用桌面宽度、侧栏展开/收起及深浅主题，并顺带核对计划详情、路径配置和运行记录详情的同类返回入口。

### 3. 文案全部说人话

运行和配置页面逐页检查文案。每条提示必须说明“发生了什么、为什么、用户现在能做什么”，删除“态势、洞察、语义、工作区、链路、就绪度”等没有直接操作含义的描述。界面不显示内部 ID、英文状态、字段英文名或技术栈名词，不能让用户面对提示后仍不知道下一步。

## 真实验收样本

从目标平台近期记录中选择：

- 5 个 FormMaking 表单流程；
- 5 个 Vue 自定义表单（`vue_custom`/NoFormFlow）流程。

先按近期实例数量排序，再按最近运行时间排序，选择真实使用较多且当前测试账号可操作的流程。某个候选因权限或目标数据无法完成时，记录原因并换下一个候选，不能把未跑通的候选计入 5 个。

不要提交账号、凭证、目标内部 ID、原始请求正文或敏感业务数据。验收清单只记录业务名称和结果；原始证据放在被 Git 忽略的运行目录。

## 每个样本必须走通的全链路

1. 从“新建计划”开始，验证账号并选择真实流程。
2. 创建计划、选择执行路径，完成历史数据、节点人员、字段权限和动作配置。
3. 检查 FormMaking 或自定义表单真实回显、联动、必填校验、分支字段和保存结果。
4. 运行前检查必须给出明确、可操作的结论。
5. 启动真实运行，完成配置中的全部步骤和动作，不只验证发起。
6. 在运行画布点击每个已执行节点，核对该节点的状态、动作、耗时、请求结果和错误说明。
7. 核对运行列表、运行详情、事件流、最终目标事实和日志引用一致。
8. 刷新页面并重启服务，确认已经落库的记录仍可查看；运行现场丢失时按新的返回上级页面规则处理，不出现对账表单。

## 运行能力覆盖矩阵

每类 5 个流程至少分配为：2 个单步、2 个自动、1 个人工控制。十个样本合计必须真实覆盖：

- 首次写断点、节点断点、动作断点的命中和放行；
- 单步执行、自动连续执行、人工控制；
- 暂停、继续、停止以及重复点击幂等；
- 串行、多路径并行和最大并发限制；
- 至少一个 FormMaking 和一个 Vue 自定义表单执行同一动作两次以上，确认“动作次数/循环”真实生效，记录和目标状态与次数一致；
- 保存草稿、提交、同意及所选流程实际允许的其他动作。某个动作在当前流程不可用时必须显示真实原因，并换可用流程补齐验证，不能伪造通过；
- 运行失败时其他路径不被错误终止，运行信息能从节点直接看到。

每个样本都必须最终至少有一次完整成功运行；为了验证暂停或停止而中断的试跑不能替代完整运行。

## 页面质量要求

- 以现有 Naive UI 和页面结构为基础，不重建第二套画布或详情页。
- 一个区域只保留一个主操作，次要操作合理收纳；禁止按钮、卡片和提示堆砌。
- 信息层级、留白、对齐、字号和状态必须清晰；加载、空白、失败、禁用和完成状态都要可理解。
- 不使用整页遮罩，不只靠颜色表达状态，控制台不得有未处理错误，关键请求不得重复发送。
- 页面可以克制，但必须像可交付产品，不能像组件示例页。

## 执行与修复规则

1. 先读 `AGENTS.md`、`CONTEXT.md`、PRODUCT、ARCHITECTURE、ROADMAP、PROGRESS、EXECUTION_PROGRAM 和相关功能文档，再检查当前代码与提交，禁止重复建设。
2. 按“发现问题 → 定位根因 → 最小修复 → 定向测试/构建 → 浏览器复验 → 中文提交”循环执行，不停下来等用户。
3. 新增测试按类别放入根目录 `test/`；实际运行受影响的 `test/run-fXXX.sh` 和前端构建。
4. 所有提交说明使用中文，只本地提交，不 push；保留用户已有改动，不提交凭证、日志、缓存、依赖或参考源码。
5. 真实写仅使用本机忽略配置中的指定测试账号和流程；每次尝试最多一次写请求，禁止盲目重发、修改目标源码或直接改目标数据库。
6. `rsh-cloud-invest-power-system` 只查看 `GroupApproveManage` 及其直接引用的公共组件。
7. 外部模型或额度不可用时直接自行完成审查，不等待、不反复重试。
