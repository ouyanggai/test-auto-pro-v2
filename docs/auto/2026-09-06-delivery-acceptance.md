## 已确认的产品调整

### 1. 移除用户侧对账功能

用户不理解也不需要运行详情顶部的“待对账”区域、说明、输入框和人工登记操作，全部移除。

- 服务重启造成运行现场丢失时，不再要求用户填写对账信息。
- 页面给出一句大白话提示后返回运行记录上级页面，让用户重新进入；禁止跳转循环。
- 重新进入后展示已经落库的只读运行记录；无法安全继续的运行明确结束，并引导用户从计划重新运行。
- 不得因移除对账界面而自动继续、重放或重复发送真实写请求。
- 后端可以保留保证安全所必需的内部判定与日志，但不能再把处理责任推给用户；清理不再使用的接口、DTO、前端状态和测试，并同步 PRODUCT、ARCHITECTURE、EXECUTION_PROGRAM、ROADMAP、PROGRESS 与相关功能文档。

### 2. 修复返回入口对齐

运行详情的返回按钮、标题和下方内容区左边界必须对齐。使用同一内容容器、间距变量或布局规则解决，不用针对某个分辨率硬写偏移。实际检查常用桌面宽度、侧栏展开/收起及深浅主题，并顺带核对计划详情、路径配置和运行记录详情的同类返回入口。

### 3. 重做运行记录层级并支持删除

- 运行记录列表一行只对应一次计划运行，不把同一次运行的多条路径拆成多行。
- 每条运行记录显示计划、运行方式、整体状态、准确进度、开始/结束时间，并提供删除入口。
- 删除针对整次工具侧运行及其路径、步骤、尝试、事件和控制记录，绝不删除目标平台实例或业务数据。运行中的记录必须先停止再删除；删除前明确提示计划、运行号、路径数量和影响范围，失败不能留下半删状态。
- 点击一条运行先进入“本次运行的执行路径”二级页面，显示本次实际勾选的路径，而不是计划的全部路径。每条路径显示名称、当前状态、当前节点、已完成步骤/总步骤和准确进度。
- 进度必须来自已落库步骤和本次运行冻结的总步骤：完成才是 100%，失败或停止保留实际进度，不按时间估算、不用假进度。
- 点击路径详情进入现有运行面板。运行面板返回二级路径页，二级路径页再返回运行记录列表；三层返回入口和内容区对齐。

### 4. 运行中可以切换自动与单步

- 自动运行可切换为单步，单步也可切换为自动；切换只影响当前路径，多路径运行不能暗中改变其他路径。
- 切换在安全步骤边界生效：已经发出的写请求必须完成核验与落账，不能中途打断、重复写或跳步。
- 界面即时显示当前模式和“将在本步完成后切换”；生效后写入控制事实，刷新后显示一致。
- 原有断点、暂停、停止和人工控制规则继续有效，模式切换不能绕过断点或门禁。
- 所有放行、暂停、停止、模式切换和断点操作都以后端返回的可用命令、当前步骤和控制版本为准，前端不得自行猜测状态。
- 每个控制请求必须幂等且带当前版本：重复点击只能产生一次控制事实；响应丢失时先重读结果，禁止直接重发造成多走一步。
- 反馈严格区分“请求已收到”“将在当前步骤结束后生效”“已经生效”“执行失败”，不能点完按钮只换文案，也不能在后端尚未确认时提前显示成功。
- 状态、按钮、当前节点和右栏必须来自同一次服务端快照；遇到版本过期应刷新并说明实际结果，不能继续操作旧节点。

### 5. 提升运行画布质感与信息准确性

- 重做运行节点卡片的排版、间距、圆角、边框、阴影和状态层级，使节点名、当前状态、动作和耗时自然呈现，不做彩色标签堆砌。
- 未开始、等待、运行中、暂停、完成、失败、停止等状态既有文字也有克制的视觉差异；状态变化平滑但不制造假进度。
- 运行中的卡片必须有细小、连续的动态反馈，例如状态点呼吸、边缘进度光或当前连线的方向流动；动画只表达“仍在处理”，不冒充完成百分比，不让整张卡片跳动。出现、切换、选中、展开和定位动画都要自然衔接，不能卡顿、跳变或突然闪烁。
- 失败节点必须呈现明确错误态和错误摘要。点击后右栏先用大白话说明哪一步失败、为什么、能做什么，再允许展开技术证据。
- 点击卡片必须有明确选中反馈并打开右侧信息。右栏只显示该节点的真实配置和运行事实：动作、执行人、步骤、耗时、请求结果、错误与日志；没有数据时明确写“尚未执行”，不能串到其他节点或猜测。
- 错误详情至少包含失败动作、步骤与阶段、错误分类、发生时间、trace、实际请求/响应摘要、可复制 cURL、日志位置和关联配置。关联配置必须使用本次运行冻结的路径、人员、动作参数、字段权限、模式与断点快照，不能拿后来修改的当前配置冒充当时配置。
- cURL 必须由后端已记录的实际请求生成并与日志同源，前端不得重新拼装；按既有安全规则处理密码、SID、密钥等凭证。证据缺失时明确写出缺哪一项以及原因，不能显示空框或虚构内容。
- 当前节点变化时保留用户缩放，把节点平滑移动到扣除右栏后的舒适观察位置；用户手动移动画布后停止抢夺视口，并提供“回到当前节点”。
- 连线保持真实流程结构，优化线宽、转角、箭头、标签和间距；已走、当前、候选、未走和异常线路清楚但克制，禁止廉价发光、密集虚线和无意义动画。
- 深浅主题、常用桌面宽度和键盘聚焦下都必须可读；动画节奏、缓动和持续时间保持统一，整体交互自然、连贯、丝滑。

### 6. 文案全部说人话

运行和配置页面逐页检查文案。每条提示必须说明“发生了什么、为什么、用户现在能做什么”，删除“态势、洞察、语义、工作区、链路、就绪度”等没有直接操作含义的描述。界面不显示内部 ID、英文状态、字段英文名或技术栈名词，不能让用户面对提示后仍不知道下一步。

## 真实验收样本

从目标平台近期记录中选择：

- 7 个 FormMaking 表单流程；
- 3 个 Vue 自定义表单（`vue_custom`/NoFormFlow）流程。

先按近期实例数量排序，再按最近运行时间排序，选择真实使用较多且当前测试账号可操作的流程。某个候选因权限或目标数据无法完成时，记录原因并换下一个候选，不能把未跑通的候选计入十个有效样本。

不要提交账号、凭证、目标内部 ID、原始请求正文或敏感业务数据。验收清单只记录业务名称和结果；原始证据放在被 Git 忽略的运行目录。

## 每个样本必须走通的全链路

1. 从“新建计划”开始，验证账号并选择真实流程。
2. 创建计划、选择执行路径，完成历史数据、节点人员、字段权限和动作配置。
3. 检查 FormMaking 或自定义表单真实回显、联动、必填校验、分支字段和保存结果。
4. 运行前检查必须给出明确、可操作的结论。
5. 启动真实运行，完成配置中的全部步骤和动作，不只验证发起。
6. 在运行画布点击每个已执行节点，核对动画、状态、动作、耗时和请求结果；至少构造一次可控失败，确认错误卡片、错误详情、cURL、日志和本次运行配置准确对应同一节点。
7. 核对运行列表的一次计划运行汇总、二级执行路径页、运行面板、事件流、最终目标事实和日志引用一致。
8. 刷新页面并重启服务，确认已经落库的记录仍可查看；运行现场丢失时按新的返回上级页面规则处理，不出现对账表单。
9. 使用一条专门的终态试跑验证删除：确认整次运行从列表消失、子路径不可再访问，目标平台实例和业务数据不受影响。

## 运行能力覆盖矩阵

7 个 FormMaking 至少分配为 3 个单步、3 个自动、1 个人工控制；3 个 Vue 自定义表单分别覆盖单步、自动和人工控制。十个样本合计必须真实覆盖：

- 首次写断点、节点断点、动作断点的命中和放行；
- 单步执行、自动连续执行、人工控制；
- 自动切单步、单步切自动，并验证只在安全边界生效；
- 暂停、继续、停止以及重复点击幂等；
- 控制请求成功、延后生效、版本过期、响应丢失和失败时的状态反馈，确认不多走、不漏走、不重复写；
- 串行、多路径并行和最大并发限制；
- 至少一个 FormMaking 和一个 Vue 自定义表单执行同一动作两次以上，确认“动作次数/循环”真实生效，记录和目标状态与次数一致；
- 保存草稿、提交、同意及所选流程实际允许的其他动作。某个动作在当前流程不可用时必须显示真实原因，并换可用流程补齐验证，不能伪造通过；
- 运行失败时其他路径不被错误终止，运行信息能从节点直接看到。

每个样本都必须最终至少有一次完整成功运行；为了验证暂停或停止而中断的试跑不能替代完整运行。

## 页面质量要求

- 以现有 Naive UI 和页面结构为基础，不重建第二套画布或详情页。
- 一个区域只保留一个主操作，次要操作合理收纳；禁止按钮、卡片和提示堆砌。
- 信息层级、留白、对齐、字号和状态必须清晰；加载、空白、失败、禁用和完成状态都要可理解。
- 节点卡片、连线、当前节点定位、点击反馈和右侧详情必须作为一个整体设计，不能只换颜色或加阴影交差。
- 运行中动画自然、连贯、丝滑且不影响阅读；错误态一眼可见，展开后的错误、cURL、日志与运行时配置能够直接用于定位问题。
- 本项目不做“减少动态效果”分支，不添加 `prefers-reduced-motion` 或关闭动画的媒体查询；所有动画直接按统一的丝滑交互标准实现。
- 不使用整页遮罩，不只靠颜色表达状态，控制台不得有未处理错误，关键请求不得重复发送。
- 页面可以克制，但必须像可交付产品，不能像组件示例页。

不要同时铺开全部修改，严格按以下顺序逐块完成：

3. **再改画布**：只在控制状态和诊断数据准确后优化卡片、连线、动画、定位和右栏；重点文件从 `web/src/views/RunDetailView.vue`、`web/src/features/runs/`、`web/src/features/flow-graph/` 开始，后端事实从 `internal/service/run_orchestration.go`、`internal/engine/` 和运行仓储核对。不得只改 CSS 掩盖数据问题。

定位问题时按证据分层：接口数据已错就查服务、执行器和仓储；接口正确但页面错才查前端映射；目标状态与工具记录不一致就按 trace 查 `step.log`、`network.log` 和 cURL。没有证据前不要猜，不要通过加延时、吞错误或重复请求掩盖问题。
