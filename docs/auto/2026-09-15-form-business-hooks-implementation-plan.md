# 表单前置/后置业务处理同步实现方案

## 1. 完成标准

本方案完成的标志是：

1. 对 `GroupApproveManage` 及其直接引用的公共组件完成一次可追溯的业务钩子盘点，明确每个钩子的触发时机、输入、输出、目标接口和失败语义。
2. 工具执行提交、保存草稿、审批暂存、同意、不同意、重新提交和转发时，能够按目标平台顺序执行前置校验/业务处理、目标流程写入、后置业务处理，并把每一步落入运行事实。
3. 钩子只允许调用登记过的目标接口和表单事件，流程名称始终使用工具平台值，不复制目标平台流程名称处理。
4. 前置失败时不发送流程写请求；目标写结果不确定时不执行后置钩子；后置失败时保留目标已发生的事实并将运行标记为“业务处理失败”，禁止回滚或盲目重放。
5. 自动化测试、契约检查和只读集成验证均可执行，真实写动作仍按现有人工验收门禁逐项验证。

## 2. 当前实现与问题边界

现有工具已经能回填历史表单并调用 12 个白名单写端点，但这只覆盖“表单数据 + 流程动作”。目标前端还会在流程写入前后执行业务逻辑：

- 发起页面和审批页面通过 `generateForm.triggerEvent('beforeSubmitAndDraft', context)` 执行自定义业务；无业务场景另触发 `beforeSubmitAndDraftNoBiz`。
- 发起成功后通过 `afterSaveFlowInstance` 执行依赖新流程实例 ID 的业务。
- 审批页面在 `getData()` 校验、`findApprovePermission` 字段权限计算、`getFormData` 回读之后才组装最终请求。
- FormMaking 控件会按 `remoteFunc`/`remoteOption` 获取远程选项，并同步真实值、显示值、虚拟字段和名称伴生字段。
- 附件先上传，再由 `saveBatchFile` 按实例或任务关系绑定；转发会合并 `dynamicParam` 和业务关联数据。
- 审批意见、下一节点人员选择、自动审批信息字段和业务模块回调会改变最终业务数据。

本方案只研究和实现上述业务处理；流程名称解析、展示和命名规则明确排除，统一沿用工具平台的流程名称。

## 3. 已核实的目标行为清单

| 阶段 | 目标代码证据 | 工具需要同步的行为 |
|---|---|---|
| 表单装载 | `ExamineDialog.vue`/`EnterpriseExamineDialog.vue` 的 `getFormDataById`、`getFormData` | 读取原始 JSON；完成远程选项绑定后再形成有效表单数据；失败不得覆盖已有有效值 |
| 字段权限 | `EnterpriseExamineDialog.vue:findApprovePermission` 调用 `/web/flowProxy/getFlowNodePower`，并合并已审批节点隐藏字段 | 按当前任务、已审批节点和重发场景计算可编辑/隐藏字段；字段权限缺失时阻塞 |
| 提交前校验 | `handleBeforeSubmit` 调用 `approveForm.validate`，随后调用 `generateForm.getData()` | 先执行控件校验，再执行业务前置钩子；校验错误不得产生写请求 |
| 业务前置 | `EnterpriseExamineOpinion.vue`、`Submitted/components/FlowDialog.vue` 的 `beforeSubmitAndDraft` 与 `beforeSubmitAndDraftNoBiz` | 事件脚本串行执行；支持脚本返回新载荷/拒绝；记录脚本名、输入摘要和输出摘要 |
| 流程写入 | `Api.qualityManage.submitTask` `/flowInstanceApi/audit` 及现有动作目录 | 继续使用现有一次写约束、会话重登和写后核验；钩子不得自行调用流程写端点 |
| 发起后业务 | `FlowDialog.vue` 的 `afterSaveFlowInstance` | 仅在流程写入确定成功且拿到新实例 ID 后执行；每个回调独立记录，失败不回滚流程 |
| 表单后处理 | `getFormData` 回读及 `auto_audit_info_*` 衍生字段处理 | 以目标当前实例为权威，保留目标生成的审批人、状态、时间和意见格式 |
| 附件 | `getAttachmentList`、`bindBatchFileByIds`、`saveBatchFile` | 上传与关系绑定分开记账；实例级、任务级关系不可混用；绑定失败明确影响范围 |
| 转发 | `flowTypeMixin.js` 的 `dynamicParam` 合并及 `flowInstanceBizRelevanceList` | 业务参数和日志/附言按目标顺序合并；辅助实例独立登记，不能改写主实例游标 |
| 审批人员 | `getNodeList`、`run_node_choose` 分支 | 发送前读取实时待办和候选人员；显式选择缺失时阻塞，不能回退到登录账号 |

## 4. 建议的运行时架构

新增“业务钩子编排层”，不把脚本散落到各动作适配器：

```text
有效表单数据构建
  -> HookPlanResolver（按表单模板/节点/动作解析已登记钩子）
  -> PreHookRunner（校验、远程选项、业务前置、附件准备）
  -> TargetActionWriter（现有动作目录与一次写约束）
  -> PostHookRunner（实例回读、附件绑定、afterSaveFlowInstance、业务回调）
  -> FactProjector（运行详情、日志、辅助实例、最终表单）
```

### 4.1 钩子契约

每个钩子登记为不可变定义：`hook_key`、触发阶段、适用动作、适用表单类型、目标端点/事件名、输入字段白名单、输出字段白名单、幂等键、超时、重试策略、成功判据和失败分类。运行快照保存定义版本，禁止运行时读取变化后的模板脚本。

### 4.2 执行上下文

上下文只提供：工具流程名称、目标 `flowInstanceId`/`jobTaskId`（若已证明存在）、真实节点标识、当前完整表单数据、节点可编辑字段、附件关系、审批意见、下一节点人员和业务关联。禁止传入 SID、密码、任意 URL、未登记字段和不透明 `nodeKey`。

### 4.3 结果状态

统一使用 `not_started`、`running`、`succeeded`、`blocked`、`failed`、`uncertain`。前置钩子失败属于确定失败；目标写入 `uncertain` 时后置钩子不运行；后置钩子失败记录“目标流程已改变，业务回调未完成”，仅允许用户从计划重新发起。

## 5. 分阶段实施任务

### 阶段 A：盘点与证据固化

1. 建立 `docs/TARGET_SEMANTICS.md` 新条目，记录事件触发顺序、远程选项绑定、权限合并、附件关系和发起后回调。
2. 为每个端点补齐请求/响应样例、成功判据、业务副作用和参考仓库 HEAD；无法实测的标为“源码证据”，不得登记可运行动作。
3. 生成 `HookCatalog`，把现有 `ActionKey` 与钩子阶段建立一对多关系。

### 阶段 B：有效表单数据与前置链

1. 抽取 `BuildEffectiveFormData`：历史数据、路径补丁、远程选项最终值、虚拟字段和名称伴生字段在内存中一次合并。
2. 实现 `PreHookRunner`：先权限检查，再表单校验，再执行 `beforeSubmitAndDraft`/`beforeSubmitAndDraftNoBiz`；任何一步失败立即停止。
3. 附件上传仅作为准备步骤，关系绑定延后到目标写入确定成功后；所有网络调用进入请求明细。
4. 对脚本返回载荷做字段白名单和 JSON 数字保真校验，拒绝脚本偷偷修改流程标识或未授权字段。

### 阶段 C：写入后的业务链

1. 目标写入确定成功后重新读取实例和任务事实，确认实例 ID、节点游标和状态。
2. 发起动作执行 `afterSaveFlowInstance`；审批动作执行目标要求的表单回读、自动审批信息投影和任务级附件绑定。
3. 转发动作取得辅助实例 ID 后执行辅助实例只读确认并写入独立事件；主实例只按主写入结果推进。
4. 后置步骤失败不重发流程写请求，支持从同一运行查看失败原因和已完成步骤。

### 阶段 D：前端/运行详情接入

1. 在现有运行画布中显示“前置业务处理”“目标流程动作”“后置业务处理”三个阶段及真实中文结果。
2. 展示钩子名称、业务影响、目标请求耗时、失败下一步和是否发送过流程写请求；不展示脚本正文、SID 或内部节点键。
3. 运行准备页按动作快照检查钩子证据；未登记钩子只能提醒或阻塞，不能因同端点已有证据自动解锁。

### 阶段 E：验证与交接

1. 纯逻辑测试覆盖顺序、短路、幂等键、字段权限、远程选项冲突、附件关系和不确定写保护。
2. 契约测试检查钩子端点白名单、流程名称未被目标逻辑覆盖、请求不含 SID/密码/`batchCode`/临时节点键。
3. 只读集成测试验证表单回读、权限和远程选项；真实写按用户指定测试流程逐动作验证前置与后置副作用。
4. 更新 `docs/PROGRESS.md`、对应功能文档和人工验收清单，状态停在 `ready_for_manual`。

## 6. 测试目录规划

新增测试必须分类放在根目录 `test/`：

- `test/unit/backend/form_hooks/`：钩子解析、执行顺序、字段白名单、状态机和 JSON 保真。
- `test/integration/form_hooks/`：目标只读权限、远程选项、实例回读、附件关系和转发辅助实例。
- `test/contracts/form_hooks/`：端点白名单、事件名、流程名称隔离、敏感字段和一次写约束。
- `test/run-form-hooks.sh`：只运行本方案相关测试并输出证据摘要。

## 7. 风险与处理原则

- 目标脚本可能依赖浏览器 DOM 或登录态：先判断能否转为登记的 HTTP 业务调用；不能证明协议时阻塞，不执行猜测实现。
- 远程选项随时间变化：保存选项快照和解析依据，值/显示值无法唯一对应时发送前阻塞。
- 后置回调可能已产生业务副作用：每个回调必须有幂等键和只读确认；失败只记录事实，不做补偿性重复调用。
- 目标版本漂移：语义证据与参考 HEAD 不一致时自动标记需复核，禁止沿用旧协议。
- 一次运行包含多条路径时，钩子上下文必须绑定路径运行 ID；在多路径能力落地前不得共享实例或钩子现场。

## 8. 人工验收步骤

1. 选择包含远程下拉、字段权限和附件的表单，确认提交前业务处理完成后才发流程写请求。
2. 制造前置校验失败，确认没有流程写请求且运行显示阻塞原因。
3. 执行发起并检查 `afterSaveFlowInstance` 业务结果、实例回读和附件绑定关系。
4. 执行审批暂存、同意、不同意和重新提交，确认各自前置/后置链不同且审批暂存不推进任务。
5. 执行转发，确认辅助实例独立展示，主实例节点游标未被伪造推进。
6. 模拟目标写响应丢失，确认后置钩子未运行，运行进入“结果待确认”且无重试入口。

## 9. 明确不在本方案内

- 流程名称的解析、拼装、兼容和展示规则。
- 修改目标平台源码、权限配置、数据库结构或基础设施。
- 为未取得真实证据的业务钩子伪造成功状态。
- 自动补偿、自动重放或以工具账号替换目标实际操作人。
