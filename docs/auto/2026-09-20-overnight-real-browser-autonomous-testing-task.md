- **按顺序往下遍历**：从目标系统可发起的业务流程列表中，按顺序依次测试各流程模板（如员工请假单、报销审批、投资立项、风控等）。
- **流程计划创建**：
  - 每个流程模板在页面上点击「新建计划」；
  - 绑定登录人「骆蒙恩」；
  - 计划名称命名规范：`夜测_[流程名]_[时间戳]`。

### 2. 路径生成与配置要求
- **每个流程最多测试 12 条执行路径**：
  - 点击「生成路径」后，若解析出的合法完整路径不足 12 条，则取全量有效路径；若超过 12 条，按序号严格截取前 12 条；
  - **全部先选自动模式**：动作编排配置选择「每节点随机一个动作」（充分激发同意、加签、退回、驳回、取回等组合分支）。
  - **历史数据注入**：在基础表单数据弹窗中，选取真实历史实例数据自动回放填充。

### 3. 执行模式覆盖（并发与串行矩阵）
针对每个流程的 12 条（或实际 N 条）执行路径，随机且均衡地测试以下维度：
- **串行执行**：路径逐条按序放行，重点验证状态流转与事实回读的线性一致性；
- **并发执行**：随机选取一定数量的路径（例如 2~4 条并发），在就绪度检查弹窗中配置并发放行，重点压测与暴露：
  - 目标系统分布式锁/代理更新版本竞态；
  - 本地 SQLite 会话连接竞争；
  - 动态加签插入节点的原子性；
  - 会话多任务流转冲突。

## 四、遇到问题时的自主深度思考框架（拒绝硬修）

当你（Agent）在执行过程中遇到任何阻断或报错时，**按照以下步骤进行深度归因与通用设计**：

```
[现象捕获] 页面/执行器报错 -> 提取事实、日志上下文、请求报文与目标响应
      ↓
[本质定性] 是「目标平台鉴权/时延特性」还是「本地执行器/状态树缺陷」？
      ↓
[根因深挖] 为什么旧逻辑会失败？
  ├── 是否存在异步时序竞态？（如目标已办尚未生成，但执行器立刻核对）
  ├── 是否存在代理树克隆后 ID 失效？（如 updateFlowProxy 后的锚点平移）
  ├── 是否存在表单字段权限与原生 JS 渲染时差？
  └── 是否存在重试机制不足或保守停机判断误报？
      ↓
[通用化修复] 
  ├── 严禁写死特定的流程 ID、节点名称或正则特判；
  ├── 在抽象层（如 Analyzer、Executor、Driver 或 Orchestrator）补齐状态机容错、幂等保护或自适应重试；
  └── 编写/更新对应的 Go 单测或契约测试，确保不破坏既有场景。
      ↓
[验证与原子提交]
  ├── 本地 go test + npm run typecheck 验证；
  ├── 重新在浏览器上重跑该路径，验证问题彻底消除；
  └── 中文提交：清晰说明「背景、深层根因、通用方案与验证事实」。
```
