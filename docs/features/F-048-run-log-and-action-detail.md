# F-048 事件总览与动作接口详情

- 状态：ready_for_manual
- 批准依据：用户要求继续改进日志、状态、目标错误原话和动作详情弹窗，明确授权直接提交；随后明确“事件流看整个流程，动作详情看局部接口”。
- 业务依据：当前目标平台 `GroupApproveManage/components/flowTypeMixin.js` 的转发及附言保存链路，以及本项目当前运行源码。不把历史方案当成业务依据。

## 用户要看到什么

事件流是整个流程的观察窗口：到了哪个节点，谁做了什么，是否继续，哪里出错，错误原话是什么。只读导航和目标自动跳过也不能在这里凭空消失。

动作详情只看打开的这一个动作：调用了哪些接口，先后顺序是什么，每个接口花了多久，目标返回了什么。一次转发的主请求和附言保存应各出现一条；同节点的同意、催办等其他动作不能混进来。

## 从当前源码发现的问题

1. 打开一个动作，前端却把同一节点的所有动作接口一起列出；随后又列一遍执行器轨迹，既串记录又容易看成重复发送。
2. runtime 使用页面运行号作为运行 ID，独立转发循环又没有完整日志归属，导致请求可能落到别的目录或缺少动作身份。
3. 日志记的是“第几步”，后台却把它与数据库的步骤主键直接比较。两者不同就漏掉真实请求；此前的测试把两者碰巧写成同一个数，没测出这个问题。
4. 网络摘要会压平换行、替换空格，并把目标消息截到 200 个字符，用户看不到完整原话。
5. 空列表被直接解释成“没有请求”，没有区分日志缺失、读取中断、归属缺失和真实为空；轮转后的早期动作记录也会被漏读。
6. 接口计时在收到响应头时就结束，慢响应正文没有计入；无错误说明的失败读取又可能被摘要显示为“读取成功”。
7. 导航和目标自动跳过没有经过写后核验状态，原来的事件登记分支会略过它们；事件颜色还使用了当前代码不再产生的事件名。

## 本次改动边界

- 把真实运行 ID、路径、步骤、尝试、目录与阶段接回 runtime 转发请求。装载归为“准备”，动作请求归为“执行”，同一请求的会话刷新重放保持同一阶段。
- 用目标已登记的端点分类读取和写入，补足转发附言的写入分类。HTTP 方法本身不是分类依据。
- 通过真实步骤记录把数据库主键换成日志里的步骤序号，按步骤和尝试精确归属；删除按时间猜归属的逻辑。
- 读取当前及现有保留的轮转日志，用真实开始时刻排列接口。完整读取响应正文后再结束传输计时。
- 完整保存并还原目标 message，分别展示 HTTP 状态、明确的业务结论和业务码；不能把 HTTP 200 当成业务成功。
- 动作详情只消费当前动作。用尝试内的请求序号、方法和端点关联轨迹与网络记录；同一笔只显示一次，真实重试的每次物理传输都保留。
- 只有轨迹而没有传输日志时，说明已观察到的事实，耗时显示未知。本地拦截、转发中止、目标拒绝和日志缺失分别说清楚。
- 事件流记录步骤、节点、实际执行人与结果原话；补上只读步骤的观察事件。观察记录失败只报告，不改变已有执行结论。
- 弹窗按“动作结果 → 当前动作的接口流转 → 返回说明 → 折叠日志入口”排列，接收人保持可见，长文本可以换行和滚动。

本次不改目标平台源码、请求正文、动作与写入顺序、处理人、一次写约束、核验、SID 刷新、安全重试和运行结论。不增加数据库表、迁移、状态机或新的日志基础设施，不扩大公开正文查看权限。

## 人工核对步骤

1. 打开包含多个节点和动作的运行，查看事件流：节点、步序、执行人和停止原因是否清楚；导航和自动跳过是否留下记录。
2. 同一节点分别打开两个动作：每个弹窗只显示对应动作的接口。对一次转发核对主请求与附言保存各出现一次、接收人正确、顺序正确。
3. 对照同一路径的 `network.log` 和 `curl.log`，核对方法、接口、耗时、HTTP 状态、业务结果和追踪号；真实重试应保留每次传输。
4. 查看一次目标拒绝或附言失败的动作，核对事件流与动作详情能读到完整原话；主请求成功而附言失败时，页面不能声称完全没有写入。
5. 查看日志缺失或不完整的动作，确认页面说明证据不足。缩窄浏览器窗口，检查长错误、接口和日志内容可完整读完，复制入口可用。
