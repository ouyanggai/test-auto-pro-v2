## 这次解决什么

现在工具发出转发主请求就能报成功，但目标页面还会给新生成的转发实例保存当前附言。少做第二笔请求，别人收到的流程就可能少了这次填写的话。

“勾选附言”决定历史附言怎么带过去，不决定这次附言要不要保存。即使不勾选、这次附言为空，目标页面也会保存。不能把两个含义混在一起。

业务依据只取目标源码，不采用以前文档中的业务结论：

- `参考代码/rsh-flow-components/src/views/GroupApproveManage/components/flowTypeMixin.js:127-282`：原生 `confirmTranspond` 读取当前表单、历史附言和流程日志，构造转发数据；主请求成功后调用 `handleSubmitPostscript(res.data.id)`。
- 同文件 `:285-299`：保存当前 `approveForm.approveMessage`，使用新的附言 ID 和主请求返回的新实例 ID；空附言拦截代码已被注释。
- 同文件 `:147-199、218-266`：首次和再次转发的数据、原发名称及业务关联分别处理，不能用工具自行拼的小载荷代替。

## 准备怎么做

1. 转发进入现有原生运行时，调用目标列表组件的 `confirmTranspond`。接收人、当前意见和历史勾选项使用本步配置；表单、历史记录、名称和业务关联由目标组件按源码组织。
2. 保持当前待办、实际处理人和实例级转发的输入约束，不改变别的动作。执行服务不可用就写前停止，不能偷偷改走只发主请求的旧路径。
3. 第一笔必须拿到明确成功和新实例 ID，才允许第二笔。第二笔必须指向这个新实例；每笔只放行一次。不能因为附言失败或连接断开再转发一次。
4. 两笔都有完整成功响应才报整步成功。主请求已成功、附言明确失败或没有发出时，如实报“转发已创建，附言未完成”；附言响应丢失或结果未知时进入待确认。保留新实例引用和完整请求证据，不能报成没有写入。

## 本轮完成标准

- 有、没有 `fuyan` 都必须保存当前附言；非空和空文本都按原生输入处理。
