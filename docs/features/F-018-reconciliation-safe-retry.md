# F-018 对账与安全重试

- 状态：awaiting_approval
- 产品依据：`docs/PRODUCT.md` 产品原则第 6 条（写操作结果不明确时先核对真实状态，禁止盲目重发）、第 2 条（工具问题与目标平台问题必须分开说明，暂时无法判断时按工具问题处理）、第 4 条（产生运行记录后固化），以及「明确不做」中的「跳过失败写动作」
- 架构依据：`docs/ARCHITECTURE.md` 的「系统边界」（`internal/engine` 承载执行状态机，目标请求只能由 `internal/adapter/target` 发出）
- 纲领依据：`docs/EXECUTION_PROGRAM.md` 第 4.1 节 `internal/engine/reconcile` 包边界（不自动重发写请求）、第 4.4 节写结果不确定与安全重试、第 6.2 节 `recovery.log`、第 6.4 节 `error_class`、第 7.1 与 7.2 节 `run_step_attempts` 的对账结论/恢复动作/是否重放三列、第 7.4 节失败分类、第 9 节 F-018 行、第 10 节写端点白名单纪律
- 语义依据：`docs/TARGET_SEMANTICS.md` 第 1 节错误语义（三值判定规则、前置拒绝清单、乐观锁提示）、第 2 节幂等与重复提交（2.1 目标平台没有幂等键、2.2 `batchCode` 禁令、2.3 两道可能拦住重复写的防线、2.4 跨存储非原子导致的部分生效、2.5 待实测结论与重复写探针清单）
- 计划确认时间：2026-09-05（本次按用户要求补齐计划）
- 前置条件：F-016（`待对账`状态、`verdict` 三值判定、运行记录六张表、七阶段）与 F-017（运行控制、`control.log`、暂停原因区）必须已实施完成并由用户明确验收。本切片是 F-016 留下的那个缺口的唯一出路。

## 目标

让停在`待对账`的路径运行有且只有一条合法出路，而这条出路由只读对账的结论决定，不由用户猜、也不由工具赌。

## 为什么这是最危险的一个切片

目标平台没有幂等键（`docs/TARGET_SEMANTICS.md` 第 2.1 节，源码可证），一次盲目重发就是目标平台上一条真实的双写数据。F-016 因此把重发这条路彻底堵死，代价是不确定写只能停在`待对账`不动。本切片要把这条路重新打开一条缝，缝的宽度必须由证据决定：

- 只有当重读事实**在每一个维度上都证明写没有发生**时才允许重放。任一维度读不到、读不全、互相矛盾，都归为仍无法判定，不重放。
- 跨存储非原子的部分生效（第 2.4 节：审批端点在乐观锁检查之前已写入 Mongo 表单数据且不受该事务约束）必须被识别为独立形状，且映射到不重放。重放会把表单数据再写一次。
- 对账过程本身只允许读。`internal/engine/reconcile` 包不得引用任何写端点，这一条用测试锁定，不靠自觉。

## 单一用户结果

一条路径运行因写结果不确定停在`待对账`。工具自动做一次只读对账，然后在界面上给出一句中文结论、逐条判断依据（实例状态、当前节点、当前待办、已办记录、动作痕迹各自读到了什么）、以及**唯一一个**可执行的后续动作：

- 判定上一次写已生效：唯一动作是「确认并前进到下一步」。
- 判定上一次写未生效：唯一动作是「重放这一步」。重放是一次新的尝试，重新走完整七阶段，包含门禁复验。
- 仍无法判定：不提供任何前进或重放入口，只提供「记录人工核对结论并结束本路径运行」，让用户把他在目标平台上亲眼看到的事实登记为人工结论事实。

用户在任何时候都不会看到「重试」和「继续」两个按钮让他二选一。对账依据、结论和最终决定全部写 `recovery.log` 并落 `run_step_attempts`，可在 code-server 里逐行核对。

## 范围

### 包含

- `internal/engine/reconcile` 包：纯只读对账。输入是上一次尝试的写意图与响应事实、以及重读到的目标事实；输出是三值结论、唯一合法后续动作、逐维度依据清单与中文说明。
- 强证据规则：判定"未生效"必须五个维度同时成立（实例状态未变、当前节点未变、当前待办仍是原待办、已办记录无该动作痕迹、动作痕迹无本次写的迹象）。任一维度缺失或矛盾即降级为仍无法判定。
- 部分生效形状：表单数据已变但流程未推进（第 2.4 节）作为独立识别结果，结论固定为仍无法判定，不允许重放，并在界面明说"表单数据可能已经写进去了"。
- 重放的安全边界：重放前必须重新对账（不能沿用旧结论）；重放作为新的一次尝试记录（`attempt` 递增）；重放必须重新通过 `gate`；一次尝试仍然最多一次写请求；重放次数上限走配置（默认 1 次），超限固定进入仍无法判定。
- 自动对账与对账失败：进入`待对账`后执行器自动做一次对账（只读，安全）；对账因目标抖动失败时按 F-016 的有界重试与退避处理，仍失败则如实说明"暂时无法对账"，保持`待对账`并提供「重新对账」入口（只读，可以给）。
- 崩溃恢复的衔接：F-016 把重启后处于`运行中`与`核验中`的路径运行一律置为`待对账`。本切片让这批路径运行第一次真正有出路，走同一套对账逻辑，不为崩溃单独开一条路径。
- `recovery.log` 写入器（纲领第 6.2 节，F-013 已把它归属本切片）：对账输入、逐维度判断、结论、依据、最终决定、是否重放逐行可查，字段语义沿用 V1 已验证形态，行格式与关联键与 `step.log`、`control.log` 一致。
- `run_step_attempts` 的对账结论、恢复动作、是否重放三列真实写入（列由 F-016 建），以及对应的 `run_events` 中文标签事件。
- 人工结论事实：用户登记他在目标平台上核对到的实例状态与当前节点，作为 append-only 事实落库，路径运行随之进入终态。人工结论不覆盖任何机器判定，两者并存可回放。
- 失败分类对齐（纲领第 7.4 与 6.4 节）：对账后确定失败的路径运行按`目标拒绝`落分类；工具侧对账缺陷按`工具缺陷`落分类，同一件事在界面与日志里同名。
- 界面：`待对账`区域给一句结论、逐维度依据、唯一动作按钮、日志入口。落在 F-016 与 F-017 已有的运行画布与侧栏上，不新建页面。

### 不包含

- 写端点白名单扩张。仍只有 `/web/flowInstanceApi/submit` 与 `/flowInstanceApi/audit`；重放用的是原步骤自己的端点，不新增端点。
- 动作全集、恢复步骤与导航步骤的真实执行。属 F-019。
- 多路径调度与定时启动。属 F-020。一次运行仍只跑一条路径。
- 运行记录分析视图与事件流时间线。属 F-021。
- 自动重发、后台静默重试、失败自动跳过。前两条与产品原则第 6 条冲突，第三条产品明确不做。
- 修改 F-014 的三值判定规则与 F-016 的七阶段判据。本切片只在`待对账`之后接一段只读判断。
- 让对账去写目标平台，包括"用一次只读探针试探"以外的任何请求。

## 设计要点

### 三结论三动作，一一对应

| 对账结论 | 唯一合法后续动作 | 路径运行状态 |
| --- | --- | --- |
| 已生效 | 确认并前进到下一步 | 回到`运行中`，步骤游标前进 |
| 未生效 | 重放这一步（新尝试，重走七阶段） | 回到`运行中`，步骤游标不动 |
| 仍无法判定 | 只能登记人工核对结论并结束 | 保持`待对账`，登记后进入终态 |

一个结论只对应一个动作，这是纲领第 4.4 节的原话，也是本切片界面设计的唯一约束。界面不得在同一时刻渲染两个前进类按钮。

### 为什么"仍无法判定"给的是登记而不是选择

纲领要求这种情况"要求人工确认，不给第二个按钮"。本切片把人工确认落地为**登记用户看到的事实**，而不是让用户替工具选"算成功还是算失败"：

- 用户填写他在目标平台上看到的实例状态与当前节点，工具把它作为人工结论事实 INSERT 落库，并结束本路径运行。
- 要继续跑就新建一次运行（计划已固化，产品原则第 4 条）。这样工具永远不会在没有证据的情况下继续对同一个真实实例发写请求。
- 这一条是取舍，写进「未决与需要用户裁决的事项」。如果用户希望登记"已生效"后能继续跑完剩下的步骤，改动不大，但必须接受"继续的依据是人的口述而不是机器证据"。

### 强证据规则

判"未生效"是本切片唯一会导致再次真实写的分支，所以它的门槛最高：

| 维度 | 判"未生效"要求 |
| --- | --- |
| 实例状态 | 读到且与写之前一致 |
| 当前节点 | 读到且与写之前一致 |
| 当前待办 | 读到且仍是写之前那一条 |
| 已办记录 | 读到且不含本次动作 |
| 动作痕迹 | 读到且无本次写的迹象 |

五个维度全部成立才判未生效。任一维度读不到、超时、为空或与其它维度矛盾，一律降级为仍无法判定。降级理由逐条写进 `recovery.log`，不允许只写一句"无法判定"。

### 部分生效必须单独识别

`docs/TARGET_SEMANTICS.md` 第 2.4 节已勘定：审批端点在乐观锁检查之前就把表单数据写进了 Mongo，且不受该事务约束。因此存在"表单数据已变、流程未推进"的真实形状。

- 对账识别到这个形状时，结论固定为仍无法判定，绝不判未生效。
- 界面必须明说"表单数据可能已经写进去了，重放会再写一次"，让用户理解为什么工具不给重放。
- 这条规则由对照测试锁定，不允许后续改动把它优化掉。

### 重放不是重发

重放是一次新的尝试，走的是完整流程，不是把上一次的请求再发一遍：

- 重新对账 -> 重新 `plan` -> 重新 `gate`（门禁此刻不通过就停止）-> 重新 `prepare`（重新解析演员与会话）-> `submit` 一次 -> `verify` -> `settle`。
- `attempt` 递增，新的 `trace_id` 与 `curl_trace_id`，`run_step_attempts` 增一行，`is_replay` 为真。
- 重放次数上限走配置，默认 1。用完仍不确定就固定停在仍无法判定，不给第二次。
- 重放全过程受 F-017 的断点与控制约束：单步模式下重放同样需要用户放行。

### 对账只读，用测试锁定

- `internal/engine/reconcile` 不得导入任何发写请求的入口；契约测试断言该包的依赖集合里没有写端点常量与写方法。
- 对账过程中发出的目标请求全部是读，动态录制断言实际请求集合与写端点白名单交集为空。
- 这一条与 F-012 建立、F-016 改造为白名单的零写入断言体系是同一套机制，不另造。

### 日志与记录

- `recovery.log` 与 `step.log`、`control.log` 同目录同格式，关联键至少含 `run_id`、`path_run_id`、`step_id`、`attempt`、`phase`、`trace_id`。
- 对账的每一维度判断各一行，结论一行，最终决定一行。事后要能只看这个文件复盘"为什么当时不给重放"。
- 对账结论与状态变化同事务落库，事件行同事务追加（纲领第 7.1 节）。
- 迁移：`run_step_attempts` 的对账三列由 F-016 建立，正常情况下本切片不需要迁移。确需补列时取编号 `028`，不复用编号，并在状态记录写明补了什么。

## 接口与记录约束

- 对账输入只接受上一次尝试已经落库的写意图、传输阶段事实、响应初判和目标只读事实；函数不得接受目标写客户端、凭证或浏览器提交的“继续/重试”选择。
- 领域结论固定为 `effective`（已生效）、`not_effective`（未生效）、`indeterminate`（仍无法判定）。每个结论必须带五个维度的证据状态、中文依据和可执行动作；缺失字段不得被默认值填成“未生效”。
- 合法恢复动作固定为 `advance`、`replay`、`manual_end`、`reconcile_again`。其中 `replay` 只能由 `not_effective` 产生，`reconcile_again` 只在对账读取失败时出现，其他组合一律拒绝。
- 重放接口必须带当前 `path_run_id`、`step_id`、上一次 `attempt` 和幂等键。服务端在同一事务内重新核对路径状态、重放次数上限和当前租约，重复请求只能返回第一次决定，不能产生第二条写尝试。
- `run_step_attempts`、`run_events`、人工结论事实只追加不覆盖；聚合状态变化与事件追加在同一事务完成。若需要新增人工结论表，迁移编号使用 `028`，不得复用已有编号。
- 对账读取不得调用 `/web/flowInstanceApi/submit`、`/flowInstanceApi/audit` 或动作目录中任何写操作；目标请求白名单契约必须断言对账请求集合与写端点集合交集为空。

## 详细执行任务

每个任务完成后独立验证并使用中文提交说明；未获批准前只维护本计划，不实现代码。

### T01：对账领域契约与纯判定器

在 `internal/engine/reconcile` 建立输入、五维证据、部分生效标记、三值结论、恢复动作和中文说明类型。实现纯函数：五项证据全部明确未变才得出 `not_effective`；任一缺失、超时、矛盾、部分生效或未知响应均得出 `indeterminate`；已生效只在五维读数与写意图一致且响应组合满足 F-014 判定时成立。纯函数不做 IO，不持有目标客户端，不改变运行状态。

### T02：只读事实收集与部分生效识别

在目标适配层增加对账所需的实例状态、当前节点、当前待办、已办记录、动作痕迹和表单变化读取聚合。每个维度保留“读到/为空/错误/冲突”事实；表单已变化但流程未推进时返回独立的 `partial_effect`，不得把它压成“明确未变”。对账请求走只读会话入口和 F-016 的有界退避，禁止复用写调用的重放入口。

### T03：对账服务与唯一恢复动作

实现进入`待对账`后的自动对账、重读失败后的「重新对账」以及三种结论对应的唯一动作。动作执行前再次读取并校验当前路径运行状态、租约、步骤游标和重放次数；`advance` 只推进一次游标，`replay` 创建递增 `attempt` 的新尝试并重新走七阶段，`manual_end` 只登记人工事实并结束路径。任何重复放行、过期版本或动作不匹配返回当前真实状态，不发写请求。

### T04：运行记录、人工结论与事务边界

把对账结论、恢复动作、是否重放、部分生效说明和失败分类写入 `run_step_attempts`，并追加对应中文 `run_events`。新增人工核对事实的最小模型（实例状态、当前节点、说明、登记人和时间）；人工事实与机器判定并存，不能更新或覆盖机器判定。对账结论、聚合状态和事件必须同事务提交，失败回滚后不留下半份恢复记录。

### T05：`recovery.log` 与双向日志引用

复用 F-013 运行目录和日志作用域新增 `recovery.log` 写入器。每个维度一行，结论、最终决定、是否重放和失败原因各一行；行中必须带 `run_id`、`path_run_id`、`step_id`、`attempt`、`phase`、`trace_id` 与日志行号。运行记录保存相对路径、行号和 trace 引用，日志反向带运行键，保证两边可互查。

### T06：恢复 API 与错误语义

新增只读对账触发、恢复动作和人工结论登记接口；接口响应只返回中文业务文案、不透明键、依据清单和当前可用的唯一动作。参数错误、路径状态过期、目标读取失败、工具存储失败和目标拒绝分别映射稳定错误码，统一通过现有失败响应与日志同源。任何接口不得提供并列的“继续”和“重试”按钮语义。

### T07：运行画布待对账工作区

在 F-016/F-017 已有运行画布与侧栏上增加`待对账`区域：显示一句结论、五维依据、部分生效警告、日志入口和唯一动作。`not_effective` 只显示“重放这一步”，`effective` 只显示“确认并前进到下一步”，`indeterminate` 只显示人工事实登记表；对账失败只显示“重新对账”。提交中不整页遮罩，动作完成后以服务端重读结果刷新。

### T08：测试、白名单与真实安全证据

新增 `test/unit/backend/reconcile/` 覆盖五维证据矩阵、缺失/冲突/部分生效和唯一动作约束；新增真实 MySQL 集成用例覆盖 append-only、事务回滚、人工事实和重放次数；新增目标只读录制用例与 `test/contracts/f018/`，断言对账无写端点、一次重放最多一次写请求、重放前必重新对账。真实写验证只使用用户指定的可污染账号和流程，账号值不进入仓库；汇总入口 `test/run-f018.sh` 禁止静默跳过。

## 人工验收

1. 在一条因响应丢失而停在`待对账`的运行上，确认页面先展示自动对账进度，完成后只有一个与结论对应的动作按钮。
2. 构造“已生效”事实：确认页面显示实例状态、当前节点、当前待办、已办记录和动作痕迹的逐条依据，点击“确认并前进到下一步”只推进一次。
3. 构造五维均未变化且读数完整的事实：确认页面只显示“重放这一步”；执行后看到 `attempt` 递增、重新经过门禁和七阶段，且目标只收到一次写请求。
4. 构造表单已变化但流程未推进的部分生效事实：确认页面明确提示表单可能已经写入，不出现重放按钮，只能登记人工核对结论并结束路径。
5. 在目标短暂不可读时确认对账按配置退避并在预算耗尽后显示“暂时无法对账”，可点击“重新对账”，不会直接出现重放。
6. 打开 `recovery.log`，逐行核对五维依据、结论、最终决定、是否重放、运行键、步骤键和行号，并从运行详情跳回对应日志位置。
7. 重复点击同一恢复动作或使用过期页面提交，确认服务返回当前真实状态，不多出运行尝试、事件或目标写请求。
8. 在项目根执行 `./test/run-f018.sh`，确认输出包含只读白名单、真实 MySQL 和无跳过用例结果。
