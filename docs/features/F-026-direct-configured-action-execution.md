# F-026 状态感知的动作循环编排

- 状态：ready_for_manual（2026-09-10 自动验证完成，等待用户按“两次草稿”和“不同意 ×2”人工验收）

## 总结

完整替换现有“配置动作原序直执行”方案。当前执行器只插入单个恢复动作，没有理解恢复后的路径游标，属于实现缺陷。

完成标准：

- 连续两次保存草稿编译为“保存草稿 → 保存草稿 → 固定尾动作重新提交”，不提前重提、不创建第二实例。
- “不同意 ×2”能够两次真实执行，并在每次不同意后重提、逐节点同意回到原节点。
- 配置动作保持用户顺序；系统只补充执行这些动作必需的准备、恢复和导航。
- 默认提交、默认同意固定在节点末尾并单独等待人工放行。
- 恢复过程不再被误判为路径偏离；真实分支偏离仍立即停止。

## 关键改动

- 配置界面使用已有 `base` 契约展示不可删除、不可拖动、不可重复的固定尾动作：
  - 发起节点：默认提交；前序动作产生草稿、驳回或撤回实例时，运行时显示并调用“重新提交”。
  - 审批/协同节点：默认同意，明确提示“同意后将进入下一节点，所以始终最后执行”。
  - 提交和同意从可配置动作下拉中移除。

- 将场景编译器改为基于“实例状态 + 当前节点游标 + 已办/待办事实”的状态编译器：
  - 保存草稿可连续执行，直到固定提交时才根据实例状态选择提交或重新提交。
  - 不同意后生成“重新提交 → 沿已选路径逐个人工节点同意 → 返回原节点”的完整恢复链。
  - 撤回同样从发起节点重提并重走到原目标节点。
  - 回退后从真实前驱节点逐步处理并返回原节点。
  - 取回前没有可取回已办时，先同意产生已办，再执行取回；重复取回重复生成该循环。
  - 暂存、加签、移交、催办、转发、关注等不离开节点的动作不插入无关恢复。
  - 条件、并行、空节点等系统节点仅做只读导航确认；经过人工节点必须发出真实同意写操作。

- 配置校验分级：
  - 仅伪造动作、错误作用域、节点不属于路径、缺少必填人工配置、选定路径上不存在可生成的恢复链等结构问题阻止保存。
  - 重复动作、运行时演员变化、实时待办变化等保存为非阻断提醒，允许启动后按目标事实裁决。
  - `ActionConfigurationIssue.Blocking=false` 的问题进入运行前提醒，不再触发“动作顺序无法恢复”。

- 人工控制按“动作组”放行：
  - 一次放行执行一个配置动作及其必要的前置/后置恢复链。
  - 例如第一次放行“不同意”后，自动完成重提和前驱节点同意，回到目标节点后停在第二次“不同意”之前。
  - 固定提交/同意属于独立动作组，仍单独等待放行。
  - 每个内部写步骤继续独立重读事实、落运行记录并遵守一次写约束；失败、结果不确定、真实路径偏离或用户停止时立即在安全步骤边界停止。
  - 人工恢复组内部不响应普通断点；单步模式仍可逐个查看内部物理步骤，自动模式保持连续运行。

## 接口与数据

- `CompiledActionStep` 增加：
  - `ReleaseGroup`：标识同一次人工放行包含的物理步骤。
  - `ReleaseRequired`：标识动作组的首个步骤。
  - 新步骤来源 `system_default`，区分固定尾动作、用户动作、系统恢复和系统导航。
- 编译场景和运行详情返回动作组及内部步骤，运行面板按组展示恢复原因和当前内部步骤。
- 现有放行接口和请求体不变；服务端根据动作组决定人工模式的执行边界。
- 不修改数据库结构；动作组信息继续存入现有 `compiled_steps` JSON。
- 使用新编译器保留原用户动作、人员和表单数据，重新编译 `oyg测试1003/路径1`；已开始的历史运行不改写。
