## 目标

让每条执行路径拥有一个可判定的成功断言，并在启动之前给出一句用户能直接照做的中文结论：这条路径现在能不能跑；不能跑的，逐条说清为什么，并且每条都能点进具体路径的具体位置去改。

本切片不启动运行、不创建运行记录、不发任何目标写请求。它是 F-016 第一次真实写的前置门槛：先有可判定的成功标准和可信的启动前结论，再谈执行。

## 为什么现在做这一项

- F-014 已经把「一次写请求的结果」变成可编码的三值判定，但「一条路径整体算不算成功」还没有任何判据。没有它，F-016 跑完最后一步也说不出结论。
- 当前只有 `model.IsExecutionPathRunnable`：只看路径节点配置与数据两个状态，返回一个布尔值，没有原因、没有定位、也不复验编译场景、人员解析和路径拓扑。用户看到的只会是「不能运行」，不知道改哪里。
- 纲领已经写明 F-019 之前执行器只允许执行已验证过的动作子集，其余动作必须在运行准备阶段直接阻塞。这条纪律没有落点，F-016 就只能靠实施者自觉。
- F-014 记录了四条部署依赖与读取行为变化（待办列表不再带实例运行态字段、终态实例不再返回当前处理人、流程图详情改走无 Redis 链路、`auditWay` 迁移前可能仍是数字）。断言判定所依赖的事实必须避开这些坑，这一步正是把它们变成明确约束的地方。

## 单一用户结果

用户为一条路径选定成功断言：从这条路径真实经过的结束节点里选一个，配上目标平台真实存在的期望状态；该结束节点在这条路径上会到达多次时，必须指定第几次到达。

保存后回到计划的路径列表，用户看到一句中文结论：要么「这 3 条路径可以启动」，要么「2 条可以启动，1 条被阻塞」并逐条列出阻塞原因，例如「历史业务数据未就绪」「成功断言引用的结束节点已不在当前真实路径上」「本路径包含尚未验证可执行的动作」。每条阻塞项都可点击，直接落到那条路径的对应配置面板。

启动按钮、运行模式选择、断点与运行记录都不在本切片。

## 设计要点

### 成功断言的三个字段

| 字段 | 取值来源 | 约束 |
| --- | --- | --- |
| 结束节点 | 该路径已保存的真实线路与真实流程树中类型为结束的节点（`internal/analyzer/flow_graph.go` 已识别 `end` 类型节点） | 只能从候选里选；候选为空时给中文原因并阻塞，不允许自由输入节点键 |
| 期望状态 | 目标平台真实实例状态：`await_sent` 待发、`draft` 草稿、`run` 运行中、`withdraw` 撤销、`termination` 终止、`abandon` 废弃、`rejected` 驳回、`end` 完结（证据：`FlowInstanceStatusEnum`） | 界面显示目标自己的中文标签，不自造状态、不合并同义状态 |
| 第几次到达 | 结束节点在本路径上的出现次数 | 出现次数为 1 时不填；大于 1 时必填且不得越界 |

一条路径只配一个成功断言，这是纲领第 7.4 节的硬约束，不做多断言、不做表达式。

### 断言判定的三值

判定发生在 F-016 的事实重读之后，本切片只定规则与实现：

| 结论 | 条件 | 后续（F-016 执行） |
| --- | --- | --- |
| 成立 | 事实重读显示实例已到达配置的结束节点且实例状态等于期望状态，到达次数满足配置 | 路径运行结果为成功 |
| 不成立 | 事实重读显示实例已进入终态但结束节点或状态与配置不符 | 路径运行失败，失败原因必须写明是断言不成立，不是执行出错 |
| 无法判定 | 事实读不到、自相矛盾，或实例仍未进入终态 | 不算成立也不算执行出错，停下并要求人工确认 |

「无法判定」不得被后续切片合并进「不成立」。这与 F-014 的兜底同一条底线：拿不准就停。

### 事实投影的硬约束

来自 F-014 的记录，直接写成判定输入的约束：

- 实例状态与当前节点只能读实例本身。待办列表在 `taskStatus=pending` 时不再查询流程实例，返回记录不带实例运行态字段。
- 不依赖终态实例的当前处理人字段，目标已改为只对运行态实例解析当前处理人。
- 不把 `auditWay` 作为断言事实的输入。F-014 已实测当前部署返回的是字符串编码名（`20260828` 迁移已执行），但它属于流程配置而不是运行事实，断言判定不读它，也不为它写死数字兼容分支。
- 判定只用目标事实，不用工具侧推断补齐缺失字段；字段缺失就是「无法判定」。
- 会话失效不一定伴随 HTTP 401：F-014 实测真实响应是 HTTP 200 加 `code=RESP401`。事实重读因会话失效而失败时按「无法判定」处理，不得当成实例未到达终态。

### 运行准备的结论结构

一个计划一句总结论，加逐条路径明细。每条阻塞项复用既有的 `model.PathConfigAffectedItem`（`kind`/`name`/`reason`）形状，另加可点击定位所需的路径标识与目标面板锚点。

| 阻塞来源 | 判断依据 | 说明 |
| --- | --- | --- |
| 节点配置未完成 | `ExecutionPath.ConfigurationStatus != configured` | 复用既有状态，不重算 |
| 历史业务数据未就绪 | `ExecutionPath.DataStatus != ready` | 复用既有状态 |
| 配置已记录的问题 | `test_execution_path_configs.issues` | 原样透出，不改写文案 |
| 成功断言缺失 | 无断言记录 | 本切片新增 |
| 成功断言失效 | 结束节点已不在当前真实路径上、期望状态不在目标真实取值内、到达序号越界 | 只读复验，不自动修正 |
| 编译场景为空 | `compiled_steps` 为空 | 不静默放行 |
| 动作尚未验证可执行 | 路径动作不在 F-016 允许执行的已验证子集内 | 纲领第 9 节明确要求直接阻塞，不做静默降级 |
| 人员解析不唯一 | 人员策略复验解析不出唯一真实处理人 | 复用 F-012 的人员校验，只读复验 |
| 路径拓扑已变 | 路径与当前真实流程结构复验不一致 | 目标结构变化必须挡住启动 |
| 语义条目待实测 | `docs/TARGET_SEMANTICS.md` 中本路径动作涉及条目仍为待实测 | 把 F-014 的成果接进门禁 |

仅提醒、不阻塞的两类：目标部署差异（`auditWay` 迁移状态一类）与计划已固化的只读提示。提醒与阻塞在界面上必须分开，不允许把提醒混成阻塞。

### 不改动的边界

- 不改 `model.IsExecutionPathRunnable` 的调用方语义之外的东西：本切片把它替换为带原因的运行准备结论，旧布尔判断在同一改动内删除，不保留兼容层。
- 不改 F-014 的 `internal/engine/verdict`。写结果三值与断言三值是两件事，不合并。
- 不新增 `NewHandlerWith...` 构造重载，沿用 F-013 已确立的包装方式。
