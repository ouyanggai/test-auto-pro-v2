## 一、用户结果与本次完成标准

用户可以在目标平台当前事实可证明的前提下配置并执行加签、取回及其后续普通动作；登录协议按实际部署 profile 分类；加签导致代理树重建时，运行场景、运行画布和目标流程结构保持一致；取回使用已办任务和回到原节点的特殊动作组；任何无法证明的事实都在写入前或写入后明确阻塞，不盲目重发、不复用旧节点 ID、不把失败说成成功。

本功能整体完成必须满足：

- [ ] 登录前获取新鲜 `flag`，登录请求携带顶层 `sign`；实际部署的验证码文字校验按 profile 登记，错误分类和会话失效分类不混淆。
- [ ] 动作目录对所有用户动作提供统一的作用域、前置事实、演员、端点、载荷、写后事实、结构效果和重读屏障；候选只有在完整编译通过时才可自动保存。
- [ ] 加签和取回不再被静态黑名单删除；不满足事实、人员、参数、恢复链或动态结构条件时保留具体节点原因并维持未配置。
- [ ] 普通节点固定尾同意仅在当前待办、动态步骤和写后核验均满足时执行；不同意、撤回、回退、取回、加签、移交、转发等动作不被套用错误尾动作。
- [ ] 取回形成“已办预检/必要准备同意 → 取回 → 当前节点与游标复验”的独立动作组；每个物理步骤最多一次写请求，写结果不确定立即终止。
- [ ] 加签使用完整代理树协议，写后确认唯一插入节点，按锚点整体重绑定；插入节点的审批方式、人数和实际处理人来自最新目标事实，不能复用写前演员。
- [ ] 运行详情和画布只消费实例最新代理树；旧 ID 和新 ID 不做并集展示，映射不唯一时只保留查看/停止，不提供放行。
- [ ] 所有自动测试、契约测试、构建、静态检查和真实浏览器验收证据完成；完成后状态停在 `ready_for_manual`，不自动标记 `accepted`。

本方案是一个待批准的完整修复切片，下面的 T01-T09 是实施顺序和原子交付任务，不是未经批准就自动启动的后续功能。

## 四、详细实施任务

### T01 目标部署登录协议核实

**目标。** 保留新鲜 `flag/sign` 适配，消除“所有部署都不校验验证码文字”的错误假设，并把登录失败、验证码接口失败、会话失效和网络失败分到正确类别。

**代码边界。** `internal/adapter/target/client.go`、登录错误类型和测试；必要时更新 `docs/TARGET_SEMANTICS.md`，不修改目标源码。

**实施步骤。**

1. 将登录协议拆成三段事实：验证码接口是否成功、登录请求是否携带本次 `flag`、目标是否要求 `data.code` 与 Redis 值一致。
2. 保持 `getVerifiCode` 失败时在凭证校验前终止；禁止空 `sign` 继续请求登录。
3. 删除或改写把“服务端不校验验证码文字”写死在代码注释、错误文案或测试名称中的表述；代码只记录当前配置/profile 的实际结论。
4. 登录错误保留目标原始 `code/message`；`RESP401`、`AUTH_401` 和 SID 失效仍按会话错误处理，不误报为密码错误。
5. 增加本地 HTTP 契约测试：旧 flag、重复 flag、正确 code、错误 code、空 code、验证码接口 4xx/业务失败和登录响应缺 SID。
6. 白天目标环境复核同一账号两次登录、三种 code 组合和登录后首个请求；证据只写入语义文档和未包含凭证的 trace 摘要。

**完成条件。** 本地测试能区分协议拒绝和网络/会话错误；目标环境结论明确标注 profile；不存在空 sign 登录请求；未引入凭证或固定账号。

**阻断条件。** 验证码接口返回格式不稳定、profile 无法确认、旧 flag 仍被接受或错误分类无法区分时，T01 停在 `needs_input`，不得继续以猜测推进真实动作。

### T02 统一动作规格与候选状态

**目标。** 让动作目录成为一套可编译、可执行、可核验的语义来源，而不是仅用 `enabled` 决定一键配置。

**代码边界。** `internal/model/action_orchestration.go`、`internal/model/path_config.go`、`internal/engine/actioncatalog/catalog.go`、`internal/service/path_action_configuration.go`、`internal/engine/scenario/scenario.go` 及对应 `test/unit/backend/action_orchestration`、`test/contracts`。

**动作规格字段。** 优先扩展现有目录模型，不新增兼容模型。每个动作必须可得到：

- `scope`：发起人、当前待办、已办任务或实例；
- 前置事实：实例状态、当前节点、待办/已办、代理树、人员和权限；
- 演员来源：计划账号、目标当前处理人、动作专属接收人；
- 目标端点和参数来源：继续由 `internal/adapter/target` 唯一构造；
- 写后事实：实例状态、当前节点、任务 ID、处理人、代理树、分支和表单值；
- `structureEffect`：无变化、游标移动、代理树重建、插入节点、恢复链或辅助实例；
- `reloadRequirements`：写后必须重读的事实集合；
- 候选状态：`auto_configurable`、`manual_only`、`fact_unavailable`，以及面向用户的原因。

**实施步骤。**

1. 对保存草稿、暂存、提交、重提、加签、移交、同意、不同意、回退、取回、撤回、催办、转发、关注/取消关注逐项填齐规格。
2. 将静态目录禁用、人员缺失、错误作用域、节点不在路径、恢复链不可生成、动态结构不可证明区分为不同原因。
3. 一键配置只接受 `auto_configurable` 且完整 `compilePathActions` 通过的候选；`manual_only` 和 `fact_unavailable` 保留在报告中，不删除目录项。
4. 候选保存必须幂等：相同计划、路径、节点和动作键不会产生重复记录；人工配置事实不能被随机策略覆盖。
5. 为每个动作补目录投影、候选状态、作用域和完整编译的单测与契约测试。

**完成条件。** 加签/取回在目录完整时可进入候选；缺人员、缺已办、结构无法证明时返回节点级原因；普通动作排序和既有配置不改变。

### T03 固定尾同意条件化

**目标。** 保留普通人工节点的固定尾同意，但只在写后事实证明当前节点仍可离开时执行。

**代码边界。** `internal/engine/scenario/scenario.go` 的 `emitFixedTaskTail`、用户动作组和恢复链；`internal/engine/step/executor.go` 的预览门禁、写后核验和下一步判断；`internal/engine/control/control.go` 的动作组放行。

**规则。**

- 保存草稿和审批暂存：写后仍在原节点且待办事实可读，才允许尾动作；连续保存草稿不能中间重提。
- 移交：写后必须使用目标返回的新处理人，原演员不可继续假设为可写人。
- 关注、取消关注、催办、转发：属于实例作用域，不因位于人工节点动作列表末尾而生成同意。
- 不同意、撤回、回退：进入恢复链，不直接生成普通尾同意。
- 取回：由 T04 动作组在取回后重新判断，不沿用取回前尾动作。
- 加签：由 T05 插入节点动作组处理，不对原节点直接套尾同意。

**实施步骤。**

1. 为固定尾步骤增加“活动待办仍属于该节点、无待处理动态组、前序写后核验已确认”的门禁事实。
2. 编译器保留系统步骤，但把条件写入 `Precondition` 和 `ReleaseGroup`，禁止在保存时伪造目标事实。
3. 执行器预览阶段重新读取实时事实；不满足时返回阻塞，不发写请求。
4. 控制层只允许当前动作组放行；组内每个物理步骤单独读、写、核验和落账。
5. 为普通、恢复、实例级、加签和取回动作分别补顺序断言，验证固定尾不会错误出现。

**完成条件。** 普通审批仍能生成正确尾同意；动态动作不会误用尾同意；固定尾条件不满足时明确显示节点、动作和下一步，命令集合为空。

### T04 取回特殊动作组

**目标。** 实现方案规定的“先形成已办，再取回”语义，并确保取回前后都以目标实时事实为准。

**代码边界。** `internal/engine/scenario/scenario.go`、`internal/engine/step/executor.go`、`internal/engine/control/control.go`、`internal/adapter/target/client.go`、`internal/adapter/target/client_fact_reads.go`、`internal/adapter/target/write_actions.go`。

**动作组结构。**

1. `retrieve_precheck`：读取当前实例、当前节点、当前用户已办任务，确认任务未取回、未被他人处理、后继未产生不可逆处理。
2. `retrieve_prepare_approve`：没有已办时，只有目标当前待办明确允许当前用户同意，才生成独立准备同意步骤；写后必须确认同一节点产生当前用户已办任务。已有已办时不生成此步骤。
3. `retrieve_write`：使用刚核实的已办 `jobTaskId` 调用 `/web/flowInstanceApi/retrieveProcess`；每次物理步骤最多一次写请求。
4. `retrieve_postcheck`：重新读取实例状态、当前节点、待办、已办、代理树和分支游标；确认回到预期节点后才生成后续步骤。
5. `retrieve_tail_gate`：取回后重新判断固定尾同意，不复用取回前预览；节点或处理人无法唯一证明时停在查看/停止。

**实施步骤。**

1. 将本地 `completed` 状态改为编译提示，运行时以 `FindDoneTaskOnNode`、精确待办和当前处理人事实决定是否需要准备同意。
2. 已办任务必须带实例、节点、批次和执行人；缺任一关键标识时在发送前阻塞。
3. 准备同意成功后重读已办列表，必须唯一命中当前用户在原节点的新已办；失败、重复或他人任务均不进入取回写入。
4. 取回写后使用新待办任务 ID 与写前已办任务 ID对照；节点相同但任务号变化应判定为前进，任务号未变化应按目标事实判定未生效。
5. 写响应丢失或核验读取失败进入结果待确认/重新核验状态，禁止自动重放取回或准备同意。
6. 将准备同意、取回和后续尾动作分别落独立步骤、尝试、请求轨迹和原始响应。

**安全停机场景。** 无已办且当前待办不属于当前用户、已办已被取回、后继已处理、取回后回到错误节点、目标任务重复、目标事实不可读、准备同意写结果不确定、取回写结果不确定。

**完成条件。** 仿真能覆盖“已有已办直接取回”和“先同意再取回”；每种不安全场景均零重复写；可证明场景继续使用同一主实例。

### T05 加签动态节点动作组

**目标。** 在复用 F-037 已有代理树写入和重绑定的基础上，把目标新增审批节点作为独立运行步骤处理。

**代码边界。** `internal/adapter/target/add_sign_proxy.go`、`internal/adapter/target/client_fact_reads.go`、`internal/engine/step/executor.go`、`internal/engine/step/proxy_remap.go`、`internal/engine/control/control.go`、`internal/engine/scenario/scenario.go`。

**实施步骤。**

1. 写前读取当前活动人工待办、实例完整代理原文、可编辑锚点和加签人员策略；锚点缺失或重复时不构造写载荷。
2. 使用目标真实 `updateFlowProxy` 协议插入加签审批节点，保留未知字段、字段权限和锚点原后继；新节点不伪造稳定 ID。
3. 写后按实例最新 `flowProxyId` 重新读取完整代理树，确认恰好一个节点以 `personnel` 明细包含全部加签人员；零个或多个命中均停机。
4. 使用锚点和稳定结构路径应用 `ProxyRemap`，整体更新节点、边、分支选择、下一节点处理人和运行现场；禁止旧/新 ID 并集。
5. 从最新代理树和待办读取插入节点的审批方式、会签人数和当前实际处理人，编译独立系统审批步骤。竞签按一人完成条件，串签/会签按目标返回规则，不固定假设人数。
6. 插入节点每个实际处理人单独执行、单独重读和落账；节点完成后再读取实例与代理树，重新定位原编译路径的后续步骤。
7. 动态节点处理人缺失、代理树结构无法唯一映射或会签完成条件不明时，清空后续放行命令，只保留事实卡片、日志和停止入口。

**完成条件。** 代理树重建后新节点可见、可点击、可执行；旧节点不会重复显示；插入节点处理人来自最新待办；映射失败不提供放行。

### T06 其它动作安全边界复核

**目标。** 让所有动作遵守相同的作用域、演员、一次写请求和写后事实约束。

**动作分组。**

- 不同意、撤回、回退：检查同一主实例恢复链、真实前驱、处理人和写后状态；恢复步骤不得创建第二主实例。
- 移交：写前确认当前待办和目标接收人，写后读取目标实际处理人；原处理人不得继续执行后续动作。
- 转发：使用独立实例级容器，记录辅助实例引用；主实例节点和游标不得被伪造为已推进。
- 催办、关注、取消关注：只改变实例级事实，不生成节点尾同意。
- 保存草稿、暂存：写后确认仍在原实例/任务范围；不把暂存当提交、不把发起草稿当审批暂存。

**代码边界。** `internal/engine/actioncatalog/catalog.go`、`internal/engine/scenario/scenario.go`、`internal/engine/step/executor.go`、`internal/adapter/target/write_actions.go` 以及 F-019/F-026 相关测试。

**完成条件。** 每个动作都有唯一目标端点、演员来源、写后重读和失败分类；响应不明确不重发；动作作用域错误在保存或发送前阻塞。

### T07 运行事实、日志和画布收口

**目标。** 确保动作组、代理树变化和用户可见运行详情使用同一套事实。

**实施步骤。**

1. 每个物理步骤写入唯一 `RunStep`/`RunStepAttempt`，记录动作组、来源、节点、演员、尝试号、trace、请求阶段、写后事实和判定依据。
2. 继续使用现有日志原文策略记录完整请求/响应；详情页只展示摘要和折叠排查入口，不公开 SID、密码和完整正文。
3. 运行详情优先读取实例最新代理树；静态计划图、动态节点、人员明细和已落账步骤按稳定结构路径投影。
4. 映射失败保留静态图和事实卡片，明确“结构无法唯一绑定”，清空继续/放行命令；不得猜名称、边或处理人。
5. 画布、节点侧栏、步骤时间线和任务列表使用同一终态投影：运行中、阻塞、确定失败、结果待确认和完成不得各自推断。
6. 对 F-037 已有动态投影增加刷新、加签后重建、插入节点可点击、旧节点不重复和嵌套条件回归检查；无需重写已完成的映射算法。

**完成条件。** 刷新前后运行画布结构一致；步骤只出现一次；动态结构不可证明时没有任何放行入口；日志能从业务计划、路径和运行事实定位到请求。

### T08 自动验证与真实浏览器验证

**自动测试分类。**

- 登录：新鲜 flag、sign 注入、旧 flag、code 三种组合、错误分类和会话失效。
- 动作目录：全部动作规格、作用域、人员策略、候选状态、幂等保存和具体阻塞原因。
- 场景编译：普通固定尾、恢复链、取回准备同意/取回/回归、加签插入节点审批、会签/竞签。
- 目标协议：完整代理树载荷、取回已办任务载荷、参数白名单、一次写和写后读取。
- 执行器：零写入失败、写结果不确定、核验失败、任务 ID 变化、演员变化和重启恢复。
- 代理树：锚点缺失、重复人员、重复命中、同类型节点、旧 ID 未映射、嵌套条件和新节点边。
- 画布：最新代理树投影、人员明细、动态节点、结构失败降级和命令集合为空。

**本地命令。** 只运行当前切片相关测试，并记录实际命令与结果：

```text
go test ./internal/adapter/target ./internal/engine/actioncatalog ./internal/engine/scenario ./internal/engine/step ./internal/engine/control ./internal/service
go test ./test/unit/backend/action_orchestration ./test/unit/backend/executor ./test/unit/backend/target
go test ./test/contracts/...
go build ./...
go vet ./...
pnpm --dir web run typecheck
git diff --check
```

**真实浏览器验收顺序。**

1. 先做登录协议矩阵，保存 flag/sign 与目标响应 trace；不记录凭证。
2. 验证一键配置加签：目标流程图出现独立加签节点，按目标实际处理人完成后继续原路径。
3. 验证取回已有已办直接取回；分别保存取回前后任务号、当前节点和请求次数。
4. 验证取回先准备同意再取回；确认准备同意和取回各自最多一次写请求，取回后回到预期节点。
5. 回归普通同意、不同意恢复、回退恢复、移交、转发和并发运行。
6. 刷新运行详情，确认没有旧节点/新节点重复；结构无法证明时确认只有查看/停止。

真实验证必须由用户从页面选择真实账号、流程和实例；不使用固定 ID、固定账号、自动浏览器脚本或预置动作台。
