## 1. 背景与问题

### 1.1 首轮问题（已解决）

报告中心整页是硬编码假数据：KPI、时延分位、计划质量列表、根因分类、审计流水全部写死在前端常量里，`/reports` 路由不调用任何后端接口。用户无法从报告中心看到任何真实运行事实。

首轮已把它改成只读「总分总」三级聚合：L0 首页全局计数与计划表 + 专业指标；L1 计划详情；L2 路径详情与运行实例耗时分解；L3 复用现有运行详情。事实来源是 MySQL 运行记录六表（迁移 026）与运行目录 `network.log`（F-030 传输层 `duration_s`），分位用 `github.com/montanaflynn/stats`，图表用 ECharts + `vue-echarts`，执行器墙钟耗时按用户裁决补真实计时并落库（迁移 036）。

### 1.2 本轮问题（2026-10-10 用户人工验收反馈）

用户在浏览器验收时给出五点反馈，逐条定位如下：

1. **加载速度非常慢。** 根因是每次报告读取都按路径运行串行读盘、逐行建对象，并对每条路径运行各发一次数据库查询：
   - `ReportCenterService.interfaceStatsByPathRun` 对范围内每条路径运行调用一次 `PathRunInterfaceStats`，内部 `ListRunAttempts` 一条 SQL（典型 N+1）；
   - 每条路径运行还要完整扫两遍日志：`attemptTimeWindows` 读 `step.log` 推导尝试窗口，再读 `network.log` 归属请求；
   - 归属过程对每个日志行 `parseLogLine` 建一个 `map[string]string`，再构造 DTO、排序、填充摘要，这些都是报告聚合用不到的开销。
   - 实测证据（当前工作区 `logs/`）：`network.log` 83 个文件共 66.9 MB / 118,919 行，按现有口径串行解析耗时 **1.13 s**（纯 IO 拷贝仅 31 ms）；`step.log` 66 个文件共 **131.4 MB**，同等量级。也就是说一次首页加载要串行扫约 200 MB 日志并做十万余次 map 分配；运行目录更多、或触达 200 条采样上限时还会更慢。
2. **参数和层级不合理。** `ReportMetricsPanel` 在 L0/L1/L2 三级原样复用，每级都渲染 5 张 KPI 卡 + 4 张图；用户从计划下钻到路径再下钻到运行实例，看到的是大量重复内容，一层里分不清「这一级该看什么」。
3. **缺少名词解释。** 成功率、一次通过率（FPY）、路径覆盖度、分位、执行器耗时、工具端编排耗时、阻塞、结果待确认等术语对非专业测试人员不友好，页面只在卡片下方写了一行小字，没有可随时查看的解释入口。
4. **排版需要优化。** 计数卡与指标卡混排、L2 运行实例表 12 列挤在一行、结果分布只有饼图没有数值、没有横向滚动与粘性表头、结果列没有状态标识。
5. **数据显示要细致权威。** 指标卡只有比率没有分子分母，分位没有样本数，全页没有统计截止时间，用户无法判断「这个数是怎么来的、覆盖了多少样本、新不新」。

**本轮目标（单一用户结果）**：报告中心在保持只读、不造数的前提下，做到「打开就快、每级只看本级的一等信息、每个名词随手可查、每个数字说得清来历」。

## 2. 「总分总」信息结构（本轮收敛后）

三级仍然保留（用户已确认的总分总钻取路径不变），但**每一级只放自己的一等信息**，同一套指标不再三级重复。

### L0 报告中心首页（总）

- **计划情况（第一级统计）**：全局计数卡（计划总数、有运行记录的计划、累计运行次数、累计路径运行、进行中运行）+ 计划维度表（点击行进 L1）。表列保持：计划、运行次数、路径运行、成功率、结果分布、路径覆盖度、最近运行。
- **专业指标（全局范围）**：完整指标面板——3 张比率卡（成功率/一次通过率/路径覆盖度，各带分子分母）+ 接口调用卡 + 重试统计卡；步骤耗时分位与目标接口耗时分位两张图（各带样本数与数值明细）；结果与停机分类占比、失败分类分布两张图，**图下必须同时给数值明细表**（名称、次数、占比），不能只有图形。面板右上角显示「数据截至 {generatedAt}」，触达采样上限时给出既有提示。

### L1 计划详情（分）

- 计划头部：计划名、账号、流程来源、目标对象、路径总数、累计运行次数。
- **计划核心指标摘要**（不再渲染整套指标面板）：3 张比率卡 + 一行时延口径（步骤耗时 / 目标接口耗时的 P50·P90·P95·均值与样本数）+ 一行接口与重试（调用总数/读/写、重试次数与涉及运行数）。图表、分布占比不属于本级一等信息，回到 L0 看。
- **各执行路径指标表（主体）**：序号、路径名称、运行次数、成功率、平均步骤数、平均步骤耗时、平均接口耗时、最近结果；点击行进 L2。

### L2 路径详情（分）

- 路径头部：路径序号/名称、配置状态、运行次数。
- **路径核心指标摘要**：与 L1 同构、范围收敛到本路径。
- **运行实例列表（主体）**：该路径每次运行实例一行——运行号与启动时间（合并）、结果（状态标签）、步骤数、步骤总耗时、接口耗时（含写请求耗时）、执行器耗时、工具端编排耗时、接口调用数、目标实例号、操作（查看明细进 L3）。列做合并与右对齐，外包横向滚动 + 粘性表头，避免 12 列挤压。

### L3 运行实例明细（总的收口）

- 继续复用现有运行详情页 `GET /api/runs/{runId}` 与二级路径详情，不复制第二套详情。逐请求归属仍走 `readAttemptRequests`（步骤/尝试维度），本切片不改它的口径。

## 3. 名词解释（本轮新增）

照顾不熟悉测试术语的用户，提供两种入口，二者共用同一份术语表：

- **行内 info 图标**：每个指标卡标签、表头、耗时列名旁放 info 图标，悬浮或点击弹出该名词的解释（是什么、怎么算、分母是什么、数据来自哪里、容易误解的点）。
- **右上角「指标口径说明」总入口**：L0/L1/L2 三个页面右上角各放一个入口，打开后集中列出本级涉及的全部术语。

术语表集中在 `web/src/features/reports/glossary.ts`，一个条目包含：`id`、`名称`、`一句话解释`、`怎么算（分子/分母）`、`数据来源`、`容易误解的点`。首轮必备条目（实现时按此清单逐条落地，禁止只做一半）：

| 分组 | 术语 |
| --- | --- |
| 运行事实 | 运行、路径运行、步骤、目标实例号、数据截至时间 |
| 比率 | 路径运行成功率、一次通过率（FPY）、路径覆盖度 |
| 耗时 | 步骤耗时、目标接口耗时、执行器耗时、工具端编排耗时、账号排队等待 |
| 统计 | 分位（P50/P90/P95）、均值、样本数、采样上限 |
| 接口与重试 | 读请求、写请求、目标接口调用、重试 |
| 结果 | 成功、失败、已停止、已取消、结果待确认、失败分类/阻塞 |
| 数据来源 | 运行记录表、`network.log` |

实现约束：解释文案全部中文白话，不出现内部英文键；术语表改动只能加条目或修订文案，不允许为了让页面好看而删条目。

## 4. 范围

### 包含

- **性能**：去掉按路径运行的 N+1 尝试查询（改为一次查询取回范围内路径运行的日志目录与终态）；报告接口耗时聚合改为按路径运行目录快速扫描 `network.log`（只做聚合，不建 DTO、不排序、不填充摘要、**不再读 `step.log`**）；扫描改为有界并发（worker 数固定，默认 8）；对终态路径运行的聚合结果按 `(文件大小, 修改时间)` 签名缓存，运行中的路径运行不缓存、每次重算。
- **口径修正**：报告中心的接口耗时/调用次数改为按「该路径运行目录 `network.log` 中 `path_run_id` 等于本路径运行」的**全部请求行**统计。原实现只统计能归属到具体尝试的行，`step_id/attempt` 对不上尝试的请求被丢弃，属于漏计；L3 运行详情的逐尝试归属保持原口径不变。
- **层级收敛**：新增 L1/L2 共用的「核心指标摘要」组件；`ReportMetricsPanel` 只在 L0 使用；三个视图按第 2 节各自裁剪。
- **名词解释**：`glossary.ts` 术语表、行内 `TermHint` 组件、右上角「指标口径说明」总入口。
- **数据细致权威**：三个只读接口的 DTO 增加 `generatedAt`（服务端统计时刻）；每张比率卡带分子分母；分位卡带样本数；结果/失败分类在图下补数值明细表；准备一套统一排版（页面骨架、卡片、标签、表格滚动与对齐、空/错/加载态）。
- **前端加载体验**：ECharts 包装组件改懒加载，首屏先出计数、计划表与文字指标，图表后渲染；三个视图统一刷新与状态呈现。

### 不包含（明确排除，禁止预判式引入）

- 不新增运行状态机、不改执行引擎的判定/调度/会话/核验语义、不调用目标平台任何写接口；除已落地的迁移 036 外不新增任何表或迁移。
- 不新增指标种类、不加导出（PDF/Excel）、不做定时报表、不做趋势对比与环比、不加接口端点 Top 或动作覆盖等新明细表（用户已选定「只做细不做多」）。
- 不做跨账号/跨租户的目标平台侧统计（报告只统计本工具运行事实）。
- 不改造 L3 运行详情页的版式与内容（本轮只到 L2 的入口跳转）。
- 内网项目不脱敏：现有 `network.log`/`curl.log` 继续按原样全量记录，本切片不新增任何脱敏或日志剥离逻辑。
- 不为旧数据、旧接口或旧实现保留兼容层、兜底或别名：报告服务的接口耗时读取从「借用运行编排服务」改为报告服务自己持日志根目录，原 `interfaceStatsReader` 面与 `RunOrchestrationService.PathRunInterfaceStats` 直接删除，不做双路并存。

## 5. 指标口径（既有不变量 + 本轮修正）

### 5.1 通过率与覆盖度（不变）

- 路径运行成功率 = `path_runs.result = 成功` 的路径运行数 / 该范围全部已结束路径运行数。
- 一次通过率 FPY = 首次尝试（`attempt_no = 1`）即判定成功且该路径运行最终成功的路径运行数 / 全部已结束路径运行数。
- 路径覆盖度 = 至少有一次运行记录的执行路径数 / 计划当前已保存的完整路径数。

### 5.2 时延分位（不变）

- 「步骤耗时」分位来自 `run_step_attempts.duration_ms`；「目标接口耗时」分位来自 `network.log` 的 `duration_s`（传输层真实计时），两者分开展示，绝不合并。
- 分位在服务端用统计库计算 P50/P90/P95 与均值；样本按范围有界拉取（采样上限保护），样本为空显示「暂无足够样本」，不显示 0；历史日志已清理、无 `network.log` 的旧运行显示「暂无真实请求耗时」，不回填估算。
- 本轮起每个分位都必须同时给出**样本数**，让用户判断这个数代表了多少次请求。

### 5.3 运行实例耗时分解（不变）

接口耗时 / 步骤总耗时 / 工具端编排耗时 / 执行器耗时的定义与「未知」降级规则保持第 1 轮实现：任一分量缺乏可靠事实时显示「未知」，不显示 0ms、不用阶段差值冒充；工具端编排耗时相减为负时显示「未知」，不硬凑。账号排队等待时间单列，不并入接口耗时也不并入工具端耗时。

### 5.4 执行器真实计时（不变）

`run_step_attempts.executor_ms` 由独立执行服务真实计时上报并落库（迁移 036，只写一次、永不 UPDATE）；非 runtime 步骤显示「无执行器环节」，历史行显示「未知」。

### 5.5 本轮口径修正：接口耗时与调用次数按路径运行全量计

- 报告中心的「目标接口耗时」「接口调用次数」「读/写占比」「写请求耗时」统一按 4.2 节说明的范围，统计该路径运行目录 `network.log` 中 `path_run_id` 匹配本路径运行的全部请求行（读/写归类沿用 `requestClassOf` 的端点白名单兜底，旧日志缺 `request_class` 时不漏计写请求）。
- 这样修正是为了让报告与「这次运行到底打了目标多少次」这个用户问题一致；原按尝试归属的算法会把登录、结构读取和归属不上的请求整行丢弃，报告数字小于真实调用量。
- L3 运行详情页继续按步骤/尝试归属展示，不受本修正影响；两处口径差异只在于「统计范围」不在于「计时」。

## 6. 性能方案（本轮新增）

目标：本地打开 L0/L1/L2 的首屏可读时间降到 1 秒量级，且不随运行目录数量线性恶化到不可用。可断言的验收门禁用确定性性质表达，不用墙上时间（CI 不稳定）：

1. **一次查询取目录**：新增仓储方法，用一条带 `LEFT JOIN run_step_attempts` 与分组聚合的 SQL，取回范围内每条路径运行的 ID、终态与否与日志相对路径，替代逐条 `ListRunAttempts`。断言：一次聚合对仓储只发 1 次该查询。
2. **只扫 `network.log`**：聚合不再读 `step.log`（省掉当前 131.4 MB 的扫描）。断言：临时目录只放 `network.log`、没有 `step.log` 时聚合必须成功。
3. **快速扫描器**：按行按字段名匹配，不建 map、不建 DTO、不排序、不填充摘要，只累计（总耗时样本、写请求耗时样本、读次数、写次数、是否有真实耗时）。实测同等数据量下串行 95 ms、8 并发 17 ms（现状仅 `network.log` 串行解析就 1.13 s）。
4. **有界并发**： worker 数固定（默认 8），按路径运行分发；单文件扫描失败跳过该条并继续，不因一个坏目录让整页失败。
5. **签名缓存**：终态路径运行的 `network.log` 不再变化，按 `(绝对路径, size, mtime)` 缓存聚合结果；运行中的路径运行每次重算。断言：连续两次对同一终态路径运行聚合，文件打开次数为 1。
6. **前端懒加载图表**：ECharts 走 `defineAsyncComponent`，首屏先渲染计数卡、计划表与文字指标，图表 chunk 后到；图表区在无数据时不渲染空图，只给文字状态。
