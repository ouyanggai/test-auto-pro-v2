# F-042 报告中心真实度量（总分总）

- 状态：`implementing`（2026-09-24 用户明确批准开始实施）
- 提出时间：2026-09-24
- 依赖：F-016 运行记录六表、F-020 多路径调度、F-021 运行记录分析视图、F-030 请求耗时事实、F-036 独立执行服务。前四项已落地；本切片在 F-036 执行服务上补一处真实计时上报。
- 用户裁决（2026-09-24）：执行器耗时采用选项 B（补真实计时器落库）；统计与图表一律使用成熟热门库，不手写分位与图表渲染以规避 bug。

## 1. 背景与问题

当前「报告中心」（`web/src/views/ReportsView.vue` 与 `ReportDetailView.vue`）整页是硬编码假数据：KPI、时延分位、计划质量列表、根因分类、审计流水全部写死在前端常量里，`/reports` 路由不调用任何后端接口。用户无法从报告中心看到任何真实运行事实。

同时项目里已经沉淀了完整的真实事实源，只是没有被聚合出来：

- MySQL 运行记录：`runs`、`path_runs`、`run_steps`、`run_step_attempts`、`run_events`、`run_controls`（迁移 026）。
- 每步尝试耗时 `run_step_attempts.duration_ms`、判定 `verdict`、失败分类 `failure_class`、传输结论 `transport`、状态码 `status_code`、重试来源。
- 目标接口传输层真实耗时：运行目录 `network.log` 的 `duration_s`（F-030 唯一耗时事实源），读/写分类、端点、HTTP 状态、业务结果、重试序号、trace。
- 阶段时间轴：`step.log` 的 plan/gate/prepare/verify/settle 阶段耗时（`PhaseDurations`）。
- runtime（独立执行服务）动作三阶段投影：`run_step_attempts.runtime_detail`（含逐请求 `durationMs`）。
- 运行详情单条投影已经成熟：`PathRunDetailDTO`（接口 `GET /api/runs/{runId}` 与二级路径页）。

唯一缺口：执行器（Playwright）自己的墙钟处理耗时没有被单独采集（见第 4.4 节）。本切片按用户裁决补齐它。

**本切片目标（单一用户结果）**：把报告中心从假数据改成基于真实事实的「总—分—总」三级统计看板，让用户从计划全貌逐级下钻到单条运行实例的接口与耗时明细，全程只读、不造数；并补齐执行器真实计时使耗时分解完整。

## 2. 「总分总」信息结构

### L0 报告中心首页（总）

- **上半部分：第一级计划情况统计。**
  - 全局计数：计划总数、有运行记录的计划数、累计运行次数、累计路径运行次数、进行中运行数。
  - 计划维度表：每个计划一行——计划名、运行次数、路径运行次数、结果分布（成功/失败/已停止/结果待确认/已取消）、最近一次运行时间与结果、路径覆盖度。点击任一行进入 L1。
- **下半部分：专业测试指标（全局聚合，全部来自真实事实）。**
  1. 路径运行成功率与一次通过率（FPY）。
  2. 路径覆盖度：至少运行过一次的路径数 / 计划已保存路径总数。
  3. 时延分位：分别给「步骤耗时」和「目标接口耗时」的 P50/P90/P95 与均值（两者口径不同，绝不合并）。
  4. 结果与停机分类占比：按 `path_runs.result` + `failure_class` + `stopKind`（阻塞/目标拒绝/结果待确认/已停止/已取消）分布。
  5. 目标接口调用统计：总调用数、读/写占比、平均接口耗时、写请求平均耗时。
  6. 重试统计：发生重试的步骤数与总重试次数（写连接未建立重试逐条计数，不合并）。

  > 指标释义随卡片一起用中文写清「这个数怎么算、分母是什么」，因为用户不熟悉测试术语。指标口径见第 4 节。图表用热门图表库渲染（第 5 节）。

### L1 计划详情（分）

点击计划进入。展示：

- 计划头部：计划名、账号、流程来源、目标对象名、路径总数、累计运行次数。
- 计划级专业指标：与 L0 相同口径，但范围收敛到本计划。
- **各路径指标表**：每条执行路径一行——路径序号与名称、运行次数、成功率、平均步骤数、平均步骤耗时、平均接口耗时、最近结果、覆盖到的动作种类数。点击任一路径进入 L2。

### L2 路径详情（分）

点击路径进入。展示：

- 路径头部：路径序号/名称、分支选择摘要、配置状态、运行次数。
- 路径级指标：成功率、时延分位、失败分类分布。
- **运行实例列表**：该路径每次运行实例一行——运行号、启动时间、状态、结果、步骤数、总耗时、目标实例号（只读不透明引用）、接口调用数。点击任一实例进入 L3。

### L3 运行实例明细（总的收口）

- **直接复用现有运行详情** `RunDetailView`（`GET /api/runs/{runId}/paths/{pathRunId}` 已提供 `PathRunDetailDTO`）：它已经展示步骤、尝试、逐接口明细、耗时、门禁快照、日志与 curl 入口。
- 报告中心 L2 的实例行「查看明细」直接跳到该页，**不复制第二套运行详情**。
- 在 L2/L3 补一层「运行实例耗时分解」摘要（见第 4.3 节），把「执行了哪些接口 / 接口耗时 / 工具端耗时 / 执行器耗时」按第 4 节口径汇总呈现，执行器耗时使用第 4.4 节新采集的真实值。

## 4. 指标口径（严格遵守 F-030，不造数）

### 4.1 通过率与覆盖度

- 路径运行成功率 = `path_runs.result = 成功` 的路径运行数 / 该范围全部已结束路径运行数。
- 一次通过率 FPY = 首次尝试（`attempt_no = 1`）即判定成功且该路径运行最终成功的路径运行数 / 全部已结束路径运行数。
- 路径覆盖度 = 至少有一次运行记录的执行路径数 / 计划当前已保存的完整路径数。分母取本工具路径表真实计数。

### 4.2 时延分位

- 「步骤耗时」分位来自 `run_step_attempts.duration_ms`（步骤尝试墙钟）。
- 「目标接口耗时」分位来自 `network.log` 的 `duration_s`（传输层真实计时），与步骤耗时**分开展示**，绝不合并成一个「时延」。
- 分位在服务端用统计库计算 P50/P90/P95（不手写分位算法）；样本按范围有界拉取（设采样上限，避免全表拉取），样本为空显示「暂无足够样本」，不显示 0。
- 历史日志已清理、无 `network.log` 的旧运行：接口耗时显示「暂无真实请求耗时」，不回填估算（沿用 F-030）。

### 4.3 运行实例耗时三分解（用户明确要的口径）

对一次运行实例，按可证明事实分解并分别命名：

- **接口耗时（目标传输）**：该实例全部 `network.log` 请求 `duration_s` 合计；写请求单独再给一份合计。真实一等公民。
- **步骤总耗时**：该实例全部步骤尝试 `duration_ms` 合计。真实。
- **工具端编排耗时**：`步骤总耗时 − 同一尝试内的目标接口传输耗时合计 − 执行器耗时`。作为派生值明确标注口径；账号级排队等待时间单列，不并入接口耗时也不并入工具端耗时（沿用 F-030「不能把账号排队时间归入目标接口耗时」）。
- **执行器耗时**：来自第 4.4 节新采集的 `executor_ms`（真实墙钟）。非 runtime（Go 直发）步骤无执行器环节，显示「无执行器环节」；runtime 步骤缺该字段（历史行）显示「未知」。

任一分量缺乏可靠事实时显示「未知」，不显示 0ms、不用阶段差值冒充。

### 4.4 执行器真实计时（选项 B，本切片实施）

- 独立执行服务（Playwright）在一次动作从装载开始到链路收敛的整个过程用真实计时器测墙钟耗时，作为「执行器处理耗时」，并把它随动作结果（`ActionRunResult`）上报给 Go。
- Go 在落账该尝试时把该值写入新列 `run_step_attempts.executor_ms`（`BIGINT NULL`，只写一次、永不 UPDATE，与 `before_facts`/`runtime_detail` 同纪律）。空值表示非 runtime 步骤或本迁移之前的历史尝试。
- 迁移编号取 `036`（035 是加签排除名单，编号不复用）。仅此一条最小向前迁移。
- 计时口径：执行器墙钟处理耗时是「执行服务侧从收到装载指令到动作收敛」的真实时间，它天然包含其转发给目标的等待；因此耗时三分解只把它作为「执行器环节」整体展示，接口耗时仍单独由 `network.log` 传输层计时给出，两者不相减制造负数——工具端编排耗时的派生在出现口径冲突（相减为负）时显示「未知」，不硬凑。

## 5. 技术方案（只读聚合 + 一处最小采集 + 热门库）

- 新增 `internal/service/report_center.go`（暂名）：只读聚合服务，复用 `run_request_timings.go` 的窗口归属与耗时口径。
- 新增只读仓储方法（`internal/repository/mysql/run_repository_*.go` 增量）：计数、成功数、结果/分类分布、读写占比用**带索引的分组聚合 SQL** 一次算出；分位所需的耗时样本按范围有界拉取（采样上限保护）。
- **统计计算库（不手写分位）**：分位/均值/中位数等在 Go 侧用成熟热门统计库计算，避免手写排序与插值出 bug。首选 `github.com/montanaflynn/stats`（社区主流 Go 统计库，提供 `Percentile`/`Median`/`Mean`）。计数、求和、占比等标准聚合继续用 SQL，不引库。
- **图表渲染库（不手写图表）**：前端用成熟热门图表库渲染看板。首选 Apache ECharts + `vue-echarts`（Vue 3 生态最主流、成熟稳定，与现有 Naive UI + Vite 兼容）。折线/柱状/环形/分位条等图表由它渲染，前端不手写 SVG/Canvas 图表。
- 依赖一律锁定精确版本（实施时取当前稳定版并 pin），只引入上述广泛使用、活跃维护的库，不引冷门包。
- **执行器采集**：`executor-service` 在动作入口起真实计时，收敛时把 `executorMs` 放进动作结果协议；Go 执行器在构造尝试记录时读取并写入 `run_step_attempts.executor_ms`。协议与落账都只加字段，不改动作语义、写纪律与核验。
- 新增只读 API（`internal/api/reports.go`）：
  - `GET /api/reports/overview`：L0 全局计划计数 + 专业指标。
  - `GET /api/reports/plans/{planId}`：L1 计划头部 + 计划级指标 + 各路径指标。
  - `GET /api/reports/plans/{planId}/paths/{pathId}`：L2 路径头部 + 路径级指标 + 运行实例列表。
  - L3 复用现有 `GET /api/runs/{runId}` 与 `GET /api/runs/{runId}/paths/{pathRunId}`。
- 报告 DTO 返回统计所需字段与标识；内网项目不脱敏、不新增日志剥离层，现有 `network.log`/`curl.log` 原样保留。耗时未知字段带 `xxxKnown` 布尔，前端据此显示「未知」。
- 前端：`ReportsView.vue`（L0）、`ReportDetailView.vue`（L1）改为真实接口驱动并删除假常量；新增 L2 路径详情视图；L3 沿用 `RunDetailView`。图表用 ECharts，卡片/表格复用 Naive UI，不引入新 UI 框架。
- 详细技术边界写入 `docs/ARCHITECTURE.md`「F-042 报告中心真实度量」小节。
