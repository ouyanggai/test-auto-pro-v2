# F-028 失败动作重试

- 状态：awaiting_approval
- 产品依据：`docs/PRODUCT.md`「计划与运行主线」第 6 条（待对账终局、从计划重新发起是唯一出路）与「产品原则」（写操作结果不明确时禁止盲目重发；本切片只允许对**确定失败**重试，不触碰该原则）
- 架构依据：`docs/ARCHITECTURE.md`「F-026 状态感知的动作循环编排」、`internal/model/run.go` 路径运行状态机、`docs/EXECUTION_PROGRAM.md` 第 7 节运行记录

## 总结

路径运行中某个动作**确定失败**（写请求确认未发出或目标明确拒绝、无任何副作用）后，运行画布当前停留在失败终态，用户唯一的继续方式是从计划重新发起一次全新运行：已执行步骤全部重来，新发起计划还会创建新的主实例。用户要求：失败的动作上提供「重试」按钮，同一运行从失败的那一步继续执行。

本切片交付：运行画布失败态出现「重试失败动作」入口；点击后同一运行从失败步骤重新装填，按原运行模式继续执行；已落库事实一条不改、只追加。**结果待确认（写不确定）仍然终局，不提供重试**，维持 2026-09-06 产品裁决。

## 关键规则

1. **可重试判定（服务端唯一裁决）**：路径运行 `status = failed` 即可重试。理由：按判定矩阵，凡判「确定失败」的五类失败（门禁不满足、演员不可解析、目标拒绝、零写入、工具缺陷）都已证明本次尝试无任何目标副作用；「写结果不确定」按矩阵落 `awaiting_reconciliation` 而非 `failed`，天然被排除。界面按钮的显隐只信服务端返回的 `retryable` 字段，不自行推断。
2. **重试本身不发任何写请求**。它只做四件事：重建执行上下文、校验前缀一致性、把路径运行 `failed → running`（运行聚合同步重开）、把控制游标装填到失败步骤；之后的执行完全复用既有七阶段管线（实时门禁、一次写、写后核验、租约与围栏令牌），每次尝试独立落账。
3. **前缀一致性校验**：重试按当前 `user_actions` 重新编译场景；若已成功执行的前缀（步骤数、动作、节点顺序）与已落库事实不一致——即失败后用户改过配置——拒绝重试，中文提示「配置已变化，无法继续本次运行，请从计划重新发起」。
4. **原模式继续**：人工控制模式重试后停在失败步骤等待「放行」；单步模式等待「执行一步」；自动模式按既有自动语义继续且断点仍生效。断点集合按启动预置与运行期间断点事实回放重建；「首次写」断点在本运行已有成功写事实时视为已触发，不重复拦截。
5. **事实只追加**：重试后的步骤执行按既有规则新增 `run_steps` 行与 `run_step_attempts` 行（同一步骤号出现多行是事实的如实反映）；`run_controls` 新增 `retry_requested` 控制事实；`run_events` 追加「重试失败步骤」事件。不 UPDATE、不 DELETE 任何事实行。
6. **失败可再重试**：重试后若再次确定失败，运行再次落失败终态，按钮重新出现；重试次数只受用户点击约束，工具绝不自动重试。
7. **重复点击幂等**：第一次重试已把状态装填为运行中后，后续重试请求得到稳定的中文冲突提示，不产生第二次装填。

## 接口与数据

- 新端点：`POST /api/runs/{runId}/retry?pathRunId=...`，与既有 `approve`/`stop` 同一寻址方式；响应复用 `PathRunDetailDTO`，新增 `retryable` 字段由服务端计算。
- 状态机：`pathRunTransitions` 仅新增 `failed → running` 一条通路，注释写明这是 F-028 用户显式重试的唯一切入点；`awaiting_reconciliation`、`completed`、`stopped`、`cancelled` 仍无出边。运行聚合 `runs` 相应支持 `failed → running` 重开并清空 `finished_at`，再次终态时既有 `Finish` 镜像收尾不变。
- 聚合列：重试装填时清空 `path_runs` 的 `result`、`failure_class`、`finished_at`；历史失败事实保留在 `run_steps`/`run_step_attempts`/`run_events`，运行详情与事件流必须能同时看出「第一次失败」与「重试后结果」。
- 不新增数据库表；是否需要迁移（如尝试行标记重试来源）由实施时以最小方案裁决，默认不加列——控制事实与事件流已构成完整审计链。

## 人工验收

1. 造一次确定失败（例如目标暂不可达导致写请求未发出）：运行画布显示失败与「重试失败动作」按钮；点击后（人工控制模式）停在失败步骤，按「放行」后该动作重新执行，成功则运行继续推进。
2. 重试后再次制造失败：按钮重新出现，可再次重试；第一次失败记录在步骤列表与事件流中仍然可见，未被覆盖。
3. 失败后修改该路径动作配置再点重试：得到「配置已变化，无法继续本次运行」的明确提示，不产生任何目标写请求。
4. 结果待确认的运行：无重试按钮，说明文案与现状一致。
5. 重试过程中点「停止运行」：按既有停止语义在安全边界生效，不出现孤儿动画或僵尸运行。
