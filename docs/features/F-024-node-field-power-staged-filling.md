# F-024 节点级字段权限与分段填写

- 状态：ready_for_manual（实施与自动验证完成，等待人工验收；用户 2026-09-05 明确「开始」批准本范围）
- 产品依据：`docs/PRODUCT.md` 产品原则「目标平台代码和真实运行结果决定流程、分支、人员与动作语义」；「计划与运行主线」使用目标平台真实账号、实例和接口执行
- 架构依据：`docs/ARCHITECTURE.md` 的「系统边界」（目标写请求只能由 `internal/adapter/target` 发出；`internal/engine` 承载执行语义）
- 纲领依据：`docs/EXECUTION_PROGRAM.md` 第 4.3 节七阶段（`prepare` 与 `submit` 的载荷构造）、第 8.2 节语义清单「表单字段权限」一行（原状态：发起节点已处理、审批节点待覆盖）
- 计划确认时间：2026-09-05（用户先后裁决：分支字段无发起权限时排期到能填的节点自动填写并提示；随后回复「开始」）

## 目标

让工具每一次目标写请求携带的表单数据，与真实用户在那个节点上能提交的数据一致：以实例当前完整表单数据为基线，只覆盖该节点有编辑权限且我们配置过的字段。发起时只带发起人可编辑字段；分支条件字段若发起人无权编辑，则由路线上第一个有权编辑它的人工节点自动带上，并在配置阶段就告诉用户这个字段会在哪个节点填写。

## 为什么必须做

三条都有目标源码与实测数据可证：

- 目标保存表单数据是整份覆盖，不合并：`FormDataServiceImpl.java:404` 直接 `query.setData(formDataVo.getData())`；请求不带 `dataId` 时新建文档并把实例 `currentDataId` 指向它。审批必定走这一步（`FlowAuditServiceImpl.java:225` 无条件调 `saveFormData`）。
- 目标自己的审批页每次都提交整份表单模型：`EnterpriseExamineDialog.vue:1804` 的 `formDataMongoVo.data = generateForm.getValues()`。
- 工具当前的同意只带分支字段（`internal/engine/step/gate.go` 的 `branchFormData`），第一次真实同意就会把实例表单数据覆盖成只剩分支字段；F-019 其余动作相反地带整份历史快照，会覆盖上游审批人已填内容。同意从未在真实目标执行过，因此这个缺陷尚未造成真实损坏。

覆盖面：目标库 2732 个流程模板中，1718 个存在「某审批节点可编辑、发起节点不可编辑」的字段。

## 范围

### 包含

- 节点级字段权限投影：从目标节点树的 `flowNodeFieldPowerTemplateList` 得出每个节点的可编辑字段集合（`edit`），`_$$_` 分隔符归一为 `.`，子表单列沿用 `<model>_col` 约定。执行期用实例绑定的代理版本，配置期用模板版本。
- 写载荷构造改为「实例当前完整表单数据 + 本节点可编辑且已配置字段」：发起没有实例，基线为空对象；其余动作先只读读取实例当前表单数据（有界重试）。请求不携带 `dataId`，与目标前端一致。
- 被权限挡掉的字段如实记录进 `step.log` 与门禁快照，不静默丢弃。
- 条件字段填写节点提示：每个条件字段算出路线上第一个能编辑它的人工节点，在数据工作区的关键字段一栏与分支补丁明细里给出中文提示；一个节点都找不到时产生阻断问题。
- 数据工作区按节点切换视图：发起人视图与路线上各人工节点视图，每个视图只开放该节点 `edit` 的字段，其余禁用、`hide` 隐藏、非可编辑字段不参与必填校验。数据仍是同一份表单数据，视图只切换权限。

### 不包含

- 不改存储结构、不新增迁移：按节点分段是「同一份表单数据 + 按节点权限过滤」得到的，不需要把数据拆成多份存。（用户批准过迁移，实测不需要，按最简单可运行实现处理。）
- 不改目标平台的权限配置，也不绕过权限：工具只按目标已声明的权限决定带什么字段。
- 不实现 `only_read` 与 `hide` 的语义扩张：`hide` 只影响显示，不影响我们带什么字段。
- 不改 F-014 判定规则、F-015 运行前检查结论与 F-016 至 F-019 的状态机。

## 顺带修复的阻塞性缺陷（本切片范围内发现，不修则分段填写无法工作）

编译场景与配置快照的 `nodeKey` 是哈希派生的不透明键（`analyzer.PathConfigNodeToken`），此前被直接当作
目标 `nodeProxyId` 使用，导致：待办新鲜读取永远匹配不上（同意必然报「目标上已无本节点待办」）、
事实重读永远判「待办已消失」（没生效的写会被判成确定成功）、对账对照与按节点写参数同样失效。
现按同一派生规则从真实结构反查真实标识补进节点表，并对任务级动作加「缺失即阻塞」兜底。
真实数据核对：`ca83e24f…` → 发起人(start)、`7f7e1ac9…` → 合同管理部-主任、`d3410634…` → 资源开发部。

## 已知边界（如实）

- 「审批节点独占可填字段」在当前测试流程（合同盖章评审）上不存在：该流程 4 个审批节点的可编辑字段
  都是发起人可编辑字段的子集，因此这条路线上看不到分段填写的效果。全库 2732 个流程模板里 1718 个存在该情形。
- 目标后端是否对越权字段做过滤或拒绝仍未实测（前端只做 UI 控制）。本切片按「只带该节点能改的字段」构造，
  比越权提交更保守；该结论待真实写覆盖到再补进语义清单。
- 不同意（`reject`）动作在 `target.BuildActionBody` 里没有对应分支，会以 `UNSUPPORTED_ACTION` 失败告终（失败安全，
  不会误写）。这是 F-019 的既有缺口，不在本切片范围内修。

## 人工验收

1. 打开一条路径的数据工作区：确认顶部可切换「发起人」与路线上各节点视图，切换后可填字段随之变化，发起人不可填的字段在发起视图里禁用。
2. 找一个发起人无编辑权限的条件字段：确认该字段旁提示「由〈节点名〉自动填写」，关键字段一栏与分支补丁明细里说法一致。
3. 启动单步运行，在第一步预览里核对「即将发出的请求」：确认只包含发起人可编辑字段，没有后续节点才可填的字段。
4. 放行到某个审批节点，核对该步预览：确认请求正文里既有实例当前值，也有该节点应当带上的配置值，其余字段与实例现状一致。
5. 回目标平台打开该实例的表单：确认上游节点填过的字段没有被后续步骤清空或改写。
6. 执行定向验证入口，确认全部通过且无跳过。
