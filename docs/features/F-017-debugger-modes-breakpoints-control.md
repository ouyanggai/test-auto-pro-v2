## 目标

让用户在一次真实运行里真正控制执行节奏：启动时选自动运行、单步运行或人工控制；用五类断点表达"跑到哪里就停下来给我看"；暂停后看清当前真实事实与下一步预览，然后放行、执行到下一节点、继续运行或停止。所有控制动作都是不可覆盖的运行事实。

## 为什么这个切片承担了"跑到哪里算成功"

成功断言已于 2026-09-04 按用户决定整体移除（纲领第 7.4 节、`docs/PRODUCT.md` 第 45 行）。移除时的替代方案就是断点：在期望的节点或动作上挂断点，命中即停，比只在最后比对一次的断言更早暴露偏离。

这意味着本切片不是"顺手加个调试面板"，而是把用户表达期望的唯一手段补上。在它交付前，用户只能靠 F-016 的强制单步一步步看；交付后，用户才能说"跑到合同审批节点停下"或"执行到第一个不同意动作停下"。

## 单一用户结果

用户在运行前检查判定为可执行的路径上点击启动，先选运行模式，并可在启动前先挂好断点（默认已开首次写断点，路径偏离断点强制开启不可关闭）。

选自动运行时，工具连续执行，但第一个写请求之前必定停下——这是安全阀，不是可选项。停下时画布把当前步节点标出并平移到操作区中央，侧栏给出当前真实目标事实、下一步预览（动作、真实处理人、预期效果、门禁结论、即将发出的请求）、以及一句中文的"为什么停在这里"（命中了哪个断点，挂在哪个对象上）。

用户在这里可以：放行一步、执行到下一节点、继续运行到下一个断点、随时增删断点、随时暂停、随时停止。单步运行模式下只有"放行一步"，这与 F-016 的行为完全一致，不给用户"看起来能连续跑"的假象。

执行中途实际命中的分支与已配置路径不一致时，路径偏离断点强制停下并显著标出偏离位置；这种停止不提供放行，因为后面的步骤在偏离后的真实结构上根本不成立。

一路控制到用户想停的地方按停止：路径运行进入`已停止`，界面如实说明"已完成 N 步、停在哪个节点、最终目标事实是什么"，不把提前停止说成成功，也不说成失败。

每一次增删断点、暂停、放行、停止、断点命中都写进 `run_controls` 与 `control.log`，可在 code-server 里按运行目录逐行核对。

## 范围

### 包含

- 三种运行模式（纲领第 5.1 节）：自动运行、单步运行、人工控制。启动时选择并落 `runs`，运行中不改模式，不写进计划配置。
- 五类断点（纲领第 5.2 节）：首次写断点、步骤断点、节点断点、动作断点、路径偏离断点。全部挂在尚未执行的对象上，只对当前运行生效，可在启动请求里预置，也可在运行中随时增删。
- 断点命中判定与命中优先级，统一在阶段 3（`control`）发生；命中在所有模式下都落事实，即使该模式本来就会停。
- 路径偏离的判定与强制停止：偏离在上一步 `verify` 认定为事实，在下一步 `control` 命中路径偏离断点并停下。
- 三条单步命令（纲领第 5.3 节）：执行一步、执行到下一节点、继续运行。可用命令集合由后端按模式与当前状态给出，前端不自行推断。
- 暂停与停止的完整语义（纲领第 4.5 节）：暂停请求只在阶段 3 生效；已进入 `submit` 的步骤必须走完 `verify` 与 `settle`；停止是终态。
- 控制命令的条件写与幂等：命令携带当前步游标与控制版本，服务端条件写；重复提交同一命令只产生一次效果。放行会触发真实写，重复放行必须不能变成两次写。
- `run_controls` 的控制事实类型扩展（增删断点、请求暂停、暂停生效、放行及命令种类、请求停止、停止生效、启动模式），append-only；当前生效断点集合由事实回放得出，不新建可变断点表。
- `control.log` 写入器（纲领第 6.2 节，F-013 已明确归属本切片）：运行模式、断点增删、断点命中、暂停、放行、停止逐行可查，字段沿用第 6.3 节统一行格式与关联键。
- `run_events` 增补中文标签事件：模式选定、断点已设置、断点已删除、断点命中、已暂停、已放行、已停止。
- 暂停时可检视内容的补齐（纲领第 5.4 节）：在 F-016 已有的当前事实、下一步预览、条件字段实际值与命中分支、日志行入口之上，补上"为什么停在这里"与"现在能做什么"。
- 界面：启动对话框的模式选择与启动前断点预置；运行画布上的断点标记与就地挂断点；断点面板（列出当前生效断点，可删）；控制命令区（按后端给出的可用命令渲染）；暂停原因区。
- 自动运行下的状态刷新：继续用轮询，间隔走配置，不引入 WebSocket。
- 断点命中并停止后的路径结果表述：`已停止` 与"已完成 N 步、停在哪个节点、最终目标事实"分开呈现，不合成一个成败判定。

## 设计要点

### 三种模式的差别就是可用命令集合

纲领第 5.1 节的"单步运行"与"人工控制"文字接近，本切片按下述方式落地，把差别定义在可用命令上，避免出现两个行为相同的模式：

| 模式 | 启动后行为 | 暂停时可用命令 |
| --- | --- | --- |
| 自动运行 | 不等放行，直接连续执行 | 执行一步、执行到下一节点、继续运行 |
| 单步运行 | 停在第一步之前 | 只有执行一步 |
| 人工控制 | 停在第一步之前 | 执行一步、执行到下一节点、继续运行 |

- 单步运行不提供"执行到下一节点"和"继续运行"：这两条都与"每一步执行前都停"直接冲突，给了就等于模式名说谎。这样单步运行与 F-016 已验收的行为完全一致，用户可以把它当作已经熟悉的那条路。
- 自动运行命中断点或需要人工后停下，可用命令与人工控制相同。否则"继续运行直到命中断点"这句话不成立。
- 三种模式都可以随时增删断点、随时暂停、随时停止。断点是安全设施，不能因为选了某个模式就不给。
- 模式在启动时确定并落 `runs`，运行中不切换。运行中切模式会让"这次运行是怎么跑的"无法一句话说清，而运行记录必须能回放。
- 默认模式是单步运行。默认值取最保守的那个，因为放行一次就是目标平台上一条真实数据。

### 断点模型

断点只有三个挂载维度，全部来自已有数据，不新造标识体系：

| 断点类型 | 挂载对象 | 命中时机 | 默认 |
| --- | --- | --- | --- |
| 首次写断点 | 本次运行整体 | 第一个写步骤的阶段 3 | 开启，安全阀 |
| 步骤断点 | 编译步骤序号 `CompiledActionStep.Sequence` | 该步骤的阶段 3 | 关闭 |
| 节点断点 | 语义节点 `NodeKey` | 进入该节点的第一个步骤的阶段 3 | 关闭 |
| 动作断点 | 动作类型 `model.ActionKey` | 该动作类型步骤的阶段 3 | 关闭 |
| 路径偏离断点 | 本次运行整体 | 上一步 `verify` 认定实际命中分支与已配置路径不一致后，下一步阶段 3 | 开启且不可关闭 |

- "是不是写步骤"由动作目录的 `TargetOperation` 是否落在写端点白名单判定，不在代码里硬编码动作名。这样 F-019 扩张动作时首次写断点自动跟上。
- 断点只能挂在尚未执行的对象上。对已执行步骤设断点直接拒绝并给中文原因，不静默忽略。
- 动作断点的现实边界：F-015 的运行前检查会阻塞未登记动作，所以当前能真正命中的动作断点只有 F-016 登记的发起与同意。其它动作类型允许设置（设置本身是合法的），但真实命中证据要等 F-019。本切片如实这样记录，不伪造真实命中。
- 断点删除是一条新的事实，不是把旧事实改掉。当前生效集合由 `run_controls` 回放得出。

### 命中判定统一在阶段 3

纲领第 4.3 节把阶段 3 定为控制判定，第 4.5 节明确"暂停只在阶段 3 生效，不打断已发出的写请求"。本切片据此把全部断点判定放在阶段 3，一个例外都不开：

- 阶段 1（`plan`）与阶段 2（`gate`）是只读的，先跑完再判定不产生副作用，并且能让下一步预览带上真实门禁结论。
- 同时命中多个断点时全部落事实，界面主因按固定顺序取：路径偏离、首次写、动作、节点、步骤。越靠前的越是安全阀，越应该先说。
- 门禁在阶段 2 已判为不通过时，停止仍然按门禁不通过生效（不允许"门禁不过还能被放行"），但若同时存在未处理的路径偏离事实，界面标题取路径偏离——因为偏离解释了门禁为什么不通过。两条原因同时落 `run_events`。

### 路径偏离：事实在 verify 认定，停止在下一步阶段 3 生效

- 偏离判据：阶段 6 事实重读得到的真实当前节点，与已配置路径的下一个预期节点不一致。判据只用重读到的真实事实，不用工具自己的条件求值结果去覆盖目标结论。
- 偏离一旦成立就在阶段 7 作为独立事实落 `run_steps` / `run_events`，界面立即显示（F-016 已交付连线标红），停止在下一步阶段 3 生效。
- **偏离停止不提供放行**。后面的编译步骤挂在不会被走到的节点上，放行只会换来一次门禁不通过。给一个必然失败的按钮是误导用户，不是给用户自由。此时只提供停止与查看，断点仍可增删。
- 合法后续处置由用户决定：计划已固化，本次运行只能停止；要按新路径跑就新建运行。界面只给中文事实与这一句结论，不提供改配置入口。

### 暂停、放行、停止的语义边界

- 暂停请求随时可提交，但只在阶段 3 生效。请求已提交、尚未生效时界面显示"将在本步结束后生效"，与 F-016 的停止按钮同一套表述。
- 已进入 `submit` 的步骤必须走完 `verify` 与 `settle`。这一条不给任何绕过入口：写请求已经发出，中断只会制造一个我们自己都判不清的不确定写。
- 停止是终态，产生`已停止`；已发生的事实全部保留。
- 暂停不是终态。`暂停 -> 运行中` 的往返由 `run_events` 完整记录。纲领第 4.2 节"状态只前进"约束的是不允许从终态回到非终态、不允许重跑已完成步骤，不是禁止暂停后继续。
- 若 F-016 实施时用`运行中`表示"等待放行"，本切片只为断点命中与暂停请求使用`暂停`状态，两者在界面上统一表述为"已暂停，等待放行"，并由 DTO 的统一停止原因字段说明区别，不让用户看到两套说法。实施时先核对 F-016 实际实现。

### 控制命令必须是条件写且幂等

放行一次等于目标平台上一条真实数据，所以控制接口不能是"点两次走两步"的裸接口。

- 每个控制命令携带当前步游标与控制版本；服务端在同一事务内校验后才 INSERT 控制事实并推进。
- 版本不匹配时返回中文冲突说明与当前真实状态，不执行。用户重复点击、页面轮询回放、两个标签页同时操作，都只可能产生一次效果。
- 放行仍然不绑定单键快捷键（F-016 已定的取舍），本切片新增的三条命令同样只接受明确的按钮点击。

### 自动运行下的状态刷新：继续轮询

F-016 把"自动模式是否需要实时推送"留给本切片评估。结论是继续轮询，不引入 WebSocket：

- 状态变化的粒度是步与阶段，目标本身存在分钟级抖动和稳定约 30 秒的慢请求（纲领第 4.4.1 节），秒级轮询已经足够跟上。
- WebSocket 会引入连接、重连、断线补偿一整套新状态机，而运行事实必须以数据库为准，推送只会多一条可能与数据库不一致的路径。
- 具体做法：轮询间隔走配置，自动运行下用较短间隔、暂停后退回较长间隔，界面显示最后一次状态更新时间。超过配置预算没有更新时按 F-016 已定的"疑似无响应"处理。

### 断点命中并停止后的路径结果

- 提前停止既不是成功也不是失败。路径结果落`已停止`，同时给三段中文事实：已完成多少步、停在哪个节点与哪个动作之前、最终目标事实（实例状态、当前节点、当前待办、已办情况）。
- 这就是断言移除后"跑到哪里算成功"的表达方式：用户挂断点表达期望，命中即停就是期望达成的证据，判断留给用户。工具不替用户下结论（纲领第 7.4 节）。
- 失败分类不新增。本切片不引入"因断点停止"这种失败分类，因为它不是失败。

### 界面落点

全部落在 F-016 的运行画布与路径运行详情页上，不新建页面、不新建第二套画布：

- 启动对话框：模式三选一（默认单步运行），并给出启动前断点预置区。首次写断点显示为已开启可关闭，路径偏离断点显示为强制开启不可关闭，并各带一句中文说明为什么。
- 画布节点与连线：已挂断点的节点带断点标记；点击节点可就地"在此节点设断点"或删除该节点断点；偏离位置沿用 F-016 的标红。

## 未决与需要用户裁决的事项

以下三项按本文件给出的方案写入，但都是可以被用户推翻的取舍，实施前若有异议请裁决：

1. **单步运行不提供"执行到下一节点"与"继续运行"。** 理由是模式名与行为必须一致。若用户希望单步只是"默认停"而仍可连续跑，则单步与人工控制会合并成一个模式，纲领第 5.1 节的三模式需要相应改写。
2. **路径偏离停止后不提供放行。** 理由是后续步骤在偏离后的结构上不成立，放行必然换来门禁不通过。若用户希望保留放行以便"亲眼看到它被门禁拦住"，改动很小，但界面必须写明放行的后果。
3. **自动运行下继续用轮询而不是 WebSocket。** 理由见设计要点。若用户要求实时推送，工作量与新增故障面都会明显上升，且推送与数据库不一致时以数据库为准的规则需要单独设计。

另有一项现实限制不是取舍而是事实：动作断点当前只能在发起与同意两个已登记动作上真正命中，其余动作要等 F-019。

## 人工验收

1. 打开一条运行准备判定为可执行的路径点击启动：确认模式有三个选项、默认是单步运行，启动前能预置断点，首次写断点已默认开启且可关闭，路径偏离断点显示为强制开启且无法关闭，两者各有一句中文说明。
2. 选单步运行跑几步：确认行为与 F-016 验收时完全一样，只有"执行一步"，没有多出"执行到下一节点"或"继续运行"。
3. 选自动运行启动：确认工具没有直接开跑到底，而是停在第一个写请求之前并说明"命中首次写断点"；放行后连续执行，直到下一个停止条件。
4. 在画布上给路径中间某个节点挂节点断点，然后继续运行：确认跑到该节点前停下，暂停原因区写明命中的是节点断点以及挂在哪个节点（用业务名称）。
5. 给同意动作挂动作断点并继续运行：确认命中并停下。再试着给一个未登记的动作（例如不同意）挂断点：确认能挂上，并确认这类路径本来就会被运行前检查阻塞。
6. 用人工控制模式启动，点"执行到下一节点"：确认连续执行到语义节点变化时停下，而不是走完一步就停、也不是一直跑到底。
7. 运行中增删断点各一次：确认画布标记与断点面板即时同步，不需要刷新页面，并且在 `logs/plans/<计划>/runs/<路径>/<运行号>/control.log` 里能看到对应行。
8. 制造一次路径偏离：在某一步暂停时，用测试账号到目标平台上手工把同一实例推进或回退一步，回来点放行，确认路径偏离断点强制停下、偏离位置在画布上显著标出、并且没有放行入口，只能停止。
9. 核对暂停时机：在放行后立刻点暂停，确认按钮显示"将在本步结束后生效"，并且这一步确实走完了 `verify` 与 `settle` 才停；`control.log` 里能看到"请求暂停"与"暂停生效"两条时间不同的行。
10. 核对重复点击：连续快速点两次放行，确认只前进一步，目标平台上只多一条真实数据。
11. 按停止结束运行：确认路径结果是`已停止`，界面分开写"已完成几步、停在哪里"和"最终目标事实"，没有把提前停止说成成功或失败。
12. 在路径运行处于`暂停`时重启后端：确认它仍然是`暂停`，没有自动继续，也没有被误判成`待对账`。
13. 通览界面：确认没有跳过步骤、任意跳节点、重置目标实例、运行中修改计划配置的入口，写结果不确定时也仍然没有任何重试或继续按钮。
