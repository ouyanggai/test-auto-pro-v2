# F-030 执行性能与请求耗时可观测优化

- 状态：ready_for_manual
- 产品依据：`docs/PRODUCT.md`「计划与运行主线」、`docs/PRODUCT.md`「F-026 状态感知的动作循环编排」、产品原则中的真实状态与可观测要求
- 架构依据：`docs/ARCHITECTURE.md`「F-029 会话缓存与网络重试」、`docs/ARCHITECTURE.md`「F-026 状态感知的动作循环编排」、`docs/EXECUTION_PROGRAM.md` 第 4.3、6.2、7.1 节
- 计划确认时间：2026-09-12（用户批准全量实施）

## 目标

在不改变目标平台业务语义的前提下，缩短一次流程运行中由重复只读请求、候选任务串行扫描和同账号排队造成的本地等待；同时让用户在节点动作详情里明确区分：

- 一步的完整墙钟耗时；
- 本地编排、账号排队和等待放行耗时；
- 目标平台每一次真实接口请求的传输耗时；
- 写请求耗时、读请求耗时、请求次数与重试情况。

用户最终看到的是“流程确实更快，慢在哪里也能直接看懂”，而不是把本地准备时间误标为目标接口慢。

## 不可破坏的行为边界

本切片只优化读取、排队和展示，不改变流程功能：

1. 编译步骤、节点顺序、动作组和固定尾动作保持不变。
2. 每次尝试最多发出一次目标写请求；不得通过缓存、合并或并发方式增加写请求次数。
3. `submit` 阶段仍禁止内部重试；读请求、会话失效处理和写连接未发出重试继续遵守 F-029 边界。
4. 写后核验仍必须读取目标实时事实；任何缓存只允许服务于同一步、同一事实版本，写请求之后必须失效，不能用旧事实判定成功。
5. 同一账号的会话和目标操作仍然串行；不得为了缩短等待而允许同账号 SID 并发覆盖或放宽账号锁。
6. 目标平台端点、请求载荷、处理人解析、路径偏离判定、失败/待确认语义和运行事实 append-only 规则不变。
7. 页面不把推算值标成真实接口耗时；没有可靠请求事实时显示“暂无真实请求耗时”，不显示 0 毫秒。

## 范围

### 包含

- **执行前基准与测量**
  - 为同一计划、同一账号、同一路径建立可复现实测基准，分别统计路径墙钟、目标请求总时长、请求次数、账号锁等待、步骤间空档和每步七阶段耗时。
  - 使用现有 `network.log` 的传输层 `duration_s` 作为目标接口真实耗时来源；不使用秒级 `step.log` 阶段差值冒充接口耗时。
  - 在运行日志中补齐可归因的本地等待原因：账号使用锁等待、调度排队、用户放行等待、预览读取和核验读取；无法证明原因时记录为“本地编排等待”，不猜测。

- **重复只读请求优化**
  - 在同一个读取边界内复用事实版本和已经读取的分页结果，避免对同一实例/任务重复扫描；预览后发生放行等待、会话代次变化或其他可能改变事实的事件时立即失效，写请求发出后强制建立新的核验读取屏障。
  - 将候选处理人逐个查任务的流程改为有界、可复用的读取批次；仍按目标返回顺序、节点、处理人和待办状态过滤，不改变候选选择结果。
  - 对任务列表分页读取增加明确的页数上限、结束条件和请求计数，避免同一逻辑查找无界重复读取；目标返回异常时仍按现有错误语义停步。
  - 先复用现有目标接口和会话管理能力；若无法证明某个“精确查询”接口与现有列表语义一致，不新增目标端点、不用猜测接口替代。

- **同账号调度与锁等待优化**
  - 调度器在放行路径前识别计划账号的有效并发边界，避免多条路径同时抢同一个账号锁后长时间空转。
  - 账号锁仍覆盖目标读取、写入和写后核验所需的安全范围；只优化排队顺序、重复争抢和等待可见性，不缩短到会破坏 SID 或目标事实一致性的范围。
  - 同账号路径仍可按计划配置运行，但界面和日志必须显示“路径并发上限”和“账号实际串行等待”是两个不同概念。

- **真实请求耗时数据**
  - 后端运行详情为每次尝试增加只读的请求耗时明细：请求阶段、读/写类型、目标接口、传输耗时、HTTP 状态、目标业务结果、重试序号和 trace 关联。
  - 请求明细只返回展示所需的安全摘要，不返回 SID、密码、完整请求体或完整响应体；完整正文仍只从 `curl.log` 查看。
  - 请求耗时以 `internal/adapter/target` 传输层开始发送到收到响应或传输失败的真实计时为准；排队、JSON 构造、页面轮询和数据库落账不计入目标接口耗时。
  - 同一次尝试包含多次只读请求时，展示请求列表和读请求合计；写请求单独展示，避免把“发送请求”误解为一条接口调用。

- **节点动作详情 UI 排版**
  - 保留现有“点击节点打开详情”的入口，不新增独立技术状态页，不改变运行画布和控制按钮位置。
  - 动作详情顶部改为紧凑摘要区：动作名称、节点、当前处理人、结论；下方固定展示四个可比较指标：步骤总耗时、目标请求耗时、请求次数、其中写请求耗时。
  - 将原来混在一起的阶段标签改为两层结构：
    - “本地执行过程”：预览、门禁、账号排队、准备、放行等待、核验、落账；
    - “目标请求明细”：每条真实接口请求的阶段、类型、接口、耗时、结果和重试。
  - 请求明细按发生顺序排列，写请求使用明确的“写入”标识，读请求使用“读取”标识；失败、重试和未发出请求必须有独立状态，不只依靠颜色。
  - 原始请求/响应和日志位置继续折叠在详情底部，保留复制日志位置与复制可重放 curl；不把 trace、内部节点键作为主标题或主要信息。
  - 弹窗在桌面窄窗口下仍保持“摘要先看、明细可滚动、原文折叠”的稳定布局；长接口名换行，不能撑破详情宽度。

- **用户能听懂的阶段说明**
  - 内部阶段名只留在日志和接口字段中，页面不直接显示“准备运行、准备放行、准备执行、门禁、演员、锁等待、落账、核验”等内部或泛化词。
  - 每个进行中状态必须同时回答“现在在做什么、为什么要做、做完后会发生什么”，并把动作、节点和实际操作人替换进句子；禁止只显示“处理中”“执行中”“请稍候”“系统准备中”。
  - 阶段文案固定采用以下用户口径：

    | 内部阶段 | 页面标题 | 页面说明示例 |
    | --- | --- | --- |
    | `plan` | 正在确认这一步要做什么 | 正在查看第 3 步要操作的节点和动作，确认它属于当前流程。 |
    | `gate` | 正在检查现在能不能做 | 正在确认流程还在“审批人 1”节点、当前操作人还有待办，并且这项操作仍被目标平台允许。 |
    | `control` | 等你确认执行这一步 | 点击“执行这一步”后，系统会由“骆蒙恩”在“审批人 1”节点执行“同意”，只发送一次目标请求。自动模式显示“已确认，正在安排第 3 步”。 |
    | 账号/调度排队 | 正在等前面的操作完成 | 还有 1 条路径正在使用账号“骆蒙恩”。为避免同一账号的会话互相覆盖，本步骤会在它完成当前操作后继续。 |
    | `prepare` | 正在准备实际操作人 | 正在准备“骆蒙恩”的目标平台登录会话；这里只做账号准备，不会提交审批动作。 |
    | `submit` | 正在向目标平台提交动作 | 正在向目标平台发送一次“同意”请求，发送后不会重复提交。 |
    | `verify` | 正在回目标平台确认结果 | 请求已经发出，正在重新查看流程节点和待办，确认“同意”是否已经生效；这里不会再次发送动作。 |
    | `settle` | 正在保存这一步的结果 | 目标平台结果已经确认，正在保存本次运行记录，然后决定下一步从哪里继续。 |
    | 只读重试 | 目标平台暂时没有回复 | 正在第 2 次重新读取“审批人 1”的状态，下一次读取将在 2 秒后开始；不会重复发送写请求。 |

  - 人工控制按钮使用结果导向的文字：“放行”改为“执行这一步”，“继续运行”改为“继续执行后续步骤”；按钮下方必须有一句说明会执行哪个动作、由谁执行、是否会发真实写请求。
  - 错误、暂停、停止和待确认也要写明下一步：例如“这一步已经发出请求，正在等目标平台返回，停止不会撤回已经发出的请求”，不能只显示“失败”“已暂停”或“等待中”。
  - 阶段名称、阶段说明、按钮说明由后端或运行详情统一口径提供；前端不得为缺失字段回退到“处理中”等泛化文案。缺失说明时显示“当前阶段说明暂时不可用”，并保留日志入口。

### 不包含

- 修改目标平台代码、目标平台数据、权限、会话协议或接口语义。
- 增加目标写端点、改变写载荷、改变动作顺序、绕过门禁或减少写后核验。
- 自动跳过步骤、自动合并用户动作、自动提高同账号真实并发或引入跨进程共享锁。
- 引入 Redis、消息队列、独立性能平台、周期调度或新的运行事实体系。
- 修改历史运行结论；旧运行没有可靠请求耗时时，按“暂无真实请求耗时”展示，不回填猜测值。
- 重新设计运行画布、运行列表、事件流和动作配置页；只改节点动作详情内的信息层级与排版。

## 方案与任务

### T01：建立基准与安全不变量

- 选定与用户反馈一致的多路径、同账号样本，记录当前路径墙钟、目标请求耗时、任务列表请求数量和账号锁等待。
- 固化不变量测试：步骤顺序、目标写端点集合、每次尝试最多一次写、重试边界、核验屏障、最终判定和运行事实行数不变。
- 先验证现有 `network.log` 能按 `run_id/path_run_id/step_id/attempt/phase` 稳定归属请求；归属不完整时先补日志作用域，不在前端猜测。

### T02：减少重复只读读取

- 在 `internal/engine/step` 和 `internal/adapter/target` 内整理同一读取边界的上下文，复用同一页结果和事实快照；控制等待或会话变化后重新读取。
- 为候选任务扫描建立明确的查询批次和页结束规则；保留当前排序、节点过滤、处理人过滤和错误分类。
- 写请求之后丢弃写前事实和任务列表缓存，核验必须重新走目标读取；会话刷新仍由 F-029 统一处理。

### T03：收敛同账号排队

- 在 `internal/engine/schedule` 与 `internal/session` 的现有边界内，减少同账号路径对锁的重复争抢和无效轮询。
- 为等待补充结构化日志，至少区分调度排队、账号锁等待、用户放行等待和目标请求耗时。
- 验证不同账号仍可按计划并发，同一账号仍串行，路径失败仍不终止其他路径。

### T04：增加真实请求耗时只读 DTO

- 以现有传输层日志为唯一事实源，按运行详情一次读取并归组请求明细，避免每个请求在详情接口中重复扫描日志。
- 扩展尝试详情 DTO 的请求摘要字段，至少包含 `phase`、`requestClass`、`endpoint`、`durationMs`、`statusCode`、`result`、`retryAttempt` 和安全的 trace 关联。
- 公开 DTO 不包含 SID、密码、完整请求/响应正文；原文继续由 curl 展开入口提供。
- 区分“目标请求耗时”和“步骤总耗时”，并给历史记录与缺失日志提供明确降级文案。

### T05：节点动作详情重排

- 复用 `web/src/features/runs/RunNodePanel.vue` 和既有弹窗，不新增第二套运行详情。
- 把摘要指标、执行过程、目标请求明细、检查结论、原始日志按用户查看顺序排列；删除容易把七阶段总和误认为接口时长的单层标签呈现。
- 保留错误、重试失败动作、复制日志和 curl 的现有入口与安全条件；失败状态和待确认状态的文案不改变。
- 适配浅色/深色主题、窄桌面窗口、长接口名、无请求和多请求场景。

### T06：分层验证与基准复测

- 后端单元测试：请求归组、耗时口径、缺失日志、重复只读读取、写后缓存失效、账号锁等待分类。
- 后端集成测试：真实 MySQL 运行详情读取、同账号串行/不同账号并发、一次写约束、目标请求明细不泄露敏感字段。
- 契约测试：目标写端点白名单不变、公开 DTO 不带 SID/密码/正文、失败和待确认语义不变、详情接口只读。
- 前端结构测试：摘要先于明细、读写分组、真实耗时文案、无请求/失败/重试/长文本布局和原有控制入口不回归。
- 使用 T01 同一基准复测；比较请求数量、目标请求服务时间、本地等待和路径总耗时，不用单次外部目标抖动得出结论。

## 完成标准

- [ ] 同一基准样本的流程语义不变：步骤、节点、处理人、动作顺序、写端点、每次尝试写次数、核验和最终判定一致。
- [ ] 同一步内可复用的只读结果不再被重复无界读取；任务列表读取有明确页数上限和可观测请求计数。
- [ ] 同一账号仍严格串行，不同账号仍可并发；账号锁等待可在日志中与目标接口耗时分开确认。
- [ ] 目标请求耗时来自传输层真实计时，精确到毫秒级展示；不再用 `step.log` 秒级阶段差值代替接口耗时。
- [ ] 节点动作详情先展示步骤总耗时与目标请求耗时，再展示本地过程和逐条请求明细；读请求、写请求、失败、重试和无请求均能区分。
- [ ] 本切片涉及的运行详情页面中，所有进行中、等待、暂停、停止和错误文案都能说明正在做什么、为什么等待和下一步是什么；页面搜索不到“准备运行、准备放行、准备执行、处理中、执行中、系统准备中、门禁、演员、锁等待、落账、核验”等内部或泛化词。
- [ ] 详情接口只读，不返回 SID、密码、完整请求/响应正文；复制 curl 和日志入口保持可用。
- [ ] 基准复测显示：重复任务列表读取次数相对 T01 至少减少 50%；在目标响应分布相近的复测中，路径本地编排等待至少减少 50%，端到端路径耗时至少减少 30%。若外部响应波动超过 20%，以本地编排等待和请求次数两个指标作为主要判定，不把目标平台波动归因于本切片。
- [ ] 当前范围单元、集成、契约和前端定向验证通过，测试文件按类别保存到根目录 `test/`，不得跳过。
- [ ] 已检查同范围相似问题：缓存跨步骤污染、写后使用旧事实、同账号 SID 覆盖、阶段耗时与请求耗时混淆、详情长文本溢出、历史日志缺失和内部标识泄露。
- [ ] 文档状态更新为 `ready_for_manual`，并保留用户手工核对步骤；不得自动进入下一切片。

## 未决与需要用户裁决的事项

1. T04 默认从已有 `network.log` 解析请求明细，不新增数据库迁移；若实施时发现历史日志无法稳定归属请求，是否允许增加最小的只读请求事实落账字段，需要用户单独批准后再改架构。
2. 性能门槛以同一目标响应分布为前提；若用户希望优先保证接口请求次数下降而不是端到端时长，需要在实施前固定唯一主指标。
3. 详情中的目标接口路径默认作为次级信息展示；若用户不希望看到任何接口路径，可只保留“读取/写入 + 耗时 + 结果”，路径继续放在日志入口中。
