# F-050 快速同意准备与运行状态一致性修复

- 状态：ready_for_manual（已发布 2.200 并完成独立资源/数据核对，待用户页面验收）
- 授权：2026-10-26 用户明确要求修复“每一步都同意后仍显示节点待配置”，调整交互，能快速跑通。
- 依据：当前编译器固定尾动作、节点确认、配置落盘与运行前检查的实际源码；相关产品边界见 PRODUCT.md，技术边界见 ARCHITECTURE.md。
- 本次只处理快速同意方案的准备、状态与运行入口，不改变目标审批规则、执行器写入/核验、数据库结构或已有运行。

## 确认的问题

1. 编译器在额外动作为空时直接返回空场景，实际没有生成默认提交/同意；保存配置又用“用户额外动作数量”判断是否完成。纯默认动作的数量是零，路径因此一直待配置。
2. 快速模式只在新生成了人员策略时顺便确认节点；目标已固定人员或已有合法策略时，会漏记确认，甚至直接返回而不保存编译场景。
3. 模式选择只是下一次一键配置的参数，当前界面没有说清楚选中不等于已经准备；任务处理结束也只报“已处理”，不能证明节点和数据都可运行。
4. 已配置额外动作时，快速模式目前会保留它们，不能保证实际只有提交与同意。

## 本轮完成标准（修改代码前确定）

- 默认显示“每一步都同意”方案；明确分开“选择方案 → 准备所选路径 → 检查并运行”。只选模式不悄悄改配置、不启动运行。
- 点击准备并确认基础表单数据时，明确说明快速方案会替换所选路径的额外动作；节点主处理人合法策略及表单数据保留，动作专属人员随被替换动作删除。随机模式继续补齐空白，不覆盖人工动作。
- 快速方案保存编译器生成的提交/同意场景，确认所有可处理节点；没有额外动作、没有新人员项、重复准备都能正确处理，不需要逐节点点保存。
- 已保存人员策略必须按当前候选与人数规则复验；缺候选、人数不足、规则无法核对仍按具体节点报错，不伪造已配置。
- 节点状态按完整路径的确认进度和真实问题派生，不能再数额外动作；路径列表、配置页、运行前检查读取相同落盘事实。只保存一个节点也不能把其余未确认节点说成全部完成。
- 准备结束后依据刷新后的节点与数据双状态报告结果，接受现有服务端可运行的 base_ready；仅处理完但仍缺配置/数据时提示需处理，不弹“全部成功”。
- 同一配置链的回归发现前端多个额外动作的顺序号没有递增，后端会以重复顺序拒绝；本轮仅补递增，不改排序策略，保证随机/手工方案不被快速模式整改影响。
- 定向验证覆盖：零额外动作、固定/自选人员、重复准备、随机转快速、人员不足、未完成节点、真实 MySQL 列表/预检一致性，以及前端交互、类型检查与构建。
- 中文原子提交；使用现有一键脚本发布并核对服务、资源与数据保留。不启动验收浏览器，不发送目标提交/审批来代替用户验收；完成后停在 ready_for_manual。

## 人工核对

1. 勾选路径，选择快速同意并点击“准备全同意方案”，核对替换动作的提示，选择基础表单数据后开始准备。
2. 准备完成的路径显示节点已准备、数据可运行；点击“检查并运行”，无真实阻塞时可以启动，不要求逐节点保存。
3. 运行中发起节点提交，后续人工节点只同意；历史额外动作已替换，表单与处理人规则仍在。
4. 候选不足或基础数据缺必填时，应指出具体节点/字段；补好后重新准备可通过。随机方案仍保留人工配置。
