## 完成标准（开始实施前的唯一验收清单）

- [ ] 一键配置对每个可配置、可达的业务节点，除编译器固定的“提交/同意”尾动作外，至少落一条可安全编排的额外用户动作；已有人工动作和人员策略不被覆盖。
- [ ] 一键配置严格遵循目标前后端静态动作矩阵：发起节点只允许“保存草稿”作为额外动作，固定尾动作负责“提交”，草稿/驳回/撤回后的再次发起只能由编译器使用“重新提交”；审批/协同、实例容器和系统节点不得跨作用域分配动作。
- [ ] 目标节点声明“无处理人时跳过”且本次解析确实没有处理人时，动作不发送写请求并记录为“目标已跳过”；未声明跳过、运行时自选人节点没有候选、或手动分支没有入口时必须阻塞，不能用空人员或随机人员凑数。
- [ ] 额外动作优先选择本路径尚未使用的动作，并用可复现的节点种子打散选择；同一计划、路径、流程结构重复点击不会因为随机数变化而产生不同结果。
- [ ] 额外动作必须经过完整场景编译和动作人员/参数校验；没有安全候选时明确报告具体节点和原因，不以“已配置”凑数，也不把系统动作或禁用动作写入配置。
- [ ] “同意”在当前预览、步骤记录、节点计划、动作详情、错误标题及历史 DTO 缺失字段的前端兜底中均显示为“同意”，已知动作键不再直接出现在用户可见文本。
- [ ] 复现路径 4217 的手动分支错误：运行前能根据已保存路径解析到 `b037...` 的分支 2 入口 `8b676...`，或在发送前明确阻塞；不再发送缺少手动分支入口的 `/flowInstanceApi/audit` 请求。
- [ ] 目标明确返回 `isSuccess=false`、`errorType=custom_choose`、`message=手动条件分支,请选择` 时，运行落为“阻塞”语义；只有写出后响应丢失、核验无法确认等情况才显示“结果待确认”。
- [ ] 节点动作详情首屏只回答：做了什么、调用哪个接口、耗时多久、接口返回什么、为什么能/不能继续；不把内部阶段、门禁项、追踪键和原始正文作为主内容。
- [ ] 接口耗时继续来自 `network.log` 的传输层真实计时；“步骤总耗时”和“接口等待”明确区分，未知不显示为 0ms，历史缺日志不做估算。
- [ ] 日志位置、trace、curl 等复制入口改为低干扰的次级操作；路径、文件名、复制按钮不再挤在一行或堆成彩色卡片，窄屏不溢出。
- [ ] 现有一次写、写后核对、重试边界、账号串行、动作顺序、运行快照和 F-033 过渡显示不被改变。

## 用户结果

用户点击“一键配置”后，路径中每个实际需要处理的节点都有一个除固定尾动作之外的可理解动作，且不同节点尽量覆盖不同动作；运行到节点时，用户能在一个简洁面板中直接知道接口、真实耗时、返回结果和停止原因。目标平台明确要求人工选择分支时，系统在发送前就指出“阻塞”，而不是把确定的业务拒绝伪装成“结果待确认”。

## 只读排查结论与证据

### 1. 一键配置实际上只会补固定动作，且已有任意动作的节点会被跳过

- `internal/service/path_action_configuration.go:953-1002` 用 `configuredNodes` 判断节点是否存在任意动作；节点只要已有一条动作，就不会再尝试补一条额外动作。
- `autoNodeActionCandidates`（同文件约 `1094` 行）只要节点有 `Base` 就立即返回 `approve` 或 `submit`，没有进入动作目录候选；没有 `Base` 时又只保留 `autoKindAdvancesFlow` 返回真的动作。
- `autoKindAdvancesFlow`（约 `1146` 行）排除了暂存、不同意、回退、加签、移交、催办、转发、关注等动作，因此“尽量覆盖不同动作”在当前代码中被“只能让主实例前进”覆盖。
- 当前测试 `TestAutoNodeActionSkipsNonAdvancingKinds`、`TestAutoNodeActionCandidatesOrderCoversThenSeeds` 固化了旧规则；F-034 必须先改测试口径，再改实现。

这不是要求删除安全校验。正确方向是：固定尾动作仍由 F-026 编译器生成，不能把它计作额外动作；从目录中挑选额外用户动作，逐候选试编译完整路径，只有场景可恢复、参数可构造、人员策略可满足时才接受。非流转动作也可以作为额外动作，但其恢复链、放行边界和一次写约束必须由编译器证明；证明不了就换候选并说明原因。

### 2. “同意”英文的来源是公开 DTO 信任了不完整预览名称，前端又回退到原始动作键

- `internal/model/action_orchestration.go` 已有 `ActionApprove = "approve"` 和 `ActionChineseName` 映射“同意”。`internal/service/run_orchestration.go:1621` 的 `actionNameOf` 也已有集中映射。
- 但 `previewDTO`（约 `1675` 行）直接透传 `preview.ActionName`；导航/历史/旧运行或目录缺失时该字段可能为空，`RunNodePanel.vue` 又在多处使用 `currentPreview.actionName || currentPreview.action`，于是把 `approve` 直接渲染出来。
- 已落账步骤通过 `actionNameOf` 正常，当前预览和错误标题是最容易看到英文的入口。

修复应集中在后端 DTO 边界和一个前端兼容映射，不在每个模板补一处中文：已知动作键后端始终生成中文名；前端仅为旧 DTO 做同一张白名单映射，未知键显示“未识别动作（请查看日志）”，不回退原始英文键。

### 3. 1005/路径 8 的路径选择已保存，缺的是跨空节点的运行时绑定，不是路径解析漏选

只读查询得到：

- `test_execution_paths` 中 `path_id=4217` 为“路径 8”。`test_execution_path_choices` 有五条选择，其中 `route_node_id=b037ae8937574810a458c44d06eb9237`、`branch_id=2c26ec387e2f46fca04886d22fc1271e` 已保存。
- 当前真实图中该选择对应 `b037...（分支） -> 8b676f8c25b34fd2b7e54f94a59f2e3c（空节点）`；另一个分支入口是 `b9fc...（省区经理）`。因此路径解析没有漏掉手动分支。
- `curl.log` 的第 3 步 `/flowInstanceApi/audit` 请求只有 `nextAuditorList` 中的条件节点 `c359...`，没有手动分支入口 `8b676...`；目标完整返回 HTTP 200、`isSuccess=false`、`errorType=custom_choose`、`message=手动条件分支,请选择`，并列出空节点和省区经理两个 `branchNodes`。
- 当前路径运行 `123` 的数据库事实为第 3 步 `status=uncertain`、尝试 `verdict=uncertain`、`failure_class` 为空；这与“目标明确拒绝且实例仍停在发起人待办”的证据不符。

根因在 `internal/engine/step/executor.go:348-366` 的 `FollowingActionNodeKey` 会跳过导航/空节点并取下一个业务动作；`gate.go:310-325` 的 `chosenBranchEntryForNode` 只把这个下一个业务节点的目标 ID与已选分支目标比较。手动分支选择的入口是空节点 `8b676...`，而下一个业务动作的目标是后续人工节点，所以比较失败；审批载荷随后只带了其他后继人员信息。

同时，`internal/engine/verdict/classify.go` 只有清单内前置拒绝文案才返回 `InitialPreRejected`；“手动条件分支,请选择”落入 `InitialUnexplained`，即使 HTTP 200 和 `isSuccess=false` 都明确，也被三值矩阵归为 `uncertain`。这解释了日志“请求发送成功”与页面“结果待确认”同时出现：请求确实发出，但目标已经完整拒绝，工具的语义清单没有覆盖该拒绝形状。

### 4. 详情已经有真实请求计时，但首屏仍然堆叠了排查字段

- `internal/service/run_request_timings.go` 已从 `network.log` 解析 `step_id/attempt/phase/endpoint/duration_s/status_code/result`，这是 F-030 要求的真实接口计时来源。
- `RunNodePanel.vue` 当前详情仍按“摘要、四个指标、本地七阶段、请求明细、这一步的检查、尝试记录、原始 curl”连续堆叠；四指标和阶段流把用户注意力引向内部过程，目标返回正文/停止原因没有以一句话结论置顶。
- 同一组件在中断节点上无条件显示“结果待确认”（约 `100` 行），没有区分确定阻塞、确定失败和写结果不确定；复制日志位置、复制 curl、trace 也以散落文字按钮呈现。

F-034 只收敛信息层级，不删除日志事实：开发排查仍可在折叠区复制日志和 curl，普通用户首屏只看业务结论和安全摘要。

### 5. 前后端静态规则复核：当前方案还需要收紧动作安全边界

这次补充不是另起一套业务规则，而是把目标前端 `GroupApproveManage` 与后端 `FlowOperateServiceImpl` 已经存在的门禁逐项写成一键配置的候选矩阵。当前实现只做了作用域/节点类型和部分目录过滤，不能据此声称“分配到的动作在当前节点一定可执行”。前端证据包括 `EnterpriseExamineOpinion.vue` 的 `temporaryStorage -> /web/flowInstanceApi/storageFormData`、`handleSaveDraft -> /web/flowInstanceApi/submit(status=draft)`、重新发起 -> `/web/flowInstanceApi/reSubmit`；后端证据包括 `FlowOperateServiceImpl` 的空节点递归、`nodeSkip` 分支和 `validateHandBranchAndReturnExecuteNode`/`validateNodeRunNodeChooseIsExistPersonnel` 校验。

#### 5.1 允许矩阵（固定尾动作不计入额外动作）

| 配置位置 | 一键配置最多补的额外动作 | 必须满足的静态事实 | 明确禁止 |
| --- | --- | --- | --- |
| 发起节点 `start` | `save_draft`（目标页面按钮“暂存/保存草稿”） | 作用域为 `initiator`；目标是新建或草稿实例 | 把 `submit` 或 `resubmit` 当随机额外动作；在审批节点放发起动作 |
| 普通审批/协同节点 `common/synergy` | `storage_form_data`、或经证明可恢复的 `add_sign`/`transfer`/`reject`/`rollback`/`retrieve` | 作用域与节点类型匹配；动作专属人员策略、候选人数和参数均能按本次目标目录编码；恢复动作的前驱、演员和路径均可编译 | 把固定 `approve` 当额外动作；把实例动作或发起动作挂到节点；没有动作专属候选时自动填人 |
| 实例动作容器（空节点键） | 只在该容器内按实时目录选择一条可证明的实例动作（如 `urge`/`follow`/`forward`/`withdraw`） | 必须满足实例作用域、可见性、创建人/运行状态、催办接收人或转发候选等目录门禁；不参与“每个业务节点一条”计数 | 把实例动作复制到业务节点；把 `unfollow` 单独配置，或让实例动作替代节点动作 |
| 条件、手动、并行、汇聚、空、结束、定时、子流程、回调等系统节点 | 不补动作，只保留导航/只读语义 | `SystemOnly=true` 或节点类型属于系统自动集合 | 任何用户动作、处理人策略或“统一动作”记录 |

其中 `submit` 是发起节点固定尾动作，`approve` 是审批/协同节点固定尾动作；两者由 `internal/engine/scenario` 生成。若此前动作把实例置为 `draft/rejected/withdraw`，固定尾动作运行时才改为 `resubmit`。`resubmit` 是恢复链动作，不是可由一键配置随机分配的用户动作。

#### 5.2 “无处理人时跳过”必须与“运行时自选”分开

目标后端的递归逻辑在 `FlowOperateServiceImpl` 中是明确的：普通配置人员解析为空时，只有节点 `nodeSkip/isSkip=true` 才递归到后继节点；`isSkip=false` 或未声明时返回当前节点并等待/报错。这个规则不能简化成“所有解析为空都跳过”。

- `isSkip=true` 且当前目标处理人解析为空：允许保存节点动作，但执行器必须先读取事实；只有待办/当前节点已经落到路径后方时才记录“目标已跳过”，不发审批、暂存、回退等写请求。
- `isSkip=false` 或 `isSkip` 未声明且解析为空：动作不能被视为可执行，运行前或当前节点门禁应以“目标未找到处理人且模板不允许跳过”阻塞。
- `auditType=run_node_choose` 是另一条硬规则：目标后端的 `validateNodeRunNodeChooseIsExistPersonnel` 在 `nextAuditorList` 为空或没有匹配 `nodeProxyId` 时直接抛出“未设置审批人”。即使候选范围为空，也不能套用 `isSkip=true` 的普通节点跳过语义；一键配置不得用空数组伪造成功。
- 手动条件分支的选择对象也必须保留“入口事实”。目标后端 `validateHandBranchAndReturnExecuteNode` 只按 `nextAuditorList[].nodeProxyId` 匹配分支入口；入口是空节点时仍必须发送该空节点的 `nodeProxyId`，但不附带虚假的 `bizId` 或人员。缺少入口才是“手动条件分支,请选择”的阻塞原因。

#### 5.3 当前代码的安全缺口（实现时必须逐项补齐）

1. `AutoConfigurePathActions` 当前用 `configuredNodes` 判断“节点有任意动作”，有动作的节点就不补额外动作；`autoNodeActionCandidates` 遇到 `Base` 又直接返回 `approve/submit`，这会把固定尾动作伪装成用户动作。
2. `autoKindAdvancesFlow` 只允许同意、保存草稿、重新提交、撤回，反而排除了可安全作为前置检查点的审批暂存，也没有表达加签/移交/回退/取回各自的候选人与恢复约束。应改为先套本节矩阵，再逐候选完整编译，而不是用“能否前进”一个布尔值代替安全证明。
3. `scenario.Compile` 当前调用了 `validateActionStructure`、回退目标和关注提醒，但文件中定义的 `validateActionState`、`validateNodeOrder` 没有进入编译主流程；一键配置不能把“调用了完整编译”当成状态顺序已经校验，必须接入或在自动候选预检中等价执行。
4. `validateActionPersons` 只对加签/移交/转发读取动作私有人员；候选策略必须与节点主处理人键分离，并在 `ResolveActionPersonIDs` 前验证候选仍属于本次目标目录。缺候选时应淘汰候选并记录原因，而不是保存空 `userIds`。
5. `personConfig` 在 `run_node_choose` 有范围但 `Candidates` 为空时会标成“候选为空/需要处理”，这对 `isSkip=true` 的普通节点与运行时自选节点混在一起。实现时必须按目标后端规则分型：普通节点可跳过时进入“目标可能跳过”状态；`run_node_choose` 仍然是“必须显式选人”的阻塞。
6. `targetSkippedStepReason` 目前只依据实例待办是否落到后方节点推断跳过，没有携带目标 `isSkip` 和节点审批类型。应把这两个事实加入 `NodeInfo/InstanceFacts`，只有“模板允许跳过 + 目标事实确实越过本节点”才返回 `TargetSkipped`，避免把路径解析错误、权限问题或尚未生成待办误判为正常跳过。

#### 5.4 一键配置的安全算法（实现指导）

1. 先按真实图的可达序列为每个节点生成静态能力记录：节点类型、配置位置、`isSkip`、审批类型、固定尾动作、目标目录、动作专属候选、候选人数上下限和恢复前驱；系统节点和未选分支直接标记“不参与”。
2. 对每个动作先执行结构过滤：作用域、节点键、目录 `Enabled/SystemOnly/SystemInserted`、必填参数来源、动作专属人员策略、实例容器归属、回退前驱和手动分支入口全部通过后才进入排序；任何空候选不得用随机值补齐。
3. 对剩余候选按“安全等级 -> 本路径未使用 -> 稳定种子”排序。建议安全等级为：`start/save_draft`、审批 `storage_form_data`、有完整候选的 `add_sign/transfer`、有完整恢复证明的 `reject/rollback/retrieve`，实例动作单独排序；安全等级相同才追求动作多样性。
4. 每接受一条候选，都用与手工保存相同的人员编码、`scenario.Compile`、状态顺序、节点顺序和恢复链预检；预检必须验证：第一节点不会重复提交、草稿后只生成一次 `resubmit`、固定尾动作位置唯一、恢复链不跨未选分支、动作不会回到前序节点而没有恢复步骤。
5. 运行时继续做目标事实门禁：当前待办属于谁、节点是否仍是人工节点、`isSkip` 是否允许无处理人跳过、手动分支入口是否已绑定、动作专属人员是否仍在候选范围。门禁失败不发写请求；可证明越过且允许跳过才记“目标已跳过”，其余记“阻塞”。
6. 对每个业务节点最多补一条额外动作；一键配置不得因为固定尾动作、空节点、系统导航或目标自动跳过而把节点状态错误标成“已配置”。无候选时返回节点名、动作名和淘汰原因，供用户决定手工配置或保留未完成。

### T02：重做一键配置为“固定尾动作之外的一条安全额外动作”

1. 在 `AutoConfigurePathActions` 中把“是否已有任意动作”改为“该节点是否已有额外用户动作”。已保存的人工动作、参数和人员策略必须原样保留；只有没有额外用户动作时补一条。
2. `Base` 只表示编译器固定尾动作：发起节点为“提交”，审批/协同节点为“同意”。一键配置的额外动作不能用 `Base` 凑数，也不能将系统自动/系统插入动作写进 `user_actions`。对现存自动生成结果，按当前接口重新生成时要按动作来源/稳定键准确识别并清掉错误的固定动作记录，不能靠动作名称猜测。
3. 候选来源必须是该节点这次目标事实投影出来的 `Catalog`：`Enabled=true`、非 `SystemOnly`、非 `SystemInserted`，作用域和节点键匹配；固定尾动作不进入候选。需要处理人的动作只有在能按当前 `PathConfigPerson` 生成合法策略时才可接受，动作专用人员策略不能复用节点主处理人键。
4. 候选排序采用“安全可编译过滤 -> 本路径未使用优先 -> 稳定种子轮转”。种子由 `planID/pathID/nodeKey`（必要时加动作目录版本）派生；先按 `Kind` 稳定排序，再以种子偏移，最后将 `used` 未覆盖动作稳定前置。不要使用全局时间随机数，确保重试和测试可复现。
5. 对每个候选执行与手工保存相同的 `mergeNodeActions`、参数/人员校验和完整 `compilePathActions`。候选动作导致恢复链不可生成、必填参数无法安全生成、动作目录当前禁用或目标节点不是可配置业务节点时，记录候选失败原因并试下一个。
6. 每个可配置、可达业务节点最多由本次自动操作补一条额外动作；已有一条或多条额外动作的节点不重复追加。没有任何可安全候选时，该节点保持未完成，并在任务结果/路径状态中显示“节点 X 未找到可安全配置的额外动作：原因 Y”，不得把固定尾动作视为完成。
7. 保存仍使用现有一次读取、一次事务写入和幂等边界；不要为动作多样化添加目标请求、逐节点保存或数据库迁移。

建议保留/新增的纯函数边界：`autoNodeActionCandidates` 返回已过滤、带动作级失败原因的候选；`autoExtraActionForNode` 只负责选一条；`compileAutoCandidate` 只负责验证完整场景。函数上方补中文注释，说明“不覆盖人工事实”和“固定尾动作不计入额外动作”的约束。

### T03：统一中文动作名

1. 在 `previewDTO` 及所有公开运行 DTO 生成处统一调用 `actionNameOf(string(action))`；非空的业务展示名也要确认属于可信中文投影，不能把原始动作键直接当名称。

### T04：在发送前正确绑定手动分支，并把确定拒绝归为阻塞

1. 在 `buildRunContext` 之后保留真实图边和路径选择的映射，不只保留 `routeNodeID -> targetID` 的扁平值。实现一个只读 `resolveBranchEntriesForTransition(currentNodeID, nextBusinessNodeID, graph, branchSelections)`：沿当前真实路径走过 sequence、manual、condition、parallel、empty/navigation 节点，返回本次实际跨越的手动分支入口；必须精确匹配当前 transition，不能使用路线第一条分支兜底，也不能按名称猜测。
2. `submit`、`resubmit`、`approve` 共用这个解析器。预览阶段和真正写入前的待办刷新使用同一解析结果；结果冻结在本次运行上下文中，写前只刷新任务号/流程代理，不重新猜路径。
3. 若图中存在已保存手动分支但本次 transition 无法解析入口，写前门禁直接返回 `BlockReason`：“当前路径没有找到从“分支”选择的入口，请重新选择路径”，不发 `/flowInstanceApi/audit`。若一条 transition 经过多个手动分支，全部按目标协议要求加入，且顺序稳定。
4. 在 `internal/engine/verdict` 的目标拒绝清单中登记 `audit + custom_choose/手动条件分支,请选择`（以及已验证的同类“未设置审批人”前置拒绝），证据必须同步 `docs/TARGET_SEMANTICS.md`。目标完整响应 `HTTP 200 + isSuccess=false + 精确业务拒绝` 且执行前后事实未变化时，判为确定失败/无副作用；展示层把该类“前置条件未满足”标记为“阻塞”。
5. 不要把所有 `target_rejected` 都改成“阻塞”：权限拒绝、数据拒绝等仍保留“失败”。增加明确 `stopKind`/`blockedReason` 公开投影，或由后端按受控拒绝清单生成，前端不得用任意错误文案模糊猜测。
6. 运行状态模型仍可保持 `PathRunStatusFailed` 与现有终态迁移，避免为一个展示词增加状态机和数据库迁移；“阻塞”是确定失败中的业务阻塞展示语义。`awaiting_reconciliation` 只保留给传输中断/响应丢失/核验不可判定。
7. 失败落账继续使用现有 `failure_class`、`reason` 和门禁/事实快照；公开 DTO 再按受控清单稳定派生 `stopKind=blocked`。若确需结构化保存，复用现有 JSON 快照，不新增表或列；不能让目标返回消息只存在日志而 API 详情拿不到。

### T05：扩展安全的请求结果摘要

1. 保持 `RunRequestDTO` 的真实字段和安全边界，新增最小的 `endpointName`、`resultSummary`、`blocking`（或等价字段）即可；不要返回 SID、密码、完整请求/响应正文。
2. `resultSummary` 应来自结构化 `WriteResponse.Message/Code`、传输状态和已有尝试原因：例如“目标已接受请求”“目标拒绝：手动条件分支,请选择”“连接未建立，未发送”。读请求没有业务 message 时显示“读取成功/读取失败（HTTP N）”，不要编造返回对象内容。
3. `requestClass=write` 只代表真实写请求，不因失败而隐藏；`statusCode=200` 不能单独显示成功，必须同时看 `result` 和业务摘要。未知耗时仍显示“耗时未知”。
4. 尝试级 `requestSummary` 继续分别计算步骤总耗时、目标请求总耗时、写请求耗时与次数；不要把准备账号、读取待办、前端轮询算进接口耗时。

### T06：重排节点动作详情和复制入口

将 `web/src/features/runs/RunNodePanel.vue` 的步骤详情收敛为以下固定顺序：

1. **结果摘要**：状态（成功/阻塞/失败/结果待确认）、动作中文名、节点、处理人、步骤总耗时；阻塞或失败时紧邻显示一句“为什么不能继续”和“下一步怎么处理”。
2. **接口请求**：按真实发生顺序的简洁行列表，每行只显示“读取/写入、接口路径、真实耗时、HTTP/业务结果摘要”。接口路径为次级等宽文本，可换行；不显示 phase、内部键或追踪 ID 作为主列。
3. **耗时说明**：用一句白话解释步骤总耗时与接口等待的关系，例如“这一步共 6.3 秒，其中目标接口等待 2.1 秒，其余时间用于读取当前待办和保存结果”。没有可靠请求日志显示“暂无真实接口耗时”，不显示 0ms。
