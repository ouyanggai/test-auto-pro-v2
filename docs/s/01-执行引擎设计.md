# 执行引擎设计

## 1. 完成标准

本改造只有满足以下条件才算完成：

1. Go 可以创建一个 runtime 会话，指定账号、SID、流程实例、任务、节点、表单数据和动作。
2. runtime 可以加载真实 form-runtime 页面和目标 Vue 组件，不需要打开可见窗口。
3. Go 可以通过稳定的业务命令调用提交、同意、不同意、保存草稿、审批暂存、重新提交方法，不调用按钮、不查元素、不使用坐标。
4. FormMaking 的表单 JSON 事件、目标自定义组件方法、表单校验和远程请求按目标页面原顺序执行。
5. runtime 发出的每个目标请求都被转发到 Go；Go 使用当前账号缓存的 SID 发送并将原始响应返回 runtime。
6. 一个动作的所有请求和异步回调结束后，runtime 返回完整请求轨迹、表单前后数据、业务摘要和异常；Go 再做一次目标事实核验。
7. 同一账号串行、不同账号并行；账号切换不复用旧 BrowserContext，不发生用户、表单、Vuex 或回调串线。
8. 目标写请求发出后发生响应丢失时，不重新调用 runtime 的写方法，不重复发送流程动作，进入现有结果待确认流程。

## 2. 总体结构

```text
Go cmd/server
  ├─ 计划、路径、动作编排
  ├─ 账号和 SID 会话管理
  ├─ runtime 会话管理器
  ├─ WebSocket 指令发送和事件接收
  ├─ 目标事实读取、写后核验、结果裁决
  └─ 完整请求/响应和运行事实落盘

form-runtime 执行服务
  ├─ Playwright + Chromium 无头实例
  ├─ 每次任务独立 BrowserContext
  ├─ 固定 runtime 路由和真实 Vue 组件树
  ├─ 注入 window.__runtimeBridge__
  ├─ 业务命令适配器
  ├─ page.route() 网络拦截
  └─ 事件、请求、异常和完成状态回传
```

### 2.1 无头浏览器的使用边界

无头浏览器是没有可见窗口的 Chromium。它仍然提供真实浏览器的 DOM、Canvas、文件、定时器、XHR、Fetch、Vue 生命周期和组件挂载能力，因此可以运行现有目标前端代码。

本项目不把它当 RPA 使用。执行器禁止：

- `page.locator()`、`page.$()`、XPath、CSS 选择器找业务控件；
- `page.click()`、`page.fill()`、键盘、鼠标和坐标；
- 根据按钮文字或页面截图判断动作；
- 通过页面视觉变化代替目标请求和事实核验。

允许的 Playwright 用法只有：启动/关闭浏览器、创建/关闭 BrowserContext、加载固定 runtime 路由、注入桥接、拦截请求、监听异常和收集页面事件。

### 2.2 为什么不采用 jsdom/happy-dom

目标 FormMaking 和自定义组件会使用文件上传、Canvas、ResizeObserver、真实 DOM 生命周期、富文本或第三方组件。jsdom/happy-dom 缺少其中一部分能力，可能在简单表单通过、复杂表单运行到中途才失败。使用固定 Chromium 运行真实前端代码，减少人为补浏览器 API 的工作。

## 3. runtime 会话隔离

### 3.1 一次执行一个 BrowserContext

每次 Go 执行一个节点动作时创建新的 BrowserContext。Context 内包含当前账号的 cookies、localStorage、sessionStorage、SID、Vuex、表单组件树、请求监听器和异步回调。

动作完成、失败或超时后关闭 Context。第一版不复用 Context，先保证隔离正确；后续只有经过资源压测和状态清理验证才允许池化复用。

### 3.2 Go 侧排队规则

- 队列键使用目标账号唯一键。
- 同一账号同一时刻只能执行一个 runtime 动作。
- 不同账号可以并行，但并发上限必须由配置控制。
- Context 创建失败、页面加载失败或关闭失败必须写入运行日志。

## 4. 页面和组件加载

### 4.1 第一版固定加载本项目 runtime

第一版不得直接加载目标平台完整导航页面。runtime 服务加载本项目 form-runtime 的固定执行路由，由该路由加载目标同步源码中的 FormMaking、`OtherSteps2.vue`、审批组件和已注册自定义组件。

目标页面代码保持原样运行；执行路由只提供必要的宿主数据和调用桥。

### 4.2 组件引用注入

在 form-runtime 组件树创建完成后，由 runtime 适配层主动把业务根组件的方法挂到：

```javascript
window.__runtimeBridge__ = {
  loadInitiate,
  loadApprove,
  execute,
  capture,
  destroy
}
```

Go 不依赖 `$parent` 层数查找组件。目标 JSON 脚本内部仍可以使用它自己的 `$parent`、`$refs` 和 `$store`，但外部调用只使用 `__runtimeBridge__`。

### 4.3 外部动作与目标方法

| Go 命令 | runtime 内部动作 | 目标行为 |
|---|---|---|
| `load_initiate` | 创建发起页面组件 | 读取/回填发起表单，等待远程数据完成 |
| `load_approve` | 创建审批页面组件 | 读取任务、权限、表单和附件 |
| `capture` | 调用 `getValues` | 返回含虚拟字段的当前数据 |
| `validate` | 调用目标表单 `getData` | 按动作决定是否校验 |
| `save_draft` | 调用发起保存入口 | 按目标草稿逻辑执行 |
| `submit` | 调用发起提交入口 | 执行提交前事件、流程提交和提交后处理 |
| `temporary_save` | 调用审批暂存入口 | 不推进任务，只保存当前检查点 |
| `approve` | 调用审批同意入口 | 执行同意专属业务和流程审批 |
| `reject` | 调用审批不同意入口 | 按目标不同意分支执行 |
| `resubmit` | 调用重新发起入口 | 执行重新提交前后业务 |
| `destroy` | 关闭组件和 Context | 清理全部状态 |

### 4.4 不同动作不能共用错误顺序

runtime 适配层不得把所有动作统一成一套流程：同意有表单校验和同意专属字段处理；不同意不执行同意专属字段校验；发起提交执行发起前置和后置事件；审批暂存带 `temporary: true`；重新提交带 `reInit: true`；保存草稿不能提前发送最终提交。

## 5. Go 与 runtime 的通信

### 5.1 连接方式

runtime 服务使用 WebSocket 与 Go 长连接通信。一个动作会包含多次请求、页面事件、异常和异步回调，不能依赖一个简单同步 HTTP 响应。保留 HTTP 状态查询作为兜底，但状态查询不执行动作、不触发目标请求。

接口：

```text
POST /runtime/session                 创建执行会话
POST /runtime/session/{id}/load       装载身份、流程和表单
WS   /runtime/session/{id}/execute    执行业务命令并推送事件
GET  /runtime/session/{id}/status     查询当前状态
POST /runtime/session/{id}/destroy    关闭会话
```

### 5.2 Go 发给 runtime 的命令

命令必须包含 `requestId`、`runId`、`pathRunId`、`stepId`、动作、实例、任务、真实节点、当前操作人、原发起人、当前表单、字段权限、审批意见、下一节点人员、分支选择、附件和工具流程名称。SID 只从 Go 当前账号会话传入，不由 runtime 自己登录。

流程名称只使用工具值。目标页面脚本如果尝试修改名称，适配层在最终流程请求发出前恢复工具名称；其他业务字段保留目标脚本结果。

### 5.3 runtime 请求转发给 Go

runtime 通过 `page.route('**/*')` 拦截所有目标 `/web`、`/flowInstanceApi` 和文件请求，并向 Go 发送方法、完整 URL、请求头、请求正文、动作和步骤编号。

Go 收到后：

1. 校验请求属于当前运行和当前账号。
2. 校验目标路径在允许清单中。
3. 对写请求应用现有一次写、会话失效和结果待确认规则。
4. 使用 `internal/adapter/target` 发目标请求。
5. 原样记录请求和响应到现有网络日志。
6. 把 HTTP 状态、响应头和响应正文返回 runtime。

runtime 使用 `route.fulfill()` 把 Go 响应交给页面原代码。不能由 runtime 自己直接访问目标平台。

## 6. 动作完成判断

不能以“调用方法返回”或“流程接口返回成功”单独判定完成。必须同时满足：业务入口返回或发出明确完成事件；请求计数归零并保持稳定窗口；页面没有 `pageerror` 或未处理 Promise rejection；业务完成事件没有失败项；没有正在执行的附件、文件状态、业务回调或后置处理；runtime 返回表单前值、最终值和请求轨迹；Go 重新读取实例、任务、节点和表单并按现有 `verify` 规则裁决。

任一条件无法确认时不得返回成功：响应丢失为 `uncertain`；目标明确拒绝为 `target_rejected`；流程未发出且页面业务异常为 `failed`；流程成功但后置业务失败为 `business_failed`；Context 崩溃且无法确认写出状态为 `uncertain`。

## 7. 请求、身份和停止

内网项目不脱敏。Go 记录完整请求方法、URL、请求头、SID、请求正文、响应状态、响应头、响应正文、运行编号、动作、异常堆栈、发送阶段、耗时和重试序号。不把 SID、密码、缓存、日志和构建产物提交 Git。

Go 停止动作后 runtime 不允许新写请求；已发请求继续记录真实结果。当前动作超时后停止后续业务回调，关闭 Context，不能再次调用原动作方法。每个操作人使用新 Context，关闭后释放路由拦截器、页面监听器、定时器和 WebSocket 请求。

## 8. 接入现有 Go 执行器

第一阶段只新增 runtime 执行器，不替换现有 Go 写路径。先让一个动作通过 runtime 完成并由 Go 核验，再接入 `internal/engine/step.Executor`。

接入后，`internal/engine/step` 继续负责七阶段、动作组、演员、暂停和停止；runtime 只替代表单相关动作执行入口；Go 不能在 runtime 动作完成后再次组装并发送同一个流程写请求；非表单、实例级、已确认不依赖表单运行时的动作继续使用现有 TargetClient；runtime 结果使用现有运行状态投影。

## 9. 能力边界和验证顺序

第一版支持 FormMaking JSON 事件、普通校验/联动/远程选项、已注册自定义组件、六个表单动作，以及通过 HTTP/XHR/Fetch 完成的业务保存、附件绑定和业务关联。

第一版不自动支持浏览器插件、依赖真实尺寸或拖拽的功能、在线 Office 未完成初始化的功能、未登记外部网络请求和无法由请求/回读确认结果的组件。遇到这些能力返回 `unsupported`，Go 阻塞当前动作。

验证顺序固定为：启动无头 Chromium；加载普通表单；执行 JSON `beforeSubmitAndDraft`；验证请求拦截转发和响应回填；完成提交；完成同意/不同意；验证两个 Context 隔离；验证失败、响应丢失、超时、SID 失效和 Context 崩溃；最后用真实目标结果与人工操作对比并登记能力。
