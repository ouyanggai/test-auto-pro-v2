# 资产清单：新项目该带走什么，该留下什么

这份清单基于对仓库实际内容的检查，并且**优先服从项目自己在 PRD 里写下的规则**（见 `01-PRD-产品需求真相文档.md` 里的 Further Notes），而不是我个人的通用工程经验——因为你们自己已经踩过坑、总结过一次了，没必要再绕回去。

## ⚠️ 最重要的一条，先看这个

**`参考代码/` 目录不在你上传的 GitHub 仓库里。**

检查 `.gitignore` 发现这一行：
```
# Local reference code, kept for implementation lookup only
/参考代码/
```

而根目录 `CONTEXT.md` 对"目标平台"的定义是：*"本文中'目标平台'唯一指 `参考代码` 目录内对应的前后端实现，所有流程能力和行为判断以该代码的真实逻辑为准。"* PRD 的 Further Notes 里也再次强调：*"目标平台代码和真实运行结果是流程、分支、人员和动作语义的唯一依据。"*

也就是说——**这是整个项目里优先级最高的参考资料，是所有业务规则的唯一真相来源，但它只存在于你本地机器上，没有进版本控制。** 新项目无论怎么组织，第一步都应该是把这份代码（`参考代码/java-serve/rsh-cloud-workflow-center` 等目录）妥善保留、纳入新项目能访问的位置，哪怖只读挂载也行，但绝不能弄丢。

## ✅ 建议带走的东西

### 1. `参考代码/`（本地，见上）
目标平台的真实前后端实现（Java + Vue），是流程规则、状态机、审批分支逻辑的唯一权威来源。**不是要抄它的架构，是要在实现自动化测试工具时，随时能回去读它的真实业务逻辑。**

### 2. `CONTEXT.md`（根目录）
已经整理成 `01-PRD-产品需求真相文档.md`。

### 3. 测试契约与真实场景清单
- `test/contracts/`（`e2e-minimal.md`、`live_regression.md`、`session.md`、`live_regression_catalog.json`）——这些是对目标平台真实接口行为的契约描述，比代码本身更稳定，值得直接带到新项目当验收基准。
- `test/e2e/` 下的分类（`condition_branch`、`minimal_flow`、`parallel_branch`、`random_regression`、`reproduce`）和 `internal/analyzer` 目录（`审批阶段表单人员预绑测试`、`岗级审批回退测试`、`并行分支运行时恢复`等中文命名的测试场景，你原始目录树里能看到几十个）——这些名字本身就是一份隐藏的"业务验收标准清单"，是真实测试过的场景，比任何 PRD 文字描述都具体。新项目可以把这份清单当作"必须覆盖的业务场景"起点。

### 4. 问题收集
- `问题收集/单实例动作程序与自主调度分析报告.md`（1053行，篇幅很大，是一份认真的分析报告）
- `问题收集/问题记录.md`
这些是"人"给出的判断和长期观察，价值高于任何自动生成的文档。

### 5. `docs/product/` 下的业务规则文档
`流程动作状态机基线规则.md`、`流程动作状态机改造实施计划.md`、`流程节点与动作统计.md` ——如果内容和 `01-PRD` 不冲突，可以作为更细粒度的业务规则补充；如果冲突，以 `01-PRD` 为准（它更晚、更权威）。

## 🟡 需要人工判断，不要直接照搬

### `internal/engine/` 的 Go 业务逻辑代码
这里有 22 个核心文件（状态机、并行调度、加签、分支控制、事件总线等），代表大量已经调通、跑过真实场景的实现经验。**但项目自己的 PRD 明确写了："V1 只用于识别常用账号、最近账号、流程搜索、分页、双击确认和安全路径重跑等已验证便利，不复用其业务代码。"**

这不是我的建议，是你们自己在吃过亏之后定下的规矩——业务规则必须重新对照 `参考代码/`（目标平台真实逻辑）推导，不能把 v1 当年写的分支判断、状态机逻辑当真理直接搬过去，因为 v1 的实现本身可能就包含没被发现的偏差。**这份代码的价值是"参考实现思路、少踩并发和状态机的坑"，不是"业务规则的来源"。**

### `internal/analyzer`、`internal/builder` 里的表单/人员解析逻辑
同样：可以读、可以参考"这类问题大概怎么解"，但字段映射、派生值计算这些具体规则要回到 `参考代码/` 核对，不能直接信任旧实现。

## ❌ 不建议带到新项目起点的东西（但不要删，留着做历史存档）

### `v2/` 整个目录下的实现代码
包括：
- 用 Element Plus 手写的第一版前端（`44A`~`66` 六轮"切换"的产出）——**已经被最新 PRD 的技术选型否决**（PRD 明确要求 Vue Vben Admin 5 + Element Plus 适配器作为应用基座，不是裸 Element Plus）。
- `v2/web`（vue-vben-admin 官方脚手架 + 在 `apps/web-ele` 里写的业务页面）——脚手架部分可以重新拉取官方仓库获得，不需要带着历史包袱；`apps/web-ele/src/workbench/` 下的业务页面实现，因为是在旧规格（`v2/CONTEXT.md`，已废弃）指导下写的，建议只作为"这个页面大概需要哪些交互元素"的草稿参考，重新对照最新 PRD 走一遍。
- `v2/internal/` 后端实现——同 `internal/engine` 的原则，规则要重新对齐目标平台，不直接信任。

### `v2/docs/adr/`（46份）和 `v2/docs/tickets/`（66个）
这些是过程文档，记录了"当时是怎么想的"，**读一遍能帮你理解走过的弯路，但不要当作新项目的任务清单直接复用**。原因见 `00-诊断报告.md`：这批任务几乎全部标记"completed"，但至少 UI 部分被证明是不可靠的自我验收；而且里面很多决策已经被更晚的根目录 `CONTEXT.md` 覆盖或推翻。如果要用，只能带着"批判性阅读"的态度，逐条对照最新 PRD 核实是否还成立。

### `task/v2/tickets.md`（T01~T20）
第一次 v2 重构尝试，卡在 T20 被放弃，同样只做历史参考。

## 一句话总结

**新项目的地基是两样东西：`参考代码/`（业务规则的真相）+ `01-PRD-产品需求真相文档.md`（产品规则的真相）。除此之外几乎所有代码，包括 v1 的 Go 业务逻辑，都只能当"经验参考"读一遍，不能直接信任、直接复用。** 这个结论不是我拍脑袋定的，是你们自己的 PRD 里白纸黑字写着的。
