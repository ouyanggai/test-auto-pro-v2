# 智能表单数据生成与 iframe 回传破局方案

## 研判目标

本目录记录 GLM 5.3、Kimi K3、DeepSeek V4 Pro 对当前仓库的联合研判，以及经过源码核对后的统一落地方案。

终极目标不是“生成一组看起来像表单的数据”，而是完成以下闭环：

```text
真实流程路径
  → 路径条件与模板/宿主规则统一编译
  → 使用当前账号可见候选的确定性求解
  → 真实 FormMaking 或宿主 Vue 页面渲染、联动、校验
  → iframe 回传完整 getValues JSON（含虚拟字段）
  → Go 后端按同一规则快照复验并保存
  → 后续真实运行前冻结 RunInputSnapshot，再由目标适配层编译提交数据
```

## 已核对的事实边界

- 现有 F-010 规则目录、F-007 表单工作区、`generator.go`、`path_form_solver.go`、`FormRuntimeFrame.vue` 和运行时安全边界已经是可复用资产，不推倒重写。
- `form-runtime/src/runtime/protocol.js` 已定义 `f007-form-runtime/v1`，不是“没有协议版本”；`formTemplate.js` 才是 FormMaking `getData(true)` 与 `getValues()` 的采集封装。
- SID 当前主要在 iframe 会话内存和目标只读请求通道使用，但这不是安全禁令；为内网排障可进入 URL、请求头、请求体、日志或后续持久化设计，不得再以“禁止泄露 SID”为由裁剪诊断信息。
- 当前配置表已保存完整 `form_values`、`form_seed`、`generated_field_paths`、`manual_override_paths`、`form_template_version`、修订号和幂等键；新增运行快照表不是本方案第一步的前提。
- 目标仓库的 FormMaking 与宿主 Vue 页面均以真实运行时为校验来源；主应用不得重画一套普通控件代替宿主页面。

## 完成标准

1. 三种指定模型已分别独立研判，并完成第二轮交叉评审；本目录保留其关键结论和分歧处理。
2. 统一方案覆盖：路径条件、模板校验、字段依赖、日期一致性、级联/集合、自定义组件值形态、候选权限、FormMaking、`vue_custom`、iframe、SID、宿主只读、后端复验、并发和未来运行输入。
3. 方案明确“现有能力 / 待实现能力 / 不做事项”，每个实施切片都有文件范围、退出标准和验收证据。
4. 方案不引入不可复现的 LLM 直接填值，不把未知协议猜成可执行，不提前执行目标平台提交或业务写接口。
5. 所有关键成功条件都能由 Go 契约测试、运行时消息测试、真实样本回放或人工页面核验给出证据。
