# GLM 5.3：端到端架构与数据契约研判

## 结论摘要

GLM 5.3 的核心判断是：当前不是“所有规则能力都没有”，而是已经存在三套经过验证的机制，却缺少可交换、可解释、可复验的统一中间表示。正确方向是收编现有能力，先建立规则 IR，再按层传播，最后保留现有有界确定性搜索兜底。

## 已证实能力

- F-010 规则目录已经把目标模板分为 `formmaking`、`vue_custom`、`unknown`，并按真实分页范围完成 735 槽位对账。
- `internal/formdata/generator.go` 已递归处理 FormMaking 容器、标准控件、级联、身份、自定义组件、人工覆盖、日期关联和虚拟字段。
- `internal/service/path_form_solver.go` 已基于真实候选做确定性回溯，限制 20000 次并支持 `eq/neq/gt/gte/lt/lte/contains/in`。
- `path_config_workspace.go` 已把路径条件投影、生成、保存时复验和模板版本检查接起来。
- `formTemplate.js` 负责真实 FormMaking 的 `getData(true)` 校验和 `getValues()` 完整值采集；`protocol.js` 与 `FormRuntimeFrame.vue` 已具备版本、会话、请求号、来源和超时边界。

## 真实根因

1. `Constraint` 是扁平字段操作符；日期关联、字段对字段比较、模板校验和路径条件分属不同通道，无法统一求交和解释。
2. 现有流程是“先填值、再覆盖约束、再回溯”，字段依赖还没有成为统一传播规则。
3. 求解失败常被归并为“未找到”，没有区分区间空交集、选项域清空、候选权限不足和前置分支抢匹配。
4. `vue_custom` 的读写依赖规则目录字段路径与宿主实例树；宿主字段不存在时若静默跳过，会产生“保存成功但运行缺字段”。
5. 配置值已经保存，但未来目标提交所需的 `form_values → 目标请求体` 仍必须由目标适配层按真实协议编译，不能由 iframe 私自转换。

## 建议的最小架构

新增或逐步收编一层 `ConstraintIR`，不与现有 `Field`、`Constraint` 并行成长为第二真相：

```text
域构造：真实选项 / 身份 / 当前账号候选 / 安全默认值
  → 常量传播：数值区间交集、枚举过滤、required 与可编辑边界
  → 依赖传播：A 变化导致 B 候选或必填状态变化；拓扑无环，环则降级
  → 现有有界确定性回溯：只处理传播不能消解的变量
  → 同一 IR 复验完整路径，输出结构化问题
```

IR 至少要带：字段规范化路径、值形态、操作符、常量或字段引用、约束来源、条件组、候选来源、阻塞等级和中文解释。未知比较方式、未知自定义组件和无法证明的动态脚本必须 fail closed。

## 重要边界

- FormMaking 与 `vue_custom` 共享字段、值形态、候选、约束和问题模型，但渲染和校验不合并：前者走真实 FormMaking，后者走 `HostVuePage` 与真实 Element 表单校验。
- 自定义组件登记 `serialization/valueShape/candidateSource/validation/playback/saveRoundTrip` 六类能力；外部对象只接受当前账号真实候选。
- 继续使用现有 `f007-form-runtime/v1`。只有破坏性变化才升版；回传应包含完整 `values`、生成/人工路径、校验结果和规则版本，后端不信任 iframe 自报的类型元数据。
- requestPolicy 由现有启发式迁移到规则目录只读请求清单前，先以影子模式统计实际命中；切换后默认拒绝未知请求，未覆盖请求必须结构化上报。

## 首个切片

P0 只做事实盘点和契约基线：建立字段/约束/候选矩阵、黄金表单回放、消息 golden JSON、求解复验器和只读请求覆盖率报告；不改变生产行为。退出条件是现有 F-010/F-009 回归全绿，所有失败能给出字段、来源、约束和阻塞等级。
